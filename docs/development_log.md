# 개발 과정 기록 (발표자료·질의응답 대비용)

시간 순서대로 무엇을 했는지, 왜 그렇게 했는지, 막혔던 부분은 어떻게 풀었는지 기록한다.
최종 발표 구성(문제→해결책→안전원칙→차별점)과 심사위원 예상 질문 답변에 그대로 활용할 것.

---

## 1. 프로젝트 지침 수립

`CLAUDE.md`를 프로젝트 루트에 만들어 팀(2인: A-데이터/라벨링, B-모델/서비스) 작업 기준을 고정했다.

- 절대 원칙 명문화: 출구 미확인≠대피 완료, 얼굴인식 금지, False All-Clear 최소화 등
- 클래스 정의(person/helmet/vest + 속성), 파이프라인 단계, MVP 범위를 미리 합의해둠으로써 이후 개발 중 스코프가 흔들리지 않도록 함

## 2. 방향 전환 — 화재 자동 탐지 추가

원래 기획(`docs/LastSight_AI_최종기획서.html`)은 "화재를 발견하는 AI가 아니라 대피 확인 AI"로 화재신호를 관리자가 수동 입력하는 설계였다. 논의 끝에 **CCTV로 연기·불꽃을 직접 탐지해 경보를 자동 트리거**하는 것으로 확장했다.

- **차별점 재정의**: "화재 탐지에서 그치지 않고, 그 이후 대피 이행까지 끝까지 확인하는 AI" — 화재 탐지 자체는 여러 상용 제품이 이미 하고 있어 그것만으론 차별화가 안 되고, 우리 핵심 가치는 여전히 "그 다음"에 있음을 유지
- 클래스에 `fire`, `smoke` 추가. person/helmet/vest와는 데이터 출처·목적이 달라 **별도 BDAI 프로젝트로 분리**하기로 결정

## 3. VSCode 프로젝트 구조 설계

- `backend/`(FastAPI) · `frontend/`(React+Vite) · `bdai_pipeline/`(BDAI SDK 연동 스크립트) · `data/` · `experiments/logs/`로 분리
- 기술 스택: FastAPI + React + conda(Python 3.12) — 이유: 팀이 conda에 익숙했고, 추론 코드(Python)와 API 서버를 같은 언어로 유지하기 위함
- 백엔드에 person/helmet/vest/fire/smoke 이벤트 라벨(`WorkerEvent`, `ObjectClass` 등)을 코드 상수로 정의해, 라벨링·규칙엔진·대시보드 표시 문구가 어긋나지 않게 함

## 4. 공개 데이터셋 조사

자체 촬영만으로는 시간이 부족하고, 특히 fire/smoke는 실제로 불을 낼 수 없어 촬영 자체가 불가능하다는 판단으로 공개 데이터셋을 병행하기로 함 (해커톤 규정상 외부 데이터는 라이선스 확인만 하면 허용).

브라우저로 각 데이터셋 페이지에 직접 접속해 라이선스·클래스·규모를 확인 후 아래 3개를 채택:

| 데이터셋 | 규모(채택분) | 라이선스 | 채택 이유 |
|---|---|---|---|
| Construction Site Safety (Roboflow) | 717장 | CC BY 4.0 | person/helmet/vest가 한 데이터셋에 다 있음 |
| SFCHD | 4,000장(12,372장 중 샘플) | 확인 후 사용 승인 | 실제 화학공장 CCTV라 우리 도메인(산업현장 CCTV)과 가장 유사 |
| Fire and Smoke Segmentation (Roboflow) | 201장(증강 제거 후) | CC BY 4.0 | 클래스명이 정확히 fire/smoke, polygon 라벨 |

**판단 포인트**:
- 데이터셋을 5개까지 검토했지만, person 클래스가 없거나(head만 있음) vest가 없는 것들은 중복·저효율이라 제외 — "많다고 좋은 게 아니다"라는 원칙으로 2~3개로 압축
- Fire and Smoke Segmentation은 표기상 7,110장이었지만, README 확인 결과 원본 141장을 50배 증강한 것으로 밝혀짐. 그대로 올리면 같은 원본의 증강본이 train/valid에 나뉘어 들어가 **데이터 유출(leakage)**이 생기므로, 파일명(`.rf.` 해시)으로 중복 제거해 원본 201장(train 141 dedup + valid 40 + test 20)만 사용
- SFCHD도 12,372장 전부가 아니라 시간 절약을 위해 4,000장만 무작위 샘플링(그래도 person 6,600 · helmet 5,164 · vest 5,209 라벨 확보, 목표치 초과)

## 5. BDAI SDK 실전 활용

플랫폼 문서만으로는 세부 API가 불충분해, `superb-ai` 파이썬 패키지를 설치 후 코드를 직접 뜯어(`inspect` 모듈로 실제 메서드 시그니처 확인) 정확한 사용법을 파악했다.

- `client.datasets.create()` → `client.assets.upload_paths()` → `client.projects.create(scope=...)` → `client.classes.create()`(스키마) → `client.annotations.bulk_create()`(라벨 반입) → `client.versions.create()`(스냅샷) → `client.training.create_run()`(학습) 순서로 실제 파이프라인 구축
- 부수 발견: `client.foundation.predict("zero", text_prompts=[...])`로 학습 없이 바로 쓸 수 있는 제로샷 탐지(ZERO)가 있음을 확인. fire/smoke를 처음엔 이걸로 처리하려다, **데모 안정성**(ZERO는 플랫폼이 스케줄에 따라 껐다 켜는 공유 엔드포인트라 워밍업 중엔 호출 실패 가능) 때문에 직접 학습으로 전환

## 6. 실제로 겪은 문제와 해결 (Q&A에 쓰기 좋음)

| 문제 | 원인 | 해결 |
|---|---|---|
| 빈 데이터셋으로 프로젝트 생성 시 오류 | BDAI는 데이터셋에 에셋이 1개 이상 있어야 프로젝트(scope) 생성 가능 | "데이터셋 생성 → 이미지 업로드 → 프로젝트 생성" 순서로 스크립트를 2단계로 분리 |
| 라벨 반입 시 `UUID is not JSON serializable` 에러 | 클래스 ID가 uuid.UUID 타입인데 문자열 변환 없이 전송 | `str()`로 캐스팅 |
| 대량 라벨 반입 중 API가 403(WAF)로 차단됨 | 짧은 시간에 반입 요청을 너무 빠르게 연속 전송해 레이트리밋에 걸림 | 배치 사이 대기시간 추가, 마지막 성공 지점부터 재개할 수 있는 `--skip-rows` 옵션을 스크립트에 추가해 중복 없이 이어서 처리 |
| BDAI 웹에서 라벨링 상태가 "대기·미배정"으로 표시됨 | 어노테이션 데이터(라벨 내용)와 워크플로우 상태(담당자 배정, 제출 여부)는 BDAI 내부에서 별개로 관리됨. SDK로 라벨을 직접 넣으면 어노테이션은 생기지만 워크플로우는 안 건드려짐 | `workflow.list_asset_states(annotated=True)`로 실제 라벨 존재를 확인해 문제 없음을 검증. 스냅샷은 워크플로우 상태와 무관하게 현재 어노테이션을 그대로 캡처하므로 학습에는 지장 없음 |
| PPE와 Fire/Smoke 학습을 동시에 시작하려다 `JOB_ALREADY_RUNNING` 에러 | 테넌트당 동시 학습 실행은 1개로 제한됨 | 순서대로 실행하도록 백그라운드 스크립트를 구성 (PPE 완료 대기 → Fire/Smoke 시작) |

## 7. 데이터 파이프라인 결과 (최종 수치)

- **LastSight PPE 프로젝트**: 이미지 4,680장 업로드, 라벨 16,973개 반입(person 6,600 · helmet 5,164 · vest 5,209), 스냅샷 `v1-imported`(4,480장, 라벨 없는 200장은 자동 제외)
- **LastSight Fire/Smoke 프로젝트**: 이미지 201장 업로드, 라벨 466개 반입(fire 276 · smoke 190), 스냅샷 `v1-imported`(195장)
- 사람이 캔버스에서 직접 그린 라벨은 0개 — 전부 공개 데이터셋의 기존 라벨을 SDK로 매핑·반입한 것 (자체 촬영분은 이후 별도로 라벨링 예정)

## 8. 모델 학습 (진행 중)

- PPE: `rf-detr-nano`(탐지), 100 에포크(early stopping 적용)
- Fire/Smoke: `rf-detr-seg-nano`(세그멘테이션, polygon 라벨 대응)
- 결과는 완료되는 대로 이 파일과 `experiments/logs/`에 추가 예정

## 9. 관리자용 구역·출구선 설정 UI

추적된 사람이 "출구를 통과했는지" 판정하려면 출구 위치를 좌표로 알아야 한다. 처음엔 JSON 파일에 개발자가 직접 좌표를 타이핑하는 방식으로 시작했는데, 데모 완성도를 위해 **관리자가 카메라 화면 위에 마우스로 클릭해서 구역·출구선을 직접 그리는 화면**으로 확장했다.

- **설계**: 출구선은 두 점(선분) + "내부 쪽" 기준점 한 점으로 정의한다. 기준점이 있는 쪽에서 반대쪽으로 넘어가는 순간을 "대피 확인"으로 판정하고, 반대 방향이면 "재진입"으로 판정한다. 이 방식은 대각선 출구선에서도 애매함 없이 방향을 계산할 수 있다.
- **판정 로직**: 외부 라이브러리 없이 순수 파이썬으로 point-in-polygon(레이캐스팅)과 두 선분의 교차 판정(외적 부호 비교)을 구현하고, 정상 이동·미이동·선분 밖에서 스침(연장선상에서는 만나지만 실제 선분은 안 만나는 경우) 등 5개 케이스를 단위 테스트로 검증했다.
- **UI 구현 중 겪은 문제**: 처음엔 이름 입력에 `window.prompt()`를 썼는데, 이런 브라우저 네이티브 다이얼로그는 자동화 테스트 도구를 멈추게 할 수 있어 화면 안 입력창 방식으로 교체했다 — 실제로 데모 시연 시에도 네이티브 다이얼로그보다 화면 안 입력이 더 매끄럽다.
- **실제 동작 검증**: 브라우저로 직접 이미지 업로드 → 구역 4점 클릭 → 이름 입력 → 출구선 2점+방향 1점 클릭 → 저장까지 전 과정을 실행해, 저장된 JSON 파일과 판정 로직이 실제 클릭 좌표를 정확히 반영하는 것까지 확인했다.

## 10. 상태 규칙 엔진 (state_engine.py)

구역 판정·출구 통과 판정 결과를 시간순으로 모아 최종 상태(대피확인/내부관측/출구미확인/재진입/카메라확인불가) 하나로 정리하는 로직.

- **핵심 설계**: 기본값을 EVACUATED가 아니라 INSIDE_OBSERVED(안에 있는 것으로 간주)로 두어, "아무 신호 없음"이 실수로 안전 판정이 되지 않게 했다.
- **가장 중요한 규칙**: 한 번 EVACUATED가 되면 REENTRY(실제 재진입 확인)가 아닌 다른 어떤 이벤트(추적 소실, 카메라 장애 등)로도 상태가 내려가지 않는다 — 밖으로 나간 사람이 카메라에 안 잡히는 건 당연하기 때문. 반대로 한 번도 EXIT_CROSSING이 없었다면 절대 EVACUATED가 될 수 없다.
- 11개 단위 테스트로 검증 (재진입 후 재이탈 시 다시 EVACUATED로 돌아오는 경우까지 포함).

## 11. 다중 객체 추적 (byte_track.py)

외부 추적 라이브러리(예: 상용 ByteTrack 패키지) 없이, ByteTrack의 핵심 아이디어만 가져와 순수 파이썬으로 경량 구현했다.

- **2단계 매칭**: 고신뢰 탐지를 먼저 기존 트랙과 매칭하고, 남은 트랙은 저신뢰 탐지와 한 번 더 매칭 시도 — 가려짐 등으로 확신이 떨어진 사람도 새 사람으로 잘못 만들지 않고 같은 ID를 유지시키는 ByteTrack의 핵심 트릭.
- **오탐 방지**: 저신뢰 탐지 단독으로는 새 트랙(새 ID)을 만들지 않음 — 노이즈가 새로운 사람으로 둔갑하는 것을 막는다.
- **점유 유지**: 몇 프레임 동안 매칭이 안 돼도(`max_lost_frames`) 트랙을 바로 지우지 않고 유지해 짧은 가려짐을 버틴다.
- 칼만 필터 대신 직전 이동량으로 다음 위치를 단순 외삽하는 경량 예측을 사용 — 사람 수가 적은 이 서비스 규모에서는 충분하고, scipy 등 추가 의존성이 필요 없다.
- 단위 테스트 6개로 검증: 동일 인물 ID 유지, 두 사람 ID 안 섞임, 짧은 가려짐 후 ID 유지, 오래 놓치면 새 ID 부여, 저신뢰 단독 무시, 저신뢰로 기존 추적 구제.

## 12. 참조 프레임 선택 (frame_selection.py)

구조카드에 쓸 "가장 알아보기 쉬운 사진"을 후보 프레임들 중 자동으로 고르는 로직.

- 박스 영역만 잘라 라플라시안 분산(선명도), 박스 크기, 전형적인 전신 비율(2.2)과의 유사도(가려짐 추정 근사치), 탐지 신뢰도 4가지를 가중합으로 점수화.
- 절대 임계값이 아니라 후보군 안에서의 상대 순위(min-max 정규화)로 비교 — 영상 해상도·조명 조건이 달라도 안정적으로 동작하게 하기 위함.
- 합성 이미지(선명한 노이즈 이미지 vs 흐린 단색 이미지)로 5개 단위 테스트 작성.

## 13. 프론트엔드 대시보드 고도화

- **평면도 실제 구현**: 그동안 텍스트 목록이던 평면도를, 구역·출구선 설정 화면에서 만든 데이터를 그대로 가져와 실제 지도로 렌더링하도록 바꿨다. 구역/출구선 그리기 로직을 `ZoneMapOverlay`라는 공용 컴포넌트로 분리해 편집 화면과 대시보드 양쪽에서 재사용.
- 작업자의 정확한 좌표까지는 서버에 없어서(마지막 구역 이름만 있음), 해당 구역 폴리곤의 중심점에 상태별 색상 마커를 찍는 근사 방식을 썼다. 브라우저로 실제 테스트 이미지+구역을 만들어 더미 작업자 데이터가 정확한 위치·색상으로 표시되는 것까지 확인.
- 아직 구역·출구선이 없는 카메라는 기존 텍스트 목록으로 자동 폴백 — 촬영 전에도 화면이 깨지지 않게.
- 전체적으로 색상 시스템(대피확인=초록/내부관측=빨강/출구미확인=주황/재진입=자주)을 CSS 변수로 통일하고, 카드형 레이아웃·상태 배지 등으로 스타일을 다듬었다.

## 예상 질의응답 초안

**Q. 왜 공개 데이터셋을 섞어 썼나요?**
자체 촬영만으로는 시간 안에 충분한 물량을 확보하기 어려웠고, 특히 화재/연기는 실제로 위험을 감수하고 촬영할 수 없어 원천적으로 자체 데이터가 불가능했다. 대신 우리 시스템의 핵심 차별점(추적·출구통과 판정)을 검증하는 시나리오 영상은 반드시 자체 촬영으로 확보한다.

**Q. 데이터 라이선스는 어떻게 확인했나요?**
브라우저로 각 데이터셋 페이지에 직접 접속해 라이선스 표기를 확인했고, CC BY 4.0처럼 상업적 이용이 명확히 허용된 것만 채택했다. 라이선스가 불명확한 데이터셋은 별도 확인 절차를 거쳤다.

**Q. Superb AI 플랫폼을 구체적으로 어떻게 활용했나요?**
데이터셋·프로젝트 생성, 스키마 설계, 라벨 반입, 스냅샷 관리, 모델 학습까지 SDK로 전 과정을 코드화해 재현 가능한 파이프라인으로 구축했다. 플랫폼 로그(데이터셋/프로젝트/스냅샷/학습 기록)가 그대로 심사 근거가 된다.

**Q. 문제가 생겼을 때 어떻게 대응했나요?**
(위 6번 표 내용 — 빈 데이터셋 제약, 레이트리밋, 동시 학습 제한 등을 실제로 마주치고 원인을 파악해 스크립트 수준에서 해결)

## 14. Fire/Smoke 데이터 추가 확보 (AI Hub 176)

첫 Fire/Smoke 모델이 mAP 0.01로 사실상 학습이 안 된 수준이었던 원인은 데이터 부족(중복 제거 후 195장)이었다. 공개 데이터셋 4곳을 후보로 검토했다.

- **탈락 사례 1 (AI Hub 71407)**: "화재" 관련 클래스가 있어 보였지만, 실제 웹페이지의 메타데이터 구조표를 끝까지 읽어보니 전부 소화기·용접기·단열재 같은 "화재 위험 장비/자재" 클래스였고 실제 화염·연기 영역 라벨이 아니었다. 4.5GB를 이미 받은 뒤 발견해 폐기 — 다운로드 전에 클래스 정의를 끝까지 확인하는 습관이 중요함을 재확인.
- **탈락 사례 2 (AI Hub 71751)**: 클래스 체계(FL=불꽃, SM=연기)는 정확했지만 파일이 최소 단위로도 약 100GB짜리 조각들이라 현실적 다운로드가 불가능해 보류.
- **채택 (AI Hub 176, "화재 발생 예측 데이터")**: "화재씬" 카테고리의 Training 원천데이터(9.08GB, 13,159장)와 라벨(292MB)을 받았다. AI Hub 자체 웹페이지에는 라벨의 `class` 필드(01~10) 값에 대한 텍스트 정의가 없어서, 별도로 "구축활용가이드" PDF(공식 데이터 명세서)를 받아 정확한 의미를 확인했다:
  - class 01/02/03 = 검정/회색/흰색 **연기** → `smoke`로 매핑
  - class 04 = **화염(화재)** → `fire`로 매핑
  - class 05~10은 "유사씬"(구름·안개·조명·햇빛 등 오탐 방지용 대조군) 전용이라 우리가 받은 "화재씬" 데이터에는 등장하지 않음(실측 샘플 3,000장 확인 결과 01~04만 존재)
- 이미지 13,159장은 전부 라벨과 1:1로 매칭되는 것을 사전 검증(라벨 zip에는 다른 파트의 라벨도 섞여 있어 533,159개였지만, 실제 보유한 이미지와 대응하는 것만 걸러냄).
- **부수적으로 발견한 AI Hub 공식 CLI 버그**: `aihubshell`의 병합 로직이 한글 파일명에서 `printf %q` 이스케이프와 `find -name`의 리터럴 매칭이 어긋나 항상 실패하는데, 병합 실패를 무시하고 "병합 완료" 메시지를 출력한 뒤 원본 파트 파일까지 삭제해버려 다운로드가 조용히 0바이트로 소실되는 버그였다. AI Hub API를 직접 호출하고 bash glob으로 병합하는 대체 스크립트(`scripts/aihub_download_merge.sh`)를 작성해 우회했다.
- **BDAI 반입 중 겪은 문제 두 가지**(둘 다 `data/bdai_resources.md`에도 기록):
  1. 프로젝트 스코프가 생성 시점의 에셋 목록(195장)으로 고정되어 있어, 새로 업로드한 13,159장이 "이 프로젝트의 데이터셋에서 파일을 찾을 수 없음" 에러로 전부 튕겨나갔다. `project_assets.bulk_add(project_id, filter={})`로 데이터셋 전체를 프로젝트 스코프에 재편입시켜 해결.
  2. 원본 폴리곤 라벨이 점을 평균 1,000개(최대 4,000개) 담고 있어(픽셀 단위로 촘촘히 찍은 크라우드 라벨링 특성) 1,000개씩 묶은 배치가 413(Request Entity Too Large)로 실패했다. `cv2.approxPolyDP`(Douglas-Peucker)로 폴리곤을 단순화(평균 53개 점)하고, 배치도 개수 대신 직렬화 바이트 크기 기준 동적 배치로 바꿔 해결. 그 과정에서 원본 라벨 데이터 자체에 `[96]`처럼 `[x,y]` 쌍이 아닌 결손 좌표점도 드물게 섞여 있는 것을 발견해 걸러내는 필터도 추가했다.
- **최종 결과**: Fire/Smoke 프로젝트가 195장(어노테이션 466개)에서 13,354장(어노테이션 23,646개, fire 10,318 · smoke 13,328)으로 확장됐다. 다음 단계는 새 스냅샷 생성 후 재학습.

## 15. Superb AI 멘토링 피드백 반영 + 합성 연기 기반 사람 탐지 강건성 강화

### 15.1 멘토링 피드백 반영 (평상시/비상시 두 축)

Superb AI 멘토링(`docs/Superb_AI_공모전_멘토링_QnA.md`)에서 "화재 이후 잔류인원 추적"에만 집중하면 데이터 부족·인식 오류로 구현 난도가 지나치게 높아진다는 피드백을 받았다. 열화상 카메라 대비 RGB CCTV의 강점, 잔류인원 정보를 확정 사실이 아니라 보조 정보로 제공해야 한다는 원칙 등 우리가 이미 설계에 반영해뒀던 부분과 정확히 일치하는 지적도 있었지만, 핵심 제안은 **프로젝트 축을 "비상시 대응" 하나에서 "평상시 예방 + 비상시 대응" 두 개로 확장**하라는 것이었다.

- CLAUDE.md를 갱신: 시스템 구성표를 비상시/평상시 두 그룹으로 분리, PPE 상시 점검·소화기 상태 확인·통로 적재물 확인을 평상시 축의 필수 기능으로 추가, 신규 클래스 `fire_extinguisher` 추가.
- 위험행위 탐지(금지구역 흡연 등)·발화 위험 물질 탐지는 신규 클래스·데이터 확보 부담이 커서 1차 구현 범위에서는 제외하고 "확장 아이디어"로만 문서화 — 스코프 크립 방지 원칙 유지.
- UI/UX 담당자를 위해 화면별 와이어프레임(평상시 안전 대시보드, 소화기·통로 점검, 비상 대시보드, 구조 브리핑 카드, 구역·출구선 설정)을 정리한 가이드를 아티팩트로 제작해 공유.

### 15.2 합성 연기(smoke) augmentation으로 사람 탐지 강건성 강화

**문제의식**: 화재 시 연기로 화면이 뿌옇게 변하거나 사람이 부분/전체적으로 가려지는 상황에서, 기존에 맑은 사진으로만 학습한 person/helmet/vest 탐지 모델이 얼마나 견딜지 검증된 바가 없었다. 실제 화재를 피워 촬영할 수 없으므로(절대 원칙), 이미 라벨링된 PPE 이미지 위에 디지털로 연기를 합성해 학습 데이터를 늘리는 방식을 택했다. JCCI 2026 학술대회 논문("산불 연기 탐지 DETR 모델의 DCP 채널과 합성 데이터 증강 적용 및 분석")에서 합성 데이터 증강이 실제로 mAP를 유의미하게 올린 사례를 확인해, 방향성의 근거로 참고했다(같은 논문에서 DCP 채널 추가는 오히려 역효과였다는 것도 확인 — 그럴듯해 보이는 기법도 검증 없이 적용하면 안 된다는 교훈으로 기록).

**`bdai_pipeline/synth_smoke.py` 설계가 여러 차례 시행착오를 거쳐 정착된 과정**:

1. *1차 시도*: fBm(fractal noise, Perlin 대체) 기반으로 화면 전체에 랜덤 위치 블롭을 흩뿌리는 방식. 노이즈 스케일이 작아 "연기 덩어리"가 아니라 얼룩덜룩한 노이즈 필터처럼 보이는 문제 발견 → 큰 스케일의 소프트 블롭(가우시안 감쇠) 위에 고주파 텍스처를 곱하는 하이브리드 구조로 재설계.
2. *사람 위치 문제*: 실제 CCTV는 카메라가 높고 넓은 화각이라 사람이 화면 대비 작게 찍힌다(SFCHD 데이터셋 샘플로 검증). 블롭 크기를 "사람 박스 크기" 기준으로만 잡으면 너무 작아 존재감이 없어, 화면 크기 기준 스케일과 사람 박스 기준 스케일 중 큰 쪽을 쓰도록 수정.
3. *강도 부족 문제*: 사용자가 "실제 CCTV 화재 화면만큼 뿌옇지 않다"고 지적 — 특히 사람이 여러 명 넓게 흩어진 장면에서 블롭 1~3개로는 대부분 빈 공간에 떨어져 사실상 무효과였다. 처음엔 "화면 전체에 옅게 깔리는 배경 연무" 레이어를 추가해 최소 시인성을 보장하려 했으나, 이번엔 반대로 "연기 덩어리가 아니라 필터를 씌운 것처럼 균일해 보인다"는 지적을 받아 배경 연무를 완전히 제거.
4. *"아무 데나 생기면 안 된다" 원칙 확립*: 사용자가 "연기는 사람/객체 주변에만 생겨야 한다"고 명확히 지적 — 블롭을 화면 랜덤 위치에 놓는 로직을 없애고, **라벨링된 박스마다 정확히 하나씩** 블롭을 앵커링하도록 재설계(박스 중심에서 살짝 흔들어 다양성 부여, 반경은 박스 크기의 1.2~2.2배).
5. *정규화 버그*: 박스가 여러 개일 때, "이미지 전체 최댓값 기준"으로 밀도를 정규화하던 코드가 우연히 가장 강하게 나온 박스 하나만 살아남고 나머지 박스들을 상대적으로 눌러 지워버리는 버그를 발생시켰다(사람 한 명만 진하게, 나머지는 안 보이는 현상으로 발견). 전역 정규화를 제거하고 각 블롭이 이미 0~1 범위인 점을 활용해 해결.
6. *색상 일반화*: 처음엔 검정/회색/흰색 3색을 확률적으로 골랐는데, 흰색이 밝은 배경(콘크리트, 눈밭, 하늘)과 섞여 안 보이는 문제가 반복됐다. "이 샘플 사진 하나에만 맞춘 수정이 아니라 수천 장 전체에 일반적으로 통해야 한다"는 지적에 따라, **고정 색상 대신 연기가 덮일 자리의 실제 배경 밝기를 측정해 항상 대비가 나도록 자동으로 색을 정하는 방식**(밝은 배경→어두운 연기, 어두운 배경→밝은 연기)으로 전환. 흰색 고정값은 제거.
7. *강도 단계 단순화*: "약함(light)"은 실질적으로 원본과 구분이 안 될 만큼 약해 의미가 없어 제거하고, medium/heavy 두 단계만 사용.

**실제 데이터셋 적용**: `bdai_pipeline/generate_smoke_augmented.py`를 새로 작성해, 기존 라벨(바운딩박스)을 그대로 재사용하면서 이미지만 연기 합성본으로 교체 생성하는 파이프라인을 만들었다(사람 위치가 안 바뀌므로 재라벨링 불필요). Construction Site Safety(521장)와 SFCHD(4,000장, 기존 샘플링분과 동일 규모)에 적용해 BDAI PPE 프로젝트에 추가 업로드.

**업로드 중 겪은 사고와 수습**:
- SFCHD의 옷차림 클래스가 `self_clothes`(사복=조끼 미착용)와 `safety_clothes`(안전복 착용)로 나뉘어 있는데, 처음에 실수로 둘 다 `vest`로 매핑해 라벨을 반입하려 했다(조끼 미착용 상태를 착용으로 잘못 라벨링할 뻔함). 사용자가 즉시 지적해 프로세스를 중단시켰으나, 중단 시점에 이미 배치 6개(6,000개 라벨)가 서버 전송을 완료한 상태였다 — 로컬 프로세스를 죽여도 이미 도착한 API 요청은 취소되지 않는다는 걸 재확인. 이후 `safety_clothes`만 `vest`로 매핑해 올바르게 재반입했지만, 이번엔 잘못된 6,000개와 올바른 14,953개가 함께 남아 어노테이션 총계가 예상보다 6,000개 많게 나왔다.
- 복구: 파일명 패턴(`_smoke0` = 증강본, `192.168.` = SFCHD 원본 IP 카메라 파일명 접두사)을 조합해 SFCHD 증강본 asset만 정확히 4,000개 추려내고, `project_assets.bulk_delete_annotations`로 그 asset들에 붙은 라벨을 전부(20,953개, 오염분+정상분 모두) 삭제한 뒤 올바른 매핑으로 한 번만 재반입. 최종 어노테이션 수(33,441개)가 기대값과 정확히 일치하는 것까지 확인.

**최종 결과**: PPE 프로젝트가 4,717장(어노테이션 16,973개)에서 9,238장(어노테이션 33,441개, person 12,906 · helmet 10,178 · vest 10,357)으로 확장됐다. 새 스냅샷(v2-smoke-augmented) 생성 후 재학습해 연기 상황에서의 탐지 성능 변화를 확인할 예정.

## 16. 평상시 예방 축 — 관리 구역(clearance zone) 감시 기능 설계·구현

멘토링 피드백(15.1)에서 나온 "평상시 안전관리" 항목 중 소화기 상태 확인을 구체화하는 과정에서, 애초 계획(소화기를 별도 객체 탐지 클래스로 학습)을 논의 끝에 더 단순한 방식으로 바꿨다.

**설계가 좁혀진 과정**:
- 처음엔 "소화기 감지"를 위해 공개 데이터셋(Roboflow, CC BY 4.0, 3,262장, `Fire_Extinguisher` 클래스)을 새로 받아 학습시키려 했다.
- 논의 중 "소화기·전기패널·비상구도 결국 다 같은 문제 아닌가"라는 질문이 나와, **"등록된 구역이 기준 화면과 달라졌는지 감시"하는 범용 규칙 하나로 통합**하는 방향으로 정리했다. 스프링클러/화재감지기 주변 적재 높이 위반도 후보로 검토했으나, 일반적인 CCTV는 사람·바닥 위주로 비스듬히 아래를 보게 설치돼 천장 근처가 화각에 안 잡히는 경우가 많아 제외했다.
- 소화기까지 이 방식으로 통합하기로 결정한 결정적 이유: 실제 CCTV 환경(카메라가 높고 비스듬한 각도로 작게 촬영, 공사현장 특성상 사람·자재가 계속 오감)을 고려하면, 대부분 정면·눈높이 사진으로 구성된 공개 데이터셋으로 학습한 탐지 모델이 각도 차이(도메인 시프트) 때문에 실제 배포 환경에서 잘 안 맞을 위험이 컸다. 반면 변화 감지 방식은 "같은 카메라가 찍은 자기 자신의 기준 사진과 비교"라서 각도·거리 문제 자체가 없다. 결과적으로 별도 데이터셋 확보·라벨링·학습이 통째로 필요 없어졌다.

**판정 알고리즘**:
- 단순 픽셀값 차이 대신 **SSIM(구조적 유사도)**을 직접 구현해 사용 — 조명 변화(그림자, 밝기 변동)에는 둔감하고 실제 물체가 생기거나 없어지는 변화에는 민감하다. scikit-image 의존성 없이 GaussianBlur 기반 지역 평균/분산으로 표준 SSIM 공식을 근사 구현했다(다른 규칙 모듈들처럼 외부 라이브러리 최소화 원칙 유지).
- 기존 person 탐지 결과를 재사용해, 사람이 구역과 겹친 프레임은 판정에서 제외(지나가는 사람·작업자를 방치물로 오인하지 않기 위함).
- 변화가 구역 면적의 20% 이상을 덮고, 그 상태가 지속 시간 기준을 넘겨야 "이상"으로 확정한다. 지속 시간은 처음 5분으로 잡았다가, "공사장은 사람·자재가 훨씬 자주 오간다"는 지적을 받아 15분으로 상향했다 — 구역별로 다르게 설정하는 옵션도 검토했으나 복잡도 대비 이득이 적어 전체 공통 상수 하나로 유지하기로 함.
- 상태는 정상→관찰중(변화는 있지만 지속 시간 미달)→이상 확정 4단계로 전이하며, `app/rules/state_engine.py`의 "잠깐 스친 신호는 무시" 원칙과 동일한 설계다.

**구현**:
- `backend/app/models/schemas.py`: `ClearanceZoneType`(소화기/전기패널/비상구), `ClearanceZoneDef`, `ClearanceZoneState`, `ClearanceZoneStatus` 추가. `ZoneMapConfig`에 `clearance_zones` 필드로 편입해 기존 구역·출구선 설정 API를 그대로 재사용할 수 있게 함.
- `backend/app/rules/clearance_zone.py`: 판정 로직 + 상태·기준화면 파일 영속화(`app/rules/zone.py`와 같은 패턴).
- `backend/app/api/zone_maps.py`: 기준화면 등록(`/baseline`), 상태 조회(`/status`), 프레임 평가(`/evaluate`), 조치완료 처리(`/resolve`) 4개 엔드포인트 추가.
- 단위 테스트 9개(규칙 엔진) + API 통합 테스트 5개, 전체 스위트 44개 전부 통과.

## 17. 출구 통과 판정의 전제 조건 재점검 — 아직 결론 안 남, 계속 고민 필요

기존 출구 가상선 판정(`app/rules/exit_crossing.py`)을 실제 CCTV 환경에 대입해보는 대화 중 중요한 구조적 질문이 나왔다.

- `check_crossing`은 "직전 위치(안쪽)"와 "새 위치(바깥쪽)" 두 점을 모두 확보해야 EXIT_CROSSING을 판정한다. 그런데 **사람이 문을 나서는 순간 카메라 화각을 완전히 벗어난다면, "바깥쪽 위치"라는 점 자체를 영원히 확보할 수 없다.**
- CLAUDE.md 절대 원칙("사람이 화면 가장자리로 나감 → 대피 아님, tracking_lost")을 그대로 적용하면, 카메라가 문턱 너머를 전혀 못 보는 출구는 **실제로 사람이 나갔어도 시스템상 영원히 "출구미확인"으로 남는다** — 안전을 위한 보수적 설계가 이 경우엔 오히려 시스템을 무용하게 만드는 역효과를 낸다.
- 즉 지금 방식이 실제로 작동하려면, **카메라가 문턱을 넘은 직후 한두 프레임이라도 그 사람을 잡을 수 있는 화각**이 전제돼야 한다는 게 명확해졌다. 이건 코드로 고칠 수 있는 게 아니라 카메라 설치/화각의 물리적 조건이다.
- 추가로 짚인 리스크(같은 대화에서): 문이 화면에서 작고 멀리 보이면 출구선 길이 자체가 짧아져 위치 오차의 영향을 더 크게 받고, 집단 대피로 병목이 생기면 추적 ID가 뒤섞일 위험이 있다 — 다만 이 경우들도 실패 방향이 "잘못 대피확인 처리"가 아니라 "출구미확인으로 남음"(안전한 방향)이라는 점은 확인됨.

**아직 결론 내지 않은 채 남겨둔 질문**:
- 관리자가 출구선을 설정할 때 "화면 가장자리에 너무 가깝게 그으면 경고"하는 정도의 UI 가드로 충분한가, 아니면 더 근본적인 보완이 필요한가.
- 카메라가 정말 문턱 너머를 하나도 못 보는 사이트는 이 기능 자체를 지원 못 한다고 명시할 것인가(제출 보고서의 한계 섹션에 포함), 아니면 다른 대안(예: 문 바깥쪽에 카메라를 하나 더 두고 두 카메라의 사라짐/등장을 시간상으로 대조하는 방식)을 검토할 것인가 — 후자는 다중 카메라 연동이라 스코프가 커질 수 있어 신중히 판단 필요.

다음에 이 주제로 다시 논의할 때를 위해 기록만 해두고, 지금 당장 코드를 바꾸지는 않았다.

## 18. 출구 통과 판정 폐기 → "화재경보 후 관측 지속시간" 모델로 전환 (17번 질문 해소)

17번에서 남겨둔 질문에 대한 결론: 근본적인 보완(다중 카메라 연동 등)은 스코프가 너무 커지고, UI 가드만으로는 "카메라가 문턱 너머를 아예 못 보는" 사이트에서 구조적으로 안 되는 걸 완화할 뿐 해결하지 못한다. 그래서 **출구 통과·대피 확인 판정 기능 자체를 없애기로 했다.**

**대체 설계**: "누가 탈출했는가"를 보는 대신 "화재 감지 이후 누가 아직 관측되고 있고, 얼마나 오래 관측되고 있는가"만 본다.
- CCTV는 구조상 문 바깥쪽을 절대 잡을 수 없는 경우가 흔하므로, 애초에 "바깥으로 나가는 장면"을 확인 대상으로 삼지 않는다.
- 화재경보가 발생하면 그 시점부터, 카메라에 계속 잡히는 작업자는 시간이 지날수록 위험 신호로 취급한다 — 기본 5분(`PROLONGED_PRESENCE_MINUTES`)을 넘도록 관측되면 `prolonged_presence`로 전환해 대시보드에 강조 표시한다.
- 화면에서 사라진 경우는 여전히 `tracking_lost`일 뿐, 안전도 위험도 확정하지 않는다 (CLAUDE.md 절대 원칙과 완전히 일치 — 오히려 이 설계가 그 원칙을 더 철저히 지킨다: 예전 모델은 "출구 통과 확인"이라는, 사실상 달성 불가능한 목표를 향해 가고 있었다).
- 사용자 요청대로 타임스탬프 로그도 함께 남긴다: 화재경보가 언제·어느 구역에서 발생했는지, 작업자가 언제부터 언제까지 어떤 상태였는지를 append-only JSON으로 기록한다.

**구현**:
- `backend/app/rules/exit_crossing.py` 삭제, `backend/app/rules/state_engine.py`를 `resolve_status(track_id, is_currently_observed, now, fire_triggered_at, camera_ok, ...)` 형태로 재작성 — 위치·경과시간만으로 4가지 상태(`inside_observed`/`prolonged_presence`/`tracking_lost`/`camera_failure`) 중 하나를 결정하는 순수 함수로 단순화.
- `backend/app/models/schemas.py`: `WorkerEvent`를 새 4값으로 교체, `ExitLineDef` 삭제(`ZoneMapConfig.exit_lines` 필드도 제거), `WorkerEventLogEntry`(track_id/event/zone/at) 신설.
- `backend/app/rules/fire_alert_log.py`, `backend/app/rules/worker_log.py` 신설 — 각각 `data/fire_alerts/{camera_id}.json`, `data/worker_logs/{camera_id}/{track_id}.json`에 append-only로 기록. worker_log는 상태가 실제로 바뀔 때만 기록(매 프레임 기록 아님).
- `backend/app/api/workers.py`에 `GET /{track_id}/timeline` 추가, `backend/app/api/briefing.py`에서 "EVACUATED면 브리핑 카드 생성 거부" 로직 제거(대피 확인 개념 자체가 없어졌으므로) — 대신 응답에 상태값을 그대로 포함하고 안전 미확정임을 명시하는 문구로 교체.
- 프론트엔드: `ZoneMapEditor.tsx`의 출구선 그리기 모드를 관리구역(소화기/전기패널/비상구) 그리기 모드로 교체, `FloorPlan.tsx`/`SummaryHeader.tsx`/`Timeline.tsx`/`App.tsx`/`App.css`의 상태값·색상·문구를 전부 새 4값 기준으로 갱신.
- 백엔드 테스트 43개 전부 통과(`exit_crossing` 관련 테스트는 삭제, `state_engine`/`worker_log`/`fire_alert_log` 테스트 신규 작성), 프론트엔드는 `tsc --noEmit` 통과로 컴파일 정합성 확인.
- 이 변경에 맞춰 `CLAUDE.md`(1, 2, 3, 4-1, 4-3, 4-4, 5, 6번 섹션)와 루트 `README.md`(폴더 구조)도 함께 갱신.

## 19. GitHub 공유 준비 — 화면 가이드를 Artifact에서 저장소 파일로 이전

프론트엔드 개발자와 공유할 목적으로 저장소를 GitHub에 올리기 전, 15번 섹션에서 아티팩트로만 만들어뒀던 "화면 구성 가이드"(대시보드 5개 화면 뼈대)를 점검했다. 아티팩트 내용이 이번 파이프라인 개편 이전(옛 `evacuated`/`exit_unconfirmed`/`reentry` 상태값, 출구선, 소화기 점 마커 기준) 그대로였다 — 그대로 저장소에 넣으면 프론트 개발자에게 이미 폐기된 설계를 전달하게 되는 상황이었다.

그래서 아티팩트를 그대로 옮기지 않고, 18번에서 확정한 새 모델(관측 지속시간 기반 4가지 상태, 관리구역 폴리곤+SSIM 감시)에 맞춰 내용을 다시 정리해 `docs/screen_guide.md`로 저장했다. `CLAUDE.md`의 화면 가이드 참조 문구도 실제 파일 경로를 가리키도록 수정.

같은 논의에서 `frontend/` 폴더 자체를 GitHub에 올릴지도 검토했다. 이미 만들어진 scaffold(타입·화면 구현)가 프론트 개발자에게 참고 구현으로 유용할 수 있다는 점과, 프론트 개발자가 어차피 처음부터 새로 만들 가능성이 크다는 점(그 경우 FastAPI의 자동 생성 API 문서 `/docs`가 계약 역할을 대신할 수 있음, 아무도 관리 안 하는 코드가 백엔드 변경마다 계속 stale해지는 부담 — 이번 파이프라인 개편 때도 이미 한 차례 겪음) 사이에서 저울질하다가, **`frontend/` 폴더를 완전히 삭제**하기로 결정했다. 프론트 개발자는 `docs/screen_guide.md`와 백엔드 `/docs`(Swagger UI)를 기준으로 처음부터 새로 만든다.

이 결정에 맞춰 `docs/screen_guide.md`도 다시 손봤다: "이미 구현됨"/"기존 컴포넌트 재사용" 같은 배지·문구를 전부 제거하고, 화면별 배지를 "API 준비됨"/"API 확장 필요"로 바꿔 프론트 개발자가 지금 바로 백엔드에 붙을 수 있는 화면과 백엔드 작업이 선행돼야 하는 화면을 구분할 수 있게 했다. 루트 `README.md`의 폴더 구조·시작하기·역할 분담 섹션에서도 `frontend/` 관련 내용을 제거했다.

## 20. GitHub 초기 커밋·푸시, 그리고 다중 객체 추적에 "박스 크기 유사도" 보조 기준 추가

`https://github.com/NWBS-5919/LastSight`가 이미 만들어진 빈 저장소라는 걸 확인하고 첫 커밋(109개 파일, `frontend/` 삭제 이후 상태)을 올렸다. `.gitignore`가 `.env`·모델 가중치·대용량 원본 데이터를 잘 걸러내는지, 하드코딩된 API 키가 없는지 커밋 전에 다시 한번 스캔했다.

이어서 BDAI 학습 현황을 SDK로 직접 조회해 실제 상태를 확인했다(사용자가 "구현/수집/학습 중 남은 게 뭐냐" 질문):
- PPE(person/helmet/vest): v1-baseline 완료(val_mAP 0.49), v2-smoke-augmented는 진행 중(84/100 epoch, val_mAP 0.76로 v1보다 개선) — 순조로움.
- Fire/Smoke 커스텀 학습: v1-baseline(val_mAP ~0.01), v2-aihub176(2회 실패+1회 취소), v3-subsampled("succeeded" 상태지만 실제로는 14/100 epoch에서 val_mAP가 0으로 붕괴, train_loss는 계속 감소하는 전형적 과적합/라벨 불일치 패턴) — 세 시도 모두 사실상 실패. 다만 서비스 코드(`fire_detector.py`)는 이 커스텀 모델이 아니라 BDAI ZERO 제로샷 모델을 프롬프트로 호출하는 방식이라 당장 서비스에 지장은 없음.
- `data/raw/`, `data/frames/` 둘 다 완전히 비어있음 — 자체 촬영이 아직 전혀 시작되지 않음.
- `backend/app/inference/detector.py`(person/helmet/vest 추론)는 여전히 스텁, `workers.py` API는 더미 데이터 반환 중 — 개별 규칙 모듈(zone/clearance_zone/state_engine/byte_track 등)은 구현·테스트 완료 상태지만 실제 영상 입력과 엔드투엔드로 연결한 적은 없음.
- BDAI 프로젝트 진행률 조회 결과 PPE/Fire·Smoke 둘 다 "검수 완료 0건" — SDK로 라벨을 직접 반입해서 학습엔 이미 썼지만 플랫폼 검수 워크플로우는 안 거친 상태.

이 대화 중 사람 추적(`byte_track.py`)에 대한 심화 질문이 이어졌다: "화재경보 전에 같은 사람이 화면에 나타났다 사라졌다 하면 같은 ID를 유지할 수 있나?" → 짧은 가림(≤`max_lost_frames`)은 유지되지만, 그보다 오래 사라지거나 위치가 크게 바뀌면 새 ID가 부여된다는 구조적 한계를 확인. 이어서 "두 사람이 가깝게 겹쳐 지나가면 어떻게 판단하나?" → 지금은 순전히 위치(IoU)+속도 예측만으로 그리디 매칭을 하기 때문에, 두 사람이 스치듯 지나가면 ID가 뒤바뀔 수 있는 위험(ID Switch)이 있다는 점을 확인.

이에 대한 보완책으로 사용자가 먼저 "인상착의(얼굴·복장)를 보조 기준으로 추가하면 어떠냐"고 제안했으나, 이건 CLAUDE.md 2번 절대 원칙("얼굴인식 금지", "동일 복장 = 동일인이 아니다")과 정면으로 충돌해 구현하지 않기로 확인받았다. 특히 공사장은 안전모·조끼 색이 현장 규정으로 통일된 경우가 많아, 오히려 서로 다른 두 사람의 인상착의가 비슷해 보이는 환경이라는 점도 근거로 짚었다 — "얼굴이 잘 안 보이니 괜찮지 않냐"는 재질문에도, 원칙 위반 여부와 별개로 기술적으로도 위험한 선택이라고 설명해 재확인을 받았다.

대신 얼굴·복장을 전혀 안 쓰면서도 도움이 되는 방법으로 "박스 크기·비율 유사도"를 보조 기준으로 추가하기로 하고 구현했다. 순위 결정 시 IoU(주 기준, 가중치 0.8)와 박스 크기 유사도(보조 기준, 가중치 0.2, `size_similarity_weight`)를 함께 반영하도록 `_greedy_match`를 수정 — 후보로 남는 조건(IoU 임계값)은 그대로 두고, 여러 후보 중 어느 것을 먼저 확정할지 정하는 순위에만 크기 정보를 더했다. 카메라 거리가 다른 두 사람은 화면상 박스 크기도 달라진다는 점을 이용한 것으로, 신원 정보를 전혀 쓰지 않아 원칙에 위배되지 않는다. IoU만 보면 더 큰 박스가 근소하게 앞서지만 크기가 다르면 오답이 되는 케이스를 재현하는 테스트(`test_size_similarity_breaks_ties_toward_matching_scale`)를 추가했고, 백엔드 테스트 스위트 44개 전부(신규 1개 포함) 통과.

칼만 필터(더 정교한 위치 예측)와 헝가리안 알고리즘(전역 최적 매칭)도 후보로 검토했으나, 전자는 이번 문제엔 효과가 제한적이고 후자는 사람 수가 적은 우리 촬영 계획(2~4명)에서 이득이 작은 데다 `scipy` 의존성을 새로 추가해야 해서 우선순위를 낮췄다 — 나중에 자체 촬영 영상으로 실제 ID Switch 빈도를 확인한 뒤 필요하면 추가하기로 함.

## 21. PPE 탐지 모델(detector.py) 실제 연결 — 스텁 해소

PPE v2(스모크 증강) 학습이 100/100 epoch로 완료됐다(val mAP 0.759, mAP@50 0.945, precision 0.969, recall 0.943 — v1 baseline의 mAP 0.493보다 확실히 개선). 그동안 `NotImplementedError`만 던지던 `backend/app/inference/detector.py`를 이 모델에 연결했다.

**배포가 왜 필요했나**: `fire_detector.py`는 BDAI가 상시 띄워둔 공유 엔드포인트(ZERO 제로샷 모델)를 프롬프트로 호출하는 방식이라 별도 배포가 필요 없었지만, PPE 모델은 우리가 직접 학습시킨 커스텀 체크포인트라 추론을 받으려면 BDAI에 배포(deployment, 실제 GPU 인스턴스를 띄우는 클라우드 리소스)를 먼저 만들어야 했다. 계정에 비용이 발생할 수 있는 작업이라 진행 전에 사용자에게 확인받았고("배포 진행" 선택), `c.deployments.create(model_id=...)`로 배포(`ml.g4dn.xlarge`)를 만들어 준비 완료(`ready`) 상태까지 확인한 뒤 실제 샘플 이미지로 호출 테스트까지 마쳤다.

**구현**:
- `backend/app/core/config.py`에 `ppe_deployment_id` 설정 추가, `.env`/`.env.example`에 `PPE_DEPLOYMENT_ID` 채워둠.
- `backend/app/inference/detector.py`: `fire_detector.py`와 같은 패턴(BGR 프레임 → JPEG → base64 → API 호출)으로 `client.deployments.predict()`를 호출하도록 구현. 응답의 `class_name`(`"person"`/`"helmet"`/`"vest"`)을 `ObjectClass`로 매핑 — 학습 스키마에 같이 등록됐지만 실제 학습 데이터가 없던 속성 클래스(상의 색상 등, support=0)는 매핑 테이블에 없으므로 자동으로 무시된다.
- `backend/tests/test_detector.py` 신규: `get_bdai_client`/`get_settings`를 가짜 객체로 monkeypatch해서 매핑 로직과 배포 ID 미설정 시 `RuntimeError`를 검증(2개). 실제 API를 호출하는 통합 테스트는 아님(호출 비용·네트워크 의존 때문에 유닛 테스트만 작성) — 별도로 실제 배포에 샘플 이미지를 넣어 21건 정상 탐지되는 것도 수동으로 확인함.
- 백엔드 테스트 스위트 46개 전부 통과(신규 2개 포함).

**아직 남은 것**: `workers.py` API가 여전히 더미 데이터를 반환 중이라, 이 detector와 `byte_track.py`/`app.rules` 규칙 모듈들을 실제 영상 입력과 엔드투엔드로 잇는 작업은 그대로 남아있다. 또한 배포는 살아있는 클라우드 리소스라 계속 켜두면 비용이 쌓일 수 있어, 당분간 안 쓸 때는 `c.deployments.stop(deployment_id)`로 멈추는 걸 고려할 것.

## 22. 자체 촬영 영상으로 탐지·추적 실제 테스트 — "뛰는 사람" 탐지 공백 발견 및 보강 데이터 확보

사용자가 준비한 테스트 영상(`Crowd-Activity1~3.MOV`, 320x240)으로 `detector.py`(PPE 모델)+`byte_track.py`(추적)를 실제로 돌려서 눈으로 확인했다. 0.5초 간격 샘플링 결과 트랙 ID가 비정상적으로 많이 생성돼(97샘플에 165개) 원인을 조사했다.

**진단 과정**:
- 프레임을 직접 열어 눈으로 확인하는 과정에서 한 번은 라벨을 잘못 읽어 "ID가 바뀌었다"고 오판했다가, 내부 판단 로그(IoU·크기유사도 점수)를 직접 찍어보고 정정했다 — 실제로는 정상 추적이었음. 저해상도 영상에서 육안 판독 자체가 부정확할 수 있다는 교훈.
- 샘플링 간격을 0.15초로 촘촘하게 바꾸자 최장 추적 지속시간이 18.5초→25.6초로 개선됐으나, 여전히 특정 구간(사람들이 뛰어서 흩어지는 장면, 영상 자체에 "Abnormal Crowd Activity" 자막이 박혀있어 UMN Unusual Crowd Activity 데이터셋으로 확인됨 — 라이선스 불명확이라 학습엔 미사용, 디버깅 확인 용도로만 사용)에서 사람 수가 0명까지 떨어지는 등 불안정했다.
- 프레임을 직접 열어보니 뛰는 사람 무리(6~7명)에 박스가 아예 안 그려져 있었다. `confidence_threshold`를 0.5→0.05까지 낮춰가며 재탐지했지만 대부분 여전히 안 잡혀 — 신뢰도 보정 문제가 아니라 **모델이 "뛰는 자세" 자체를 학습한 적이 없어 생기는 근본적 인식 공백**임을 확인했다(정지·저속 보행 위주로 학습된 PPE 데이터셋의 한계).
- 부수적으로 화면이 완전히 빈 상태(사람 0명)가 잠시 지속된 뒤 새로운 무리가 나타나면, `max_lost_frames`(30) 안에 있던 오래된 트랙이 엉뚱한 새 사람에게 재부착되는 별도 버그도 발견했다(사용자 요청으로 이번엔 수정하지 않고 기록만 남김).

**보강 데이터 탐색과 선택**: "뛰는 자세" 공개 데이터셋을 여러 곳에서 검토했다 — Roboflow POSE(CC BY 4.0)와 AI Hub "사람동작 영상"(달리기 태그 포함)은 열어보니 둘 다 근접·스튜디오 촬영이라 우리 CCTV 도메인과 거리가 멀어 제외. AI Hub "이상행동 CCTV 영상"(폭행/싸움/강도 등 12종, 700시간, 진짜 CCTV)은 유망하지만 뛰는 장면을 직접 골라내는 수작업이 필요해 보류. 최종적으로 **Roboflow `runningperson`(CC BY 4.0, biponjot-kaur)**을 선택 — 미리보기가 위에서 내려다보는 필드 촬영이라 도메인이 맞았다.
- 처음엔 "2,420장이면 한 장면 편향으로 과적합되지 않냐"는 우려가 나와 서브샘플링을 계획했으나, 실제로 `running person` 클래스가 붙은 이미지는 5개 서로 다른 장면(running/running2/running3/running4/running6)에 걸쳐 **196장뿐**이라는 걸 확인하고 전량 사용하기로 결정(전체 학습 데이터의 약 4%로 편향 위험 낮음).
- 사용자가 "합성(모션 블러)이 데이터 수집보다 낫지 않냐"고 물어 — 합성은 기존 이미지(전부 서 있거나 걷는 자세)를 흐리게 만들 뿐 없는 자세를 만들어내지 못하므로, **새 자세 데이터(공백 해소) + 모션 블러 합성(현실감 추가)을 함께 쓰는 게 최선**이라고 정리(모션 블러 합성은 아직 미구현, 다음 과제로 남김).
- COCO 어노테이션에서 `running person` 라벨이 붙은 이미지만 골라 `data/public_datasets/roboflow-runningperson-filtered/`로 재구성(196장, `sitting person`/`sleeping person` 등 무관한 나머지 클래스는 제외) 후, `bdai_pipeline/import_public_dataset.py`로 BDAI `lastsight-ppe` 데이터셋에 업로드하고 `class-map`으로 `running person`→`person` 매핑해 라벨 반입(196장·196라벨 전부 성공, 데이터셋 총량 9,238→9,434장 확인).

**남은 일**: 이 196장을 포함해 다음 학습 버전(v3)을 돌려 실제로 뛰는 사람 탐지가 개선되는지 확인, 트랙 재부착 버그는 여전히 미해결.

## 23. 모션 블러 합성 augmentation 구현 및 두 소스에 적용

22번에서 "새 자세 데이터만으로는 부족하다"고 정리한 대로, `bdai_pipeline/synth_smoke.py`와 같은 패턴으로 `synth_motion_blur.py`를 새로 작성했다. 카메라 고정·사람만 이동한다고 가정하고, 사람 바운딩박스 영역에만 방향성 블러 커널(`cv2.filter2D`)을 국소적으로 적용해 배경은 선명하게 유지한다(실제 셔터 노출 중 피사체만 번지는 현상과 동일). 박스 경계는 가우시안으로 페더링해 딱 잘리지 않게 블렌딩. 사람 위치 자체는 안 바뀌므로 기존 라벨을 그대로 재사용(재라벨링 불필요) — `generate_smoke_augmented.py`와 동일한 구조의 `generate_motion_blur_augmented.py`로 감쌌다.

사용자가 "196장뿐 아니라 실제 CCTV 각도인 기존 데이터에도 적용하는 게 낫지 않냐"고 제안해, 두 소스에 각각 적용하기로 했다:
- `roboflow-runningperson-filtered`(196장, 새로 받은 뛰는 자세) — "낯선 자세" 공백을 메우면서 동시에 흐림까지 더해 실전에 가장 가까운 조합을 만듦
- `sfchd`의 기존 학습 샘플(4,000장, 실제 화학공장 CCTV) — 이미 도메인이 맞는 데이터에 블러 내성만 추가

**품질 이슈 발견 및 수정**: 처음 만든 SFCHD 블러 4,000장을 샘플 확인해보니 일부(특히 "heavy" 강도)가 사람 형체를 알아볼 수 없을 정도로 뭉개져 있었다. 원인은 CCTV 특성상 사람 박스 자체가 작은데(중앙값 57px) 블러 길이를 박스 대비 40~60%까지 준 게 과했던 것 — 강도 구간을 낮추고(light/medium/heavy 각각 8~15%/15~25%/25~35%) heavy 비중도 30%→15%로 줄여 재생성, 16장 샘플로 재확인 후 대부분 "블러는 있지만 사람이라고 알아볼 수 있는" 수준으로 개선된 걸 확인하고 진행했다.

**업로드 결과**: `roboflow-runningperson-blur-aug`(196장·196라벨, `running person`→`person`)와 `sfchd-blur-aug`(4,000장·14,953라벨, `person`/`helmet`/`safety_clothes`→`vest`, `self_clothes`/`head`/`blur_head`/`blur_clothes`는 이전 SFCHD 반입 때와 동일하게 매핑 제외)를 모두 `lastsight-ppe` 데이터셋에 반입. 최종 데이터셋 총량 9,434 → 13,630장(196+4,000 정확히 일치) 확인.

**남은 일**: 이번에 추가한 4,392장(뛰는 자세 196 + 뛰는 자세 블러 196 + SFCHD 블러 4,000)을 포함해 학습 버전(v3) 실행 및 실제 뛰는 사람 탐지 개선 여부 확인.

## 24. "라벨 반입 성공"이 사실은 전부 실패였던 버그 발견·수정, v3 학습 시작

23번 작업 후 "이제 학습만 돌리면 되나" 물어보길래 스냅샷(`v3-running-blur-aug`)을 만들었는데, `frozen_asset_count`가 v2와 똑같은 8,853으로 나와서 이상함을 느꼈다. 사용자가 "SFCHD 샘플 데이터가 어디 있냐"고 묻는 사이 조사해보니 심각한 문제를 발견했다.

**버그의 정체**: `import_public_dataset.py annotate`가 매번 출력한 `<JobHandle ... status=completed 196/196>`을 나는 "196개 성공"으로 읽었는데, 실제로는 **"196개 처리 시도" 중 성공/실패 여부는 별도 필드(`succeeded`/`failed`)에 있었다.** 단일 라벨로 직접 재현해보니 `succeeded=0, failed=1`, 에러 메시지: `"filename '...' not found in this project's dataset"`. 즉 22~23번에서 시도한 라벨 반입(196+196+14,953 = 15,345개)이 **전부 실패**했었다 — "완료"로 표시된 로그를 그대로 믿은 게 원인.

**근본 원인**: BDAI에서 데이터셋에 이미지를 업로드해도 프로젝트 스코프에는 자동으로 안 들어간다. `create_project_schema.py`가 프로젝트를 `scope={"all": True}`로 만들길래 "이후 업로드되는 것도 전부 자동 포함"이라고 잘못 추측했는데, 실제로는 **프로젝트 생성 시점의 스냅샷일 뿐**이라 그 이후 업로드분은 `project_assets.bulk_add`로 별도 등록해야 라벨 반입이 가능했다. 지금까지(스모크 증강 등) 문제없이 됐던 이유는, 그때 업로드가 전부 프로젝트 생성 전이었거나 이미 등록된 상태였기 때문으로 보인다.

**수정**:
- `bulk_add(project_id, filter={})`로 프로젝트 미등록 자산을 스코프에 동기화(이미 등록된 건 idempotent하게 skip) → 13,630개 중 4,391개가 새로 등록됨.
- 3개 소스(뛰는 자세 원본/블러/SFCHD 블러) 라벨 반입을 처음부터 재실행 → 이번엔 성공. 프로젝트 전체 어노테이션 수 33,441 → 48,786개(정확히 +15,345) 확인, 실패했던 샘플 자산도 라벨 1개 정상 확인.
- **재발 방지**: `import_public_dataset.py`의 `cmd_annotate`에 `project_assets.bulk_add` 호출을 항상 먼저 실행하도록 추가. 또한 배치 로그가 `succeeded`/`failed`를 명시적으로 출력하고, 실패 시 에러 샘플까지 찍도록 수정 — "completed"라는 문구만 보고 성공을 오판하는 일이 다시는 없도록 함.

**중간에 겪은 부수적인 일들**:
- 고장난 첫 `v3-running-blur-aug` 스냅샷을 지우고 다시 만드는 과정에서 API가 연속 호출(자산 동기화 + 대량 라벨 반입 + 삭제 + 생성)로 인해 잠깐 403(WAF/속도제한)에 걸렸다. 사용자가 잠들기 직전이라 "30분 뒤 재시도 + 스냅샷 생성 + 학습까지 질문 없이 진행"을 명시적으로 지시받아, 백그라운드 스크립트(`wait_and_train.py`)로 자동화했다.
- 이 스크립트의 1차 실행이 다시 실패했는데, 원인은 API 차단이 아니라 **스크립트 자체의 버그**였다: `load_dotenv()`를 상대경로로 호출해서 백그라운드 실행 환경(CWD 불확실)에서 `.env`를 못 찾아 `KeyError`가 났다 — 30분을 그냥 날린 셈. `.env` 경로를 절대경로로 명시해서 해결.
- 재시도 시 스냅샷 이름 충돌(`NAME_TAKEN`) — 앞서 지운 스냅샷의 이름이 완전히 반납되지 않는 것으로 보여 `v3-running-blur-aug-2`로 이름을 바꿔 진행.
- 이 과정에서 승인이 필요한 명령(`pkill`, 특정 스크립트)이 몇 번 걸렸는데, 사용자가 잠들어 응답이 불가능한 상황이라 **위험해 보이는 명령(프로세스 강제 종료 등)은 아예 쓰지 않고 안전한 명령만으로 우회**하는 방식으로 대응했다. 전역 권한 설정을 바꾸는 것(`claude config set --global autoApprove true`)은 이번 세션 범위를 넘어서는 위험 부담이라 실행하지 않았다.

**결과**: 스냅샷 `v3-running-blur-aug-2` 생성 완료(에셋 13,245개, 클래스 7개), 학습 실행 `ppe-v3-running-blur-aug-2`(rf-detr-nano, 100 epoch) 시작함(status=queued).

**남은 일**: 학습 완료 후 지표 확인, 특히 뛰는 사람 탐지가 실제로 개선됐는지 자체 촬영 영상으로 재검증.

## 25. 학습 중단 — 블러 합성 코드의 설계 결함 발견

학습이 `running`으로 넘어간 직후, 사용자가 "헬멧·조끼를 머리/옷 색깔만 보고 대충 판단하게 되지 않냐"고 물어봐서 `generate_motion_blur_augmented.py`를 다시 보니 실제로 문제가 있었다.

**문제**: 블러 함수(`add_synthetic_motion_blur`)에 이미지 안의 **모든 바운딩박스(person/helmet/vest)를 각각 독립적으로 무작위 방향·세기로 블러 처리**하도록 넘기고 있었다. 즉 한 사람 안에서 몸통·헬멧·조끼가 서로 다른 방향·세기로 따로 흐려질 수 있었다 — 실제로는 한 사람이 움직이면 신체 부위 전체가 같은 방향·세기로 함께 흐려져야 하는데 물리적으로 말이 안 되는 상태였다. 이게 헬멧/조끼를 구분하는 미세한 단서(테두리 모양, 반사띠)를 부위마다 제각각 뭉개서, 모델이 "정확한 헬멧 모양"이 아니라 "머리 근처 색 뭉치 = 헬멧" 같은 대충 뭉뚱그린 기준을 배울 위험이 있다고 판단했다.

**영향 평가**: 전체 13,630장 중 블러 데이터는 4,196장(31%)뿐이라 치명적이진 않을 것으로 보이지만(나머지 69%는 또렷한 원본), 그래도 고치는 게 맞다고 판단해 **학습을 즉시 중단**했다(`ppe-v3-running-blur-aug-2`, running 상태에서 취소 — 첫 epoch 완료 전이라 손실 거의 없음).

**다음에 할 일**: `generate_motion_blur_augmented.py`를 person 박스 기준으로 블러를 한 번만 계산하고, 그 안에 포함된 helmet/vest는 같은 블러를 그대로 물려받도록 수정한 뒤 SFCHD 블러 4,000장을 다시 생성 → 재반입 → 재학습.

## 26. Fire/Smoke 재학습 — 인프라 장애 반복과 데이터량 문제

14번에서 13,354장으로 확장한 뒤 재학습(`fire-smoke-v2-aihub176-retry2`)을 돌렸는데, epoch 1에서 2시간 넘게 진전이 없어 이상함을 느꼈다. `client.training.list_runs()`로 같은 버전의 이전 시도 이력을 확인해보니, **직전 두 번의 시도가 전부 같은 원인(`reconciler: batch job FAILED — Host EC2 instance terminated`)으로 시작 1시간 15~20분 만에 죽어있었다** — 사용자 잘못이 아니라 인프라 쪽 문제였다.

**데이터량 가설 검증**: 195장짜리 최초 baseline은 20 epoch를 4분 6초(epoch당 ~12초) 만에 문제없이 완주했던 기록이 있었다. 195장→13,354장(68배)으로 epoch당 처리시간이 300배 넘게 느려진 건 정상적인 스케일링이 아니라 리소스 부족으로 호스트가 죽는 것으로 해석하는 게 타당하다고 판단, 세 번째 시도(`retry2`)를 취소했다.

**축소 방법**: AI Hub 176 파일명(`<클립ID>MF<프레임번호>.jpg`)을 보니 13,159장이 실제로는 **영상 8개에서 뽑은 연속 프레임**이었다(클립당 1,700~2,000장). 즉 물량은 많아도 실질적 장면 다양성은 8가지뿐이라는 뜻. 재업로드 없이 `versions.create(selection={"asset_ids": [...]})`로 클립별 8장 간격 stride 샘플링한 부분집합만 새 버전으로 얼렸다(`bdai_pipeline/subsample_version.py` 작성) → baseline 195장 + 서브샘플 1,649장 = **1,844장짜리 버전(`fire-smoke-v3-subsampled`)** 생성.

## 27. 학습 곡선 붕괴 발견과 "최종 모델 = 마지막 epoch" 함정

1,844장 버전으로 학습(`fire-smoke-v3-subsampled-run1`, rf-detr-seg-nano)을 돌렸더니 크래시 없이 14 epoch에서 `succeeded`로 끝났다. 그런데 epoch별 `val_map` 추이를 보니 **epoch 4에서 정점(mAP@50=0.248)을 찍은 뒤 5 epoch 연속 하락, epoch 13~14에는 완전히 0으로 붕괴**했다. `train_loss`는 그동안 계속 순조롭게 내려가고 있어서(194→30) 전형적인 과적합 패턴으로 판단.

**더 심각한 문제 발견**: `client.models.list(project_id=...)`로 실제 등록된 최종 모델을 조회해보니, 그 붕괴된 마지막 epoch(14)의 가중치가 그대로 최종 모델로 저장돼 있었다(`map=0.0, precision=0.0075`, confusion matrix상 거의 모든 이미지를 background로 오분류). **BDAI의 `early_stopping`/`patience`는 "몇 epoch 더 지켜보다 멈춘다"는 뜻일 뿐, 멈춘 뒤 최고 성능 시점(best checkpoint)으로 되돌리는 기능이 아니라는 걸 확인했다** — 이 상태로는 아무리 데이터를 개선해도 학습 곡선이 어딘가서 정점을 찍고 내려가면 항상 나쁜 시점이 저장된다. (baseline 모델도 돌이켜보면 같은 문제를 겪었을 가능성이 있음.) 이 문제는 별도로 epoch 수를 정점 근처로 고정해서 해결해야 한다는 결론만 내리고, 우선순위상 데이터/태스크 방향 결정을 먼저 하기로 함.

## 28. Segmentation → Detection 전환 결정

**계기**: 학습이 왜 이렇게 안 되는지 사용자가 물어봐서 원인을 파고들다, AI Hub 176 라벨의 대부분이 진짜 폴리곤이 아니라 bbox 폴백으로 만들어진 걸 발견했다(원본 라벨에 `box` 필드가 있으면 그걸 우선 쓰고, 없을 때만 `polygon`을 쓰는 `_parse_aihub176` 로직 때문). segmentation 태스크로 학습 중인데 실제 정답 라벨 상당수가 "정밀 마스크"가 아니라 "대충 그린 사각형"이었다는 뜻.

**실수와 정정**: 처음엔 라벨 폴더 전체를 `glob`으로 스캔해서 "bbox가 95%"라고 잘못 보고했는데, 그 폴더 안에 우리가 실제로 보유하지 않은 다른 파트의 라벨 파일 53만 개가 섞여 있었던 걸 놓친 것이었다(14번에서 이미 한 번 발견했던 이슈인데 다시 걸림). 우리가 실제로 보유한 13,159장에 정확히 매칭해서 다시 세어보니 **실제로는 polygon이 63%, bbox가 37%**로 정반대였다 — class 01(흰 연기)만 예외적으로 거의 bbox(99.6%)였고 나머지(회색/검정 연기, 화염)는 80% 이상이 진짜 폴리곤이었다.

**최종 판단 근거**:
1. MVP 요구사항(CLAUDE.md 6번)은 "화재/연기 자동 탐지 + 경보 자동 트리거"까지만 필요하고, "화재 확산 시뮬레이션"은 명시적 제외 항목 — 정밀 마스크가 주는 추가 정보(면적·경계)를 소비하는 로직이 시스템에 없음.
2. fire 폴리곤 공개 데이터셋을 서베이 논문·개별 검색·AI Hub 자체 검색 등 여러 경로로 찾아봤지만(D-Fire, MultiNatSmoke, FLAME1/2, BoWFire, AI Hub 71472 등) 전부 bbox만 있거나, 라이선스가 불명확/혼재하거나, 도메인(산불·드론 항공촬영)이 안 맞아서 탈락. 유일하게 확실한 polygon 후보는 IJmond Industrial Smoke Segmentation Dataset(CC BY 4.0, 900장/폴리곤 1,209개)인데 smoke만 있고 fire가 없음. → 이 비대칭 자체가 "근거리 화재는 업계에서도 bbox로 충분하다고 본다"는 신호로 해석.
3. `annotations.list(type="polygon")`로 뽑은 폴리곤 점들의 min/max 좌표만 계산하면 bbox를 **손실 없이** 파생시킬 수 있어서, detection 전환이 기존 polygon 라벨을 버리는 게 아니라는 걸 확인. 반대(bbox→polygon)는 원래 없던 모양 정보를 새로 만들어야 해서 사실상 재라벨링과 같은 비용이라 불가능.

**결론**: detection(`rf-detr-nano`)으로 전환하되, polygon 라벨은 그대로 두고 거기서 bbox를 계산해 추가하는 방식으로 데이터 손실 없이 진행하기로 확정.

## 29. Polygon → bbox 백필 및 Detection 재학습 착수

`bdai_pipeline/backfill_bbox_from_polygon.py` 작성 — 프로젝트의 모든 polygon 어노테이션을 조회해 각 폴리곤 점들의 외접 사각형을 계산하고, 같은 이미지·같은 클래스로 bbox 어노테이션을 추가로 `bulk_create`(1,000개씩 16배치)했다. **polygon은 삭제하지 않고 옆에 추가만 하는 방식**이라 나중에 다시 segmentation이 필요해지면 되돌릴 수 있음. 결과: polygon 15,093개 전부에서 bbox 파생 성공.

같은 1,844장 부분집합으로 새 스냅샷(`fire-smoke-v4-detection-bbox`)을 다시 얼려서 `training.stats(task="detection")`로 확인한 결과:

| | 백필 전 | 백필 후 |
|---|---|---|
| 학습 가능 이미지 | 1,590/1,844 | **1,844/1,844 (전체)** |
| 인스턴스 수 | 1,088개 | **3,365개** (fire 1,528 · smoke 1,837) |

이 버전으로 detection 학습(`fire-smoke-v4-detection-run1`, rf-detr-nano)을 시작함(status=queued). 27번에서 발견한 "최종 모델=마지막 epoch" 문제는 아직 해결 전이라, 이번 학습의 val_map 추이를 지켜보고 필요하면 정점 근처 epoch 수로 고정한 재시도를 이어갈 예정.

## 30. (부수 작업) AI Hub 71407 — 사람 감지 테스트 영상 생성

Fire/Smoke 작업과 별개로, 사람 감지 파이프라인 테스트용 영상이 필요하다는 요청으로 AI Hub 71407("건설 현장 위험 상태 판단 데이터", 226,000장/276GB)에서 소규모 샘플(48MB, 낙하사고 시나리오 N-10)만 받아 진행했다. 이 데이터셋은 14번에서 fire/smoke 라벨용으로는 이미 한 번 탈락시켰던 것인데(화재 위험 장비/자재 클래스뿐), 사람 감지 목적으로 다시 보니 `WO-01`(작업자)/`WO-02`(신호수) 같은 이동객체 클래스가 있어 이번 용도엔 재사용 가능했다.

**프레임→영상 재구성 시행착오**: 처음엔 프레임 간격을 임의로 0.133초(~7.5fps)로 가정해 영상을 만들었는데, 재생해보니 사람이 순간이동하듯 튀는 문제가 있었다. 이미지 EXIF `DateTime`을 보고 "10초 이상 간격"이라 오판했다가, 실제로는 **각 프레임의 라벨 JSON 안에 `Extraction_Time`(원본 영상 기준 정확한 타임스탬프)이 있는 걸 발견** — 그걸 기준으로 다시 계산하니 실제 간격은 프레임당 약 1.28~1.5초였다(EXIF의 `DateTime`은 AI Hub 서버의 파일 생성 시각이었을 뿐, 촬영 시각이 아니었음). `Extraction_Time` 기준으로 정확한 타이밍의 영상을 재생성해 문제를 해결했다. 다만 이 데이터셋 자체가 "초당 프레임"이 아니라 1.3초 간격 정지샷 모음이라, 아무리 타이밍을 맞춰도 완전히 매끄러운 영상은 안 된다는 구조적 한계는 남아있음(사용자도 감안하고 진행하기로 함).

**"여러 사람" 조건**: 라벨의 `class_ID`가 `WO-`로 시작하는 것만 세어 시나리오별 동시 최대 인원을 비교했는데, 낙하(물체)·안전보조장비·전도·추락(정상) 시나리오는 사람이 아예 태깅돼 있지 않았다(그 시나리오의 라벨링 대상이 사람이 아니라 다른 객체였기 때문으로 추정) — 추락(비정상, 최대 3명)·협착(정상, 최대 2명) 두 시나리오만 확인되어 이 두 개로 영상을 만들었다.

**결과물**: `data/raw/aihub71407_person_test/`에 정속 버전 2개(N-10 248초, Y-21 94초)와 4배속 버전 2개(각 62초/24초) 저장.

## 31. Detection 재학습 결과 — 성공

29번에서 시작한 `fire-smoke-v4-detection-run1`(rf-detr-nano, 1,844장, bbox 3,365개)이 39 epoch에서 `succeeded`로 완료됐다.

**segmentation 최고점(epoch 4, 저장은 안 됐던 값) 대비 detection 최종 등록 모델 비교**:

| 지표 | segmentation 최고점 | detection 최종 모델 |
|---|---|---|
| mAP | 0.093 | **0.587** |
| mAP@50 | 0.248 | **0.891** |
| precision | 0.576 | **0.907** |
| recall | 0.405 | **0.887** |

클래스별로도 fire(precision/recall 0.946/0.946)는 거의 완벽했고, smoke(0.874/0.839)는 여전히 fire보다 어렵지만 충분히 쓸만한 수준까지 올라왔다.

**27번에서 발견한 "최종 모델=마지막 epoch" 문제도 사실상 해결됨**: val_map이 epoch 29에서 정점(0.5522)을 찍은 뒤 39 epoch에서 멈췄는데, 마지막 값(0.5367)이 정점 대비 3%밖에 안 떨어져 있었다 — segmentation 때(정점 대비 100% 붕괴)와 달리 detection은 정점 이후에도 완만하게 유지되는 안정적인 곡선을 보였다. 28번에서 예상했던 "detection이 이 데이터 규모에 더 안정적으로 수렴할 것"이라는 판단이 실제로 들어맞았고, 별도의 epoch 고정 재시도 없이 이번 결과를 최종 모델로 채택하기로 함.

**교훈**: segmentation에서 겪었던 두 가지 문제(과적합 붕괴, 라벨-태스크 불일치)가 detection 전환 하나로 동시에 풀렸다. 처음부터 "이 작업에 실제로 필요한 정보가 무엇인가"(정밀 마스크 vs 위치+존재유무)를 먼저 따졌으면 더 빨리 도달했을 결론이었다.

## 32. AI Hub 163("공사현장 안전장비 인식 데이터") 검토 — 기각

2.03M장 규모의 실제 현장명 기반 공개 데이터셋이라 helmet/vest 색상·현장 다양성 문제를 한 번에 해결할 후보로 검토했다. 승인·다운로드까지는 됐으나, 서로 다른 두 카테고리(`7.스튜디오`, `2.공연장_부산 오페라 하우스`)에서 표본 5장을 직접 열어본 결과 전부 어안(fisheye) 렌즈 왜곡이 뚜렷하고 사람 눈높이 이하에서 촬영된 사진이었다 — 얼굴이 프라이버시 마스킹된 점, 파일명이 연속 프레임 번호인 점까지 종합하면 몸에 붙이거나 손에 든 액션캠으로 사람을 따라다니며 찍은 영상에서 뽑은 데이터였다. 카테고리 하나만의 특이 케이스가 아니라 데이터셋 자체의 촬영 방식이 구조적으로 웨어러블/핸드헬드였다는 뜻이라, 고정 CCTV가 위에서 내려다보는 우리 도메인과 근본적으로 다르다고 판단해 기각했다. (사용자가 먼저 "웹캠으로 찍은 것도 섞여있을 수 있다"고 정확히 짚어준 우려였다.)

## 33. helmet/vest 색상 편향 실측 및 색상 합성(hue jitter) augmentation

Task #3(색상 합성) 착수 전, "데이터셋에 색깔별로 이미 다양하게 구성돼 있지 않냐"는 질문에 추측 대신 실측으로 답했다. `construction-site-safety`/`sfchd` 각 소스의 helmet·vest 박스를 크롭해 HSV 중앙값 기반으로 색상을 분류(색상환 버킷 10종)한 결과:

- SFCHD(helmet/vest 신호의 ~93~95% 차지): helmet은 빨강 32.7%가 최다, vest는 **파랑이 66.8%**로 압도적 — 안전조끼 특유의 노랑/주황/초록 반사색이 아니라 파란 작업복 한 색이 2/3을 차지
- CSS(신호량은 helmet 542개/vest 414개로 소수): helmet 흰/파/노/빨/주황 고르게 분포, vest는 초록·노랑 위주로 실제 고시인성 색상에 가까움

즉 데이터셋 전체로는 다양해 보여도, 양이 압도적인 SFCHD 자체가 색상 편향돼 있고 색이 고른 CSS는 양이 너무 적어 상쇄가 안 됨 — "vest=파랑"이라는 얕은 상관관계를 학습할 위험이 실측으로 확인됐다.

대응으로 `bdai_pipeline/synth_color_jitter.py`(helmet/vest 박스마다 독립적으로 hue 0~180 무작위 회전 + 채도/명도 소폭 지터, 가장자리 페더링)와 `generate_color_jitter_augmented.py`(helmet/vest 라벨이 있는 이미지만 골라 증강)를 작성. SFCHD에서 helmet/vest 라벨이 있는 11,747장 중 2,000장을 샘플링해 증강본 생성 → 시각 QA(사람 크롭 확대 비교) 통과 → BDAI 업로드·반입(2,000장, 라벨 7,696개).

반입 중 마지막 배치(51개)가 익숙한 "filename not found" 오류로 실패 — `project_assets.bulk_add`로 프로젝트 스코프에 동기화했는데도 방금 업로드한 자산 일부가 아직 인덱싱 전이라 생기는 전파 지연이었다(24번에서 겪은 문제와 동일 계열이지만, 이번엔 스코프 등록 자체는 됐는데 인덱싱만 늦은 케이스). 전량 재반입하면 이미 성공한 라벨이 중복되므로, 실패한 파일만 `annotations.list(asset_id=...)`로 라벨 0개인지 확인 후 그 13개 파일(51라벨)만 골라 재동기화 후 재반입 → 전량 성공.

## 35. 우선순위 전환 — 데이터 품질 개선 대신 데모 화면부터

사용자가 "데모에서 임팩트가 있었으면 좋겠는데"라고 문제 제기. 점검해보니 `frontend/` 디렉토리가 아예 없고(`docs/screen_guide.md`에 기록된 대로 이전 참고용 React 스캐폴드는 의도적으로 삭제된 상태) 웹소켓도 빈 껍데기, `workers.py`/`briefing.py` API는 더미 데이터만 반환하는 상태였다 — 즉 지금 보여줄 수 있는 화면이 하나도 없었다. Task #4~7(no_helmet/no_vest 클래스, IoU 착용판정, 재학습)은 데이터·모델 품질을 더 다듬는 작업이라 이미 어느 정도 궤도에 오른 반면, 데모 화면은 0에서 시작해야 해서 임팩트 관점에서는 이쪽이 훨씬 급한 병목이라고 판단. 사용자와 상의해 우선순위를 프론트엔드+실시간 연동(정상→연기감지→경보→상태전환→구조카드 시나리오 데모)으로 전환하고, Task #3~7은 시간이 남으면 재개하기로 함.

## 36. no_helmet/no_vest/head 클래스 추가 및 라벨 반입 (Task #4~5)

BDAI `lastsight-ppe` 프로젝트에 `no_helmet`/`no_vest`/`head` 클래스를 추가(`client.classes.create`)하고, CLAUDE.md 4-1에도 반영. 이미 갖고 있던 데이터에서 지금까지 반입하지 않았던 라벨만 골라 추가 반입(신규 이미지·신규 라벨링 없음):

- CSS(train/valid/test): `NO-Hardhat→no_helmet`, `NO-Safety Vest→no_vest` — 984개 성공
- SFCHD 원본 + 블러/색상/연기 합성본 4종: `head→head`, `self_clothes→no_vest` — 원본은 BDAI에 실제로 업로드된 자산(4,000장)만 매칭되고 로컬 전체(12,372장) 중 나머지는 애초에 업로드 대상이 아니었으므로 "not found" 실패가 다수 발생했는데(572성공/1406실패), 이는 버그가 아니라 애초에 그 이미지들이 프로젝트에 없었기 때문 — 합성본 3종(blur/color/smoke-aug)은 전부 성공(572+247+572)

최종 클래스별 라벨 총량: `person` 21,567 · `helmet` 17,222 · `vest` 17,693 · `no_helmet` 402 · `no_vest` 1,332 · `head` 1,213.

**부수적으로 발견한 사실**: 데이터셋 소스별 구성을 다시 정확히 조사하는 과정에서, 처음 만든 분류 스크립트가 파일명의 `_smoke` 패턴을 체크하지 않아 연기 합성 이미지(SFCHD 4,000장 + CSS 521장)를 전부 "원본"으로 잘못 집계하는 버그가 있었다(사용자가 "연기 합성한 것도 있었잖아"라고 지적해서 발견). 수정 후 최종 소스 구성: SFCHD 원본 4,000 / SFCHD 블러합성 4,000 / SFCHD 연기합성 4,000 / SFCHD 색상합성 2,000 / CSS 원본 717 / CSS 연기합성 521 / Roboflow running-person 원본 196 / 블러합성 196 (합계 15,630, 정확히 일치 확인).

## 37. Fire/Smoke 커스텀 모델 배포 철회 — ZERO로 회귀

34번에서 배포·연동까지 마친 `fire-smoke-v4-detection`을 실제로 써보니, 사용자가 **ZERO(제로샷 파운데이션 모델)가 우리 커스텀 모델보다 훨씬 낫다**고 체감했다.

**원인**: 31번에서 본 F1 0.897·mAP@50 0.891은 전부 우리 학습 데이터 자체(8개 영상 클립에서 나온 검증 스플릿)로 측정한 지표다. 즉 "그 8개 장면 안에서는 잘한다"는 뜻이지 "처음 보는 장면에서도 잘한다"는 뜻이 아니었다. 반면 ZERO는 대규모 파운데이션 모델이라 우리보다 훨씬 넓은 범위의 실제 장면에 대해 일반화가 되어 있어서, 낯선 화면에서는 우리 모델보다 안정적으로 작동한다. 검증 지표가 좋다고 실제 사용성이 보장되는 게 아니라는 걸 재확인한 사례 — 26~29번에서부터 계속 걱정했던 "장면 다양성 부족(8개 클립)" 문제가 결국 여기서 실사용으로 드러난 셈이다.

**조치**: `.env`의 `FIRE_SMOKE_DEPLOYMENT_ID`를 주석 처리해 기본값(빈 문자열)으로 되돌림 → `fire_detector.py`가 자동으로 ZERO 폴백 경로를 타도록 함(34번에서 이미 이렇게 설계해뒀던 덕분에 코드 수정은 불필요). 배포된 커스텀 모델 자체는 BDAI에 그대로 남아있어 값만 다시 채우면 언제든 재활성화 가능. `.env.example`에도 이 변수와 사유를 추가해 다른 팀원이 새로 세팅할 때도 기본이 ZERO임을 알 수 있게 함. `fire_detector.py` 상단 docstring도 현재 상태(ZERO 사용 중, 커스텀 모델은 배포만 돼 있고 비활성)에 맞게 갱신.

**보고서용 정리**: 커스텀 모델 학습·실험 자체는 "모델 실험 로그" 섹션에 그대로 유효한 내용이다(segmentation 붕괴 원인 분석, detection 전환 근거, 최종 검증 지표까지). 다만 최종 서비스 배포 판단은 "검증 지표가 좋아도 학습 데이터 다양성이 부족하면 실사용에서 파운데이션 모델보다 못할 수 있다"는 걸 직접 확인하고 데이터 기반으로 ZERO를 택한 것 — 이 판단 과정 자체를 발표·질의응답 소재로 쓸 수 있다.

### 38.1 해커톤 1등 전략 점검

### 38.2 차별화 기능 3종 설계·구현

기존 컨셉(화재 탐지+PPE 체크+추적)만으로는 "참신하다"는 인상을 주기 어렵다는 우려에 따라, 새 학습·새 데이터 없이 기존 로그·모델 인프라를 재활용하는 3가지 기능을 제안하고 구현했다.

**사전 정정**: "결정적 순간에 VLM 호출" 아이디어를 논의하다, `client.foundation.list()`로 실제 테넌트를 조회해보니 등록된 파운데이션 모델이 `zero` 하나뿐이고 별도 VLM 자유 텍스트 캡셔닝 엔드포인트는 없다는 걸 확인했다. ZERO는 개방형 어휘 **탐지** 모델(문구를 주면 그 문구와 비슷한 걸 박스로 찾아줌)이지 상황을 설명해주는 캡셔닝 모델이 아니다. 그래서 "자유 문장 생성"이 아니라 "우려 문구 여러 개를 동시에 프롬프트로 던지고, 걸린 것들만 모아 문장을 조립"하는 방식으로 설계를 조정했다.

1. **사고 리플레이 타임라인** (`app/api/incidents.py` 신규)
   - `fire_alert_log`/`worker_log`/신규 `clearance_zone_log`(관리구역도 상태 변화를 append-only로 기록하도록 이번에 추가, `worker_log.py`와 동일 패턴)를 하나로 병합해 시간순 정렬한 `GET /incidents/{camera_id}/timeline`.
   - 특정 시각 기준으로 "그때 무엇이 사실이었는지" 재구성하는 `GET /incidents/{camera_id}/state-at?at=...` — 각 작업자/관리구역마다 그 시각 이전 가장 최근 로그를 찾아 스냅샷을 만든다. 사고 이후 감사·훈련 자료로 재생(replay)할 수 있는 기반이 된다.

2. **결정적 순간 2차 확인** (`app/inference/situation_probe.py` 신규)
   - 상시 감지는 그대로 두고, `PROLONGED_PRESENCE` 전환(작업자) 또는 `ABNORMAL` 전환(관리구역) 시점에만 ZERO에 우려 문구 세트(작업자: "쓰러진 사람" 등 3종, 관리구역: 종류별로 다른 3종)를 동시에 물어 걸린 것들로 짧은 문장을 만들어 `situation_note`에 채운다.
   - `scenario_runner.py`(작업자)는 `asyncio.create_task`로 비동기 백그라운드 호출 — 데모 재생 루프를 ZERO 네트워크 왕복 시간만큼 멈추지 않기 위함. `zone_maps.py`(관리구역)는 단발성 API 요청이라 동기 호출로 처리.
   - 호출 실패는 조용히 `None`으로 처리하고 파이프라인을 막지 않는다 — 화재경보 자동 트리거(필수 안전 경로)와 달리 이건 "있으면 좋은" 보조 정보이기 때문.

3. **확인 우선순위 스코어(트리아지)** (`app/rules/triage.py` 신규, `GET /workers/priority/ranked`)
   - `PROLONGED_PRESENCE`/`TRACKING_LOST` 작업자만 대상으로, 지속시간(worker_log에서 현재 상태로 바뀐 시각을 찾아 계산, 30분 상한)·화재 발생 구역과의 거리(구역 폴리곤 중심점 간 유클리드 거리)·탐지 신뢰도 3가지를 explainable하게(구성요소를 그대로 노출) 합산해 0~100점 순위를 매긴다.
   - "위험도 확정"이 아니라 "확인 인력을 어디부터 투입할지"에 대한 참고 정보라는 점을 코드 주석에도 명시 — CLAUDE.md 절대 원칙(재실 인원·위험 확정 금지)과 충돌하지 않도록 설계.

**검증**: 신규 모듈 4개(`situation_probe`/`triage`/`clearance_zone_log`/`incidents`) 전부에 단위·통합 테스트 작성(가짜 ZERO 클라이언트로 응답 모킹, 시간 계산·정렬·병합 검증), 기존 `test_clearance_zone_api.py`에도 ABNORMAL 전환 시 2차 확인이 실제로 호출되는지 검증하는 테스트 추가. 백엔드 전체 테스트 스위트 63개 → 78개(신규 15개) 전부 통과 확인, 앱 임포트·라우트 등록·실제 엔드포인트 호출까지 스모크 테스트로 재확인.

## 40. PPE v4 학습 중단 + ZERO/YOLO 비교로 데이터 다양성 부족 확인 → 데이터셋 전면 재구성

**PPE v4 학습 착수 → 중단**: no_helmet/no_vest/head 라벨을 추가한 스냅샷(`v4-no-helmet-no-vest-head`, 15,247장)으로 학습을 시작했으나(`ppe-v4-no-helmet-no-vest-head`), 사용자가 데모 영상으로 배포된 v2 모델의 실제 탐지 품질을 직접 확인하고 싶어해서 잠시 보류.

**독립 확인 툴 제작**: 대시보드와 무관하게 person/helmet/vest 탐지 품질만 빠르게 볼 수 있는 툴을 두 단계로 만들었다 — 처음엔 로컬 영상에 bbox를 그려 저장하는 CLI(`backend/scripts/annotate_video.py`), 이어서 사용자가 브라우저에서 아무 영상이나 업로드해 바로 재생해볼 수 있는 독립 페이지(`backend/app/pipeline/video_annotate.py` + `POST /annotate/upload` + `GET /tools/annotate` 정적 HTML). 이 툴로 실측한 결과, 흰색 안전모가 밝은 콘크리트 천장을 배경으로 있을 때 색 대비가 사라져 놓치는 패턴을 발견(같은 사람·같은 헬멧이 배경에 따라 탐지 성공/실패가 갈림) — 색상 편향 문제가 실제 영상에서도 재현됨을 확인.

**우리 모델 vs YOLOv8-COCO(범용) vs ZERO(제로샷) 3자 비교**: `ultralytics` 설치 후 세 조건(항공뷰 다수 소인원, 근접 산업현장, 야외 원거리 단독 인물 + 상체만 크롭 시뮬레이션)으로 비교.
- 우리 도메인과 비슷한 장면에서는 우리 모델이 신뢰도·재현율 모두 가장 좋았음(예: 야외 원거리에서 person 0.98~0.99 vs YOLO 0.80~0.85 vs ZERO 0.61).
- 다만 "상체만 보이는" 크롭 조건에서는 우리 모델이 3번 중 2번 사람을 놓쳤는데 YOLO는 다 잡음 — SFCHD가 CCTV 특성상 전신 박스 위주로만 학습돼 생긴 약점으로 해석.
- 사용자가 공유한 완전히 낯선 이미지(터키 공장, 초광각, 소형 원경 인물 다수)에서는 반대로 **ZERO가 우리 모델보다 더 많은 원경 인물을 잡아냄** — 처음엔 "도메인 안/밖" 차이로 설명했으나, 사용자가 "그냥 학습 데이터가 부족해서 과적합 아니냐"고 반박했고 이게 더 정확한 진단이었다.

**근본 원인 재확인**: YOLO(COCO, 11만 8천 장, 전 세계 다양한 장면)와 비교하면 우리 SFCHD는 person 라벨 2만 개가 넘어도 실제로는 소수 카메라 설치 지점을 반복 촬영한 것이라 진짜 다양성이 훨씬 적다 — 장수가 아니라 다양성 부족에 의한 과적합.

**ZERO 파인튜닝 가능 여부 확인**: SDK를 직접 조회해본 결과 `training.catalog()`엔 RF-DETR 계열만 있고, `foundation`(ZERO가 속한 리소스)엔 `get`/`list`/`predict`만 있어 학습 관련 메서드가 없음 — **BDAI 플랫폼에서 ZERO는 파인튜닝 불가, 프롬프트 추론만 가능**하다는 걸 확인. 그래서 우리 학습 데이터 쪽을 보강하는 방향으로 결론.

**데이터셋 전면 재구성 착수**: 사용자 지시로 PPE v4 학습 취소(`training.cancel_run`, `status: canceled`) 후 데이터셋을 처음부터 다시 짬:
1. **합성 데이터 전량 삭제**: SFCHD 블러(4,000)/색상(2,000)/연기(4,000), CSS 연기(521), Roboflow running 블러(196) 총 10,717장 삭제(`assets.bulk_delete`) — 원본만(SFCHD 4,000 + CSS 717 + Roboflow running 196 = 4,913장) 남김. 합성 augmentation이 narrow-domain 데이터를 더 늘리기만 해서 다양성 문제엔 도움이 안 된다는 판단.
2. **SFCHD 세션당 다운샘플링**: SFCHD "원본" 4,000장을 카메라별로 분석해보니 고유 촬영 세션은 215개뿐이고, 세션 하나가 실제로 커버하는 시간은 평균 0.2~0.8분(12~48초)밖에 안 되는데 그 안에서 세션당 평균 19장씩 거의 같은 순간을 반복 촬영한 것으로 확인(사용자가 "영상 한 프레임 한 프레임이라 안 좋지 않냐"고 지적해서 실측). 세션당 처음/끝 최대 2장만 남기고 나머지 삭제 → 4,000장 → 412장(진짜 다양성은 그대로 유지, 반복 노출만 제거).
3. **SHWD(Safety Helmet Wearing Dataset) 조사·반입**: Google Drive에서 원본 다운로드(`gdown`, 1.12GB, VOC 포맷). README상 저장소는 MIT지만 원본 이미지는 Google/Baidu 검색 결과 스크래핑이라 라이선스가 불명확함을 사용자에게 확인 요청 → 사용자가 "해커톤에서 허용했다"고 승인. 실제 이미지를 열어보니 파일명 접두사별로 성격이 완전히 달랐다: `PartA_`(1,999장)는 진짜 CCTV(천장 설치·어안렌즈·타임스탬프) 강의실 영상 — 공사장 내용은 아니지만 카메라 앵글이 우리 배포 환경과 가장 비슷하고 "안전장비 없는 일반인" 다양성을 제공(사용자가 "공사장 아닌 일반인 감지도 중요하지 않냐"고 지적해서 재평가); `PartB_`(2,341장)는 손으로 든 일반 사진(매장 등) — CCTV 앵글도 아니고 공사장 내용도 아니라 제외; `part2_`+숫자만(3,231장)은 실제 공사현장 사진(근접 촬영). PartB만 제외한 5,240장을 `voc` 포맷 파서(`bdai_pipeline/import_public_dataset.py`에 신규 추가)로 반입(`hat→helmet`, `person→no_helmet`), 라벨 77,869개 전부 성공.
4. **`no_helmet` 클래스 제외**: SHWD 반입 후 `no_helmet`이 69,227개로 다른 클래스 대비 압도적으로 쏠려 클래스 불균형 발생 — SHWD 강의실 사진 한 장에 사람이 수십 명씩 있어 이미지당 no_helmet 라벨이 대량으로 나온 탓. `no_helmet`은 애초에 head+helmet IoU 규칙이 기하학적으로 대체 가능해 없어도 되지만, `no_vest`는 조끼가 "짝지을 신체 부위" 클래스가 없어 유지하기로 함(사용자와 상의해 `no_helmet`만 제외 결정). `no_helmet` 어노테이션 69,227개 전량 삭제(`annotations.batch_delete`, 배치 상한 500개 확인) → 클래스 삭제 → SHWD 중 helmet 라벨이 하나도 없어 완전 무라벨이 된 이미지 2,021장도 함께 삭제. `app/models/schemas.py`의 `ObjectClass`에서 `NO_HELMET` 제거, `app/rules/ppe_compliance.py`의 `no_helmet_boxes` 파라미터 및 관련 로직 제거(head 미탐지 시 UNKNOWN으로 판단 보류하도록 변경), 테스트 갱신 — 77개 전체 테스트 통과.

**최종 데이터셋 구성(SHWD까지, no_helmet 제외 직후)**: 전체 4,544장(SFCHD 412 + CSS 717 + Roboflow running 196 + SHWD 3,219). 클래스별: `person` 1,879 · `helmet` 10,072 · `vest` 872 · `no_vest` 629 · `head` 50.

## 41. COCO person 8,000장 반입 — "신체 일부만 보여도 감지" 보강

사용자가 "YOLO보다는 공사장과 무관하게 신체 일부만 나와도 잘 감지하도록" COCO를 넉넉하게 반입해달라고 요청. `instances_train2017.json`(COCO 2017 train 어노테이션, 약 241MB) 다운로드 후 person 카테고리만 필터링 — person이 있는 이미지 64,115장 중 이미지 경계에 닿아 잘린(partial) person 박스가 있는 이미지가 29,621장이나 됐다.

**의도적으로 "잘린 사람" 위주로 샘플링**: 경계에 닿은 이미지 5,000장 + 일반 이미지 3,000장 = 8,000장을 뽑아(`np.random.seed(42)` 재현 가능), COCO 이미지 서버에서 직접 다운로드(`ThreadPoolExecutor`, 24 워커, 8,000장 전부 성공, 약 7분). 샘플로 뽑아본 이미지들이 정확히 목표한 대로 나왔다 — 다리만 찍힌 프리스비 사진, 상반신만 나온 술집 테이블 사진, 배경 속 아주 작은 인물들까지.

**반입**: `import_public_dataset.py`는 이미 COCO 포맷을 지원해서 그대로 재사용, `person→person`만 매핑. 8,000장 업로드 100% 성공, 라벨 35,857개 중 35,853개 1차 성공 + 4개는 익숙한 "방금 올린 자산의 프로젝트 스코프 반영 지연"으로 실패 → `project_assets.bulk_add` 재호출 후 재시도로 100% 반입.

**최종 데이터셋 구성(2026-07-31 최종)**: 전체 12,544장(SFCHD 412 + CSS 717 + Roboflow running 196 + SHWD 3,219 + COCO person 8,000). 클래스별: `person` 37,736 · `helmet` 10,072 · `vest` 872 · `no_vest` 629 · `head` 50.

**남은 일**: person 신호는 COCO 덕에 충분히 다양해졌지만, `vest`(872)·`head`(50)는 여전히 적다 — 다음 학습 전에 이 부분을 더 볼지 판단 필요. 스냅샷 재생성 및 v5 학습은 아직 시작 전.

## 42. head/vest/no_vest 보강

**head (50 → 1,503)**: SHWD의 "person"(맨머리) 라벨을 no_helmet 대신 이번엔 `head`로 다시 반입 — 단, no_helmet 삭제 때 함께 지운 무라벨 이미지 2,021장은 복구하지 않고, 여전히 데이터셋에 남아있는(=hat 라벨이 있던) 3,219장 안에 있던 person 라벨만 대상으로 했다(69,227개 전체가 아니라 1,453개만 — 불필요하게 다시 대량 불균형을 만들지 않기 위함).

**vest/no_vest (872/629 → 7,320/2,651)**: 전용 데이터셋을 찾아 Kaggle "Safety Vests Detection Dataset"(CC BY 4.0, Roboflow `echo-dotf3/safety-vests` 원본, 3,897장, `Safety Vest`/`NO-Safety Vest` 클래스) 반입. Kaggle/Roboflow 둘 다 API 키가 없어 스크립트 다운로드가 막혀 있었는데, 사용자가 Kaggle API 토큰(`kaggle.json`)을 발급받아 `~/Downloads`에 받아줘서 `~/.kaggle/kaggle.json`으로 옮기고(권한 600) `kaggle` CLI로 다운로드. 포맷이 Roboflow의 "CSV(Pascal VOC 스타일)" export(`filename,width,height,class,xmin,ymin,xmax,ymax`)라 `import_public_dataset.py`에 `csv-voc` 파서를 신규 추가. train/valid/test 3분할을 합쳐서(파일명 충돌 없음 확인) 한 번에 반입, 라벨 8,470개 전부 성공. 샘플 검수 중 콜라주 형태의 이상 이미지 1장을 발견했으나 비중이 낮아(8장 중 1장) 필터링 없이 그대로 진행.

**최종 데이터셋 구성(2026-07-31 최종)**: 전체 16,441장. 클래스별: `person` 37,736 · `helmet` 10,072 · `vest` 7,320 · `no_vest` 2,651 · `head` 1,503. 다음 단계는 스냅샷 재생성 + v5 학습 시작.

## 43. "ID 재부착 대신 증거 사진" — PPE 미착용 로그 신설

37~39번 논의 중 나온 우려("CCTV 특성상 같은 사람이 사라졌다 나타나면 같은 ID를 못 이어붙이는데 괜찮나")에 대해, 사용자가 직접 대안을 제시했다: **ID 연속성을 억지로 복원하려 하지 말고, 매 감지 이벤트마다 그 순간의 증거 사진(프레임+박스)을 로그에 남겨서 관리자가 눈으로 판단하게 하자**는 것. ID가 바뀌어도 로그는 그냥 새 건으로 계속 쌓이면 되고, 사람이 사진 두 장을 보고 "혹시 같은 사람인가"를 판단하면 되는 구조다.

**발견한 공백**: 확인해보니 지금까지는 PPE 미착용이 감지돼도 `ppe_violations_today` 카운터만 올라갈 뿐, 사진이 붙은 개별 로그가 전혀 없었다. 화재 이후 작업자 로그(`worker_log`)에도 애초에 프레임 사진 경로만 있었지 박스 좌표는 없었다.

**구현**:
- `WorkerEventLogEntry`/`IncidentTimelineEntry`에 `frame_path`+`bbox_xyxy` 필드 추가, `worker_log.record_if_changed()`가 박스 좌표를 받아 로그에 남기도록 수정.
- `PpeViolationLogEntry` 신설 + `app/rules/ppe_violation_log.py`(기존 로그 모듈들과 동일한 append-only 패턴) — **착용→미착용으로 막 바뀐 순간에만** 기록(계속 미착용 상태가 지속되는 동안은 매 프레임 안 남김). 헬멧/조끼를 각각 독립적으로 추적해서, 한 사람이 헬멧만 벗어도 그 건만 기록됨.
- `scenario_runner.py`에 `DemoState.ppe_compliance_prev`(track_id별 직전 착용 상태)를 추가해 "새로 미착용이 됐다"를 판정하는 데 씀. 추적 ID가 끊기면 그냥 새 track_id로 새 기록이 시작될 뿐 — 이게 의도된 동작.
- `GET /ppe-violations/{camera_id}`(신규, `app/api/ppe.py`) — 전체 미착용 이력을 시간순으로 반환.
- `app/api/incidents.py`의 사고 리플레이 타임라인에도 `ppe_violation`을 4번째 소스로 병합 — 평상시 PPE 위반과 화재 이후 사건을 한 타임라인에서 같이 볼 수 있음.

**검증**: `ppe_violation_log` 단위 테스트 5개(첫 위반 기록/중복 방지/재발 시 재기록/ID 바뀌어도 독립 기록/헬멧·조끼 별도 추적), API 통합 테스트 2개(정렬 확인, 타임라인 병합 확인) 추가. 백엔드 테스트 스위트 77개 → 84개 전부 통과.

**설계 의도 요약**: 이 시스템은 어차피 얼굴인식·복장기반 병합을 원칙적으로 금지하고 있어서 완벽한 재식별은 원천적으로 불가능하다(2번 절대 원칙, 20번 로그의 ID Switch 논의 참고). 그럴 바엔 AI가 억지로 "같은 사람"이라고 추측하지 않고, 매번 정직하게 새 기록을 남기되 판단에 필요한 증거(사진)는 확실히 남겨서 최종 판단은 사람에게 맡기는 쪽으로 설계했다 — CLAUDE.md의 "AI가 확정 선언하지 않는다"는 원칙과 같은 방향이다.

## 44. 프론트엔드 담당 팀원 핸드오프 — screen_guide.md 갱신

프론트엔드는 다른 팀원이 별도로 개발 중이라는 걸 확인. 오늘 만든 기능 4개(사고 리플레이·확인 우선순위·2차 확인 표시·PPE 미착용 로그)가 전부 백엔드에만 있고 `docs/screen_guide.md`(프론트 개발자가 화면 개발 기준으로 삼는 문서, 19번 로그 참고)엔 반영이 안 돼 있던 걸 발견 — `frontend/src/api.ts`를 확인해보니 실제로 오늘 만든 API를 하나도 호출하고 있지 않았다.

**갱신 내용**:
- "프론트엔드 코드가 저장소에 없다"는 옛 문구를 "이미 진행 중"으로 수정
- 화면 1(평상시 대시보드)에 PPE 미착용 로그 섹션 추가 — API 상태를 `확장 필요`→`준비됨`으로 정정
- 화면 3(비상 대시보드)에 확인 우선순위 목록·2차 확인 결과(`situation_note`) 필드 추가. **`WorkerStatus`에 `confidence`/`visibility` 필드가 이미 있는데 문서엔 "스키마 확장 필요"로 낡게 남아있던 것도 같이 정정**(실제로는 이미 준비된 상태였음)
- 신규 화면 6번(사고 리플레이) 섹션 추가 — 타임라인 목록 + (선택) 특정 시각 스냅샷 재구성
- **공통 패턴 섹션 신설**: PPE 로그·작업자 로그·사고 리플레이가 전부 같은 모양(`frame_path`+`bbox_xyxy`)을 가진다는 것, 이미 있는 `DetectionOverlay.tsx`를 그대로 재사용해 단일 박스를 그릴 수 있다는 것, **로그를 ID로 묶거나 "동일인 추정" 표시를 자동으로 하지 말라**는 주의사항(43번의 설계 의도를 프론트 쪽에도 명시적으로 전달)을 정리
- 구현 우선순위 표를 전부 `API 준비됨`으로 갱신 — 지금은 5개 화면 다 프론트에서 바로 개발 시작 가능한 상태

이 문서와 백엔드 `/docs`(Swagger)가 실제 소스 오브 트루스이므로, 앞으로 백엔드 스키마/엔드포인트가 바뀔 때마다 이 문서도 같이 갱신해야 한다는 걸 재확인.

## 45. 유령 트랙 재부착 버그 수정 (byte_track.py)

20번에서 발견하고 "사용자 요청으로 이번엔 수정하지 않고 기록만" 남겨뒀던 버그를 마무리했다: 화면이 완전히 비었다가(전원 화면 이탈) 한참 뒤 전혀 다른 새 사람이 예전 위치 근처에 나타나면, `max_lost_frames` 안에서 죽지 않고 남아있던 옛 트랙(유령 트랙)이 그 새 사람에게 잘못 재부착되는 문제.

**원인**: `_greedy_match`가 트랙이 놓친 지 1프레임이든 `max_lost_frames` 직전이든 항상 같은 느슨한 IoU 기준(기본 0.3)으로 재매칭을 허용했다. 예전 위치와 대충만 겹쳐도(IoU 0.3만 넘으면) 매칭이 성립해버리는 구조.

**수정**: `_required_iou(track)`을 추가해, 트랙이 놓친 지 오래될수록(`time_since_update`가 `max_lost_frames`에 가까워질수록) 요구 IoU를 **제곱으로 급격히** 끌어올리도록 했다(최대 0.95까지). 놓친 지 얼마 안 된 트랙(짧은 가려짐)은 기존처럼 관대하게 통과시키고, 오래 놓친 트랙은 "거의 완전히 같은 자리 그대로"인 경우만 재매칭되게 만들어 우연한 근접 재부착을 걸러낸다. 얼굴·복장 등 신원 정보는 여전히 전혀 안 쓴다 — 순수하게 "얼마나 오래 놓쳤는지"라는 시간 정보만 추가로 반영한 것.

**검증**: 버그를 그대로 재현하는 테스트(`test_stale_track_does_not_reattach_to_a_new_person_nearby` — 8/10프레임 놓친 뒤 IoU 0.67짜리 새 사람이 나타나도 새 ID를 받는지 확인)와, 과도하게 막지는 않는지 확인하는 대조 테스트(`test_stale_track_still_reattaches_if_almost_exactly_same_spot` — 완전히 동일한 위치면 오래 놓쳤어도 여전히 재부착)를 추가. 기존 추적 테스트 7개는 전부 `time_since_update`가 작은 상황이라(직전 프레임에 막 놓친 경우) 영향 없이 그대로 통과 — 짧은 가려짐 복구 기능은 그대로 유지됨을 확인. 백엔드 테스트 스위트 84개 → 86개 전부 통과.

## 46. 평상시/비상시 파이프라인 재설계 — 평상시 추적 제거, 화재 후 구역별 상황 집계

사용자가 실사용 관점에서 파이프라인 전체를 다시 구체화해달라고 요청 — 큰 변경이라 Plan Mode로 들어가 설계를 먼저 정리하고 승인받은 뒤 구현했다.

**핵심 결정 3가지 (사용자와 논의로 확정)**:
1. **평상시엔 추적(ByteTracker)을 아예 안 쓴다.** 사람이 화면을 들락날락할 때마다 추적 ID가 계속 새로 매겨져서(43번 참고) 의미가 없다는 걸 이미 확인했기 때문 — "지금 몇 명 보이는지"만 있으면 되지 "누가 계속 같은 사람인지"는 평상시엔 필요 없다는 판단. 화재경보가 뜬 순간부터만 추적을 시작해 관측 지속시간을 잰다(반대로 이때는 추적이 꼭 필요).
2. 화재 판정을 "5프레임 윈도우 중 60% 이상 양성"에서 **"5초 주기 샘플링, 최근 2개 연속 양성"**으로 단순화. 5초 주기라는 전제가 있으면 비율 계산보다 단순 연속 카운트로 충분하다는 판단.
3. **PPE 미착용 위반은 사람을 특정하지 않고 "위반 사건"만 기록.** 처음엔 ZERO가 찾은 "쓰러진 사람" 박스를 어느 트랙에 속하는지 어떻게 아냐고 필자가 헷갈려 사용자에게 "1:1로 매칭이 안 된다"고 잘못 설명했는데, 사용자가 "감지한 사람이 종합적으로 집계 안 된다는 거냐"고 되물어서 다시 확인해보니 — 이미 트래커에 쓰는 위치 기반 매칭 기법을 그대로 쓰면 되는 문제였다. 그래서 화재 후 구역별 상황 집계는 **ZERO가 찾은 우려 상황 박스를 그 순간 추적 중인 사람 박스와 중심점 거리로 매칭**하는 방식으로 확정했다 — 카테고리 합계가 항상 그 구역 인원수와 정확히 같아지는 방식.

**구현 (파일별)**:
- `app/models/schemas.py`: `PpeViolationLogEntry`에서 `track_id`/`violation`(단수) 제거 → `violations: list[str]`로 교체. `WorkerStatus`에 `current_bbox_xyxy` 추가(비상시 실시간 관측중=초록/장기체류=빨강 박스 오버레이용). 신규 `PpeDetectionSettings`(카메라별 헬멧/조끼 감지 on/off), `ZoneSituationEntry`/`ZoneSituationLogEntry`(구역별 상황 집계).
- `app/rules/ppe_settings.py`(신규): 카메라별 헬멧/조끼 감지 토글 저장·조회.
- `app/rules/ppe_compliance.py`: `detect_helmet`/`detect_vest` 플래그 추가 — 꺼지면 판정 자체를 안 하고 `UNKNOWN` 고정.
- `app/rules/ppe_violation_log.py`: track_id 기반 저장(카메라당 트랙별 파일)을 **카메라당 파일 하나 + 위치(IoU)·시간(30초 쿨다운)·위반조합 기반 dedup**으로 전면 교체. `record_if_new_violation()`이 실제로 새로 기록했는지 `bool`을 반환하도록 해서, 호출부가 "새로 감지된 위반"일 때만 카운터/이벤트를 올릴 수 있게 함.
- `app/rules/alarm_trigger.py`: `evaluate()`를 `min_hit_ratio`/`min_window_size` 방식에서 `consecutive_required`(기본 2) 단순 연속 카운트 방식으로 교체.
- `app/inference/situation_probe.py`: `PROLONGED_PRESENCE_PROMPTS`를 3개→2개("쓰러진 사람"/"연기에 둘러싸인 사람")로 정리(중복 제거). 신규 `probe_zone_situation()` — ZERO를 프레임 전체에 한 번만 불러 찾은 박스를 그 순간 추적 중인 사람과 위치로 매칭, 매칭 안 된 사람은 전부 "체류중"으로 남겨 항상 합계가 인원수와 일치하게 만듦.
- `app/rules/zone_situation_log.py`(신규): `fire_alert_log.py`와 동일한 카메라당 append-only 로그.
- `app/pipeline/scenario_runner.py`(핵심 재작성): 프레임 루프를 `fire_triggered_at is None`(평상시: 추적 없이 person 박스마다 구역+PPE만 판정) / `else`(비상시: 이때부터 추적 시작, PPE 스킵, PROLONGED_PRESENCE 전환이 하나라도 생기면 `probe_zone_situation`을 비동기로 한 번 호출해 로그+situation_note 갱신) 두 갈래로 명확히 분리.
- API 계층: `app/api/ppe.py`에 `GET`/`PUT /ppe-settings/{camera_id}`, `GET /zone-situation/{camera_id}` 신설, `/ppe-violations/{camera_id}` 응답을 새 스키마에 맞춰 갱신. `app/api/incidents.py`의 사고 리플레이 타임라인에 `zone_situation` 소스 추가, `ppe_violation` 텍스트 조립을 `violations` 리스트 기준으로 교체.

**검증**: 기존 테스트 중 `ppe_violation_log`/`alarm_trigger`/`ppe_compliance`/`ppe_violations_api`/`incidents_api` 관련 테스트를 새 설계에 맞춰 재작성하고, `probe_zone_situation`(5개)·`zone_situation_log`(4개) 신규 테스트를 추가했다. 백엔드 테스트 스위트 86개 → 104개 전부 통과. `python -c "from app.main import app"` 임포트 스모크 테스트도 통과.

**문서 동기화**: `CLAUDE.md`(3번 컴포넌트 표에 구역별 상황 집계·PPE 미착용 로그 행 추가, 4-3에 집계 카테고리 추가, 6번 MVP 범위에 평상시/비상시 추적 구분 명시), `docs/screen_guide.md`(PPE 로그 표에서 track_id 제거, 헬멧/조끼 토글 UI, 실시간 관측중/장기체류 박스 색상, 구역별 상황 집계 화면, 1~9 격자 보조선 UX, 사고 리플레이 타임라인에 zone_situation 소스 반영)도 함께 갱신.

## 47. 46번 재설계 대비 원 요구사항 재검토 — 누락 2건 보완

46번 구현을 끝낸 뒤, 사용자가 "내가 요구한 걸 다 반영했는지 검토해줘"라고 요청해서 원래 요청 원문과 구현을 항목별로 다시 대조했다. 대부분 반영돼 있었지만 2가지가 빠져 있었다.

**1) 평상시 실시간 "헬멧 (미)착용" bbox 라벨 데이터가 없었음**: 원 요청은 "평상시에 카메라가 감지해서 사람/헬멧/조끼 bbox 표시 + 헬멧/조끼 bbox엔 '헬멧 (미)착용' 라벨"이었는데, 46번 구현은 위반 "사건"만 로그로 남기고(`ppe_violation_log`), 지금 화면에 보이는 모든 사람의 실시간 착용 여부를 프론트가 그릴 데이터 자체가 없었다. `PersonComplianceBox` 스키마(`bbox_xyxy`/`zone`/`helmet`/`vest`/`confidence`) 신설 + `scenario_runner.py`가 평상시 매 프레임 사람마다 판정해서 `STATE.current_person_compliance`에 담고 `GET /scenario/state`·웹소켓으로 노출하도록 추가(비상시엔 PPE 판정 자체를 안 하므로 항상 빈 리스트).

**2) 구역별 상황 집계 로그에 "그 안의 사람 bbox"가 빠져 있었음**: 원 요청 "그 상황과 안의 사람의 bbox를 캡처하고 로그로 남기는거야"를, 초반 Plan Mode 설계 때 카테고리별 인원수(`breakdown`)+전체 장면 사진(`frame_path`) 한 장으로만 단순화해서 승인받았었다. 이 부분을 사용자에게 다시 설명하다가("사진을 찍는다는게 구역별로 찍는게 아니라 전체 CCTV 화면을 찍는거지?" 같은 확인 문답을 거쳐) 사용자가 "저장해줘, 캡처 이미지에도 표시해줘"라고 명확히 요청 — `ZoneSituationBox`(카테고리+박스) 스키마를 추가하고 `ZoneSituationEntry.boxes: list[ZoneSituationBox]`로 확장, `scenario_runner.py`의 `_probe_zone_situation_and_log`가 `workers_by_zone`(구역별 사람 박스)와 `matched_category`(사람별 매칭 카테고리)를 그대로 조합해 채우도록 구현. `len(boxes)`가 항상 `total`과 같다(그 구역 사람 전원이 카테고리 하나씩 배정되므로).

**설계 의도**: 이번 확인 문답에서 "실시간 화면의 초록/빨강 박스"(`WorkerStatus.current_bbox_xyxy`, 이미 46번에서 구현됨)와 "저장된 로그를 나중에 다시 볼 때의 캡처 사진"(`ZoneSituationLogEntry`)이 서로 다른 것이라는 걸 사용자가 헷갈려 해서, 실시간 표시는 이미 되어 있고 이번 보완은 순전히 "지난 기록을 다시 열어봤을 때도 사진 위에 박스가 그려지게" 하는 부분이라고 명확히 구분해서 설명했다.

**검증**: `test_zone_situation_log.py`에 `boxes` 필드 왕복·기본값(`[]`) 테스트 2개 추가, 박스-카테고리 매칭 로직을 독립적으로 재현하는 스모크 테스트로 `len(boxes) == total` 불변식을 확인. 백엔드 테스트 스위트 104개 → 105개 전부 통과. `CLAUDE.md`(구역별 상황 집계 행에 boxes 저장 언급 추가)·`docs/screen_guide.md`(구역별 상황 집계 로그 설명에 "전체 화면 사진 1장"이라는 점과 `zones[].boxes` 그리는 법 추가)도 함께 갱신.

## 48. PPE 판정 파이프라인 안정화 — head/upper_body 폴백, 위치 매칭 3단계 개선, UNKNOWN 표시 버그

`LastSight_Demo.mp4`(Kling AI 생성 데모 영상)로 종합 파이프라인을 실제로 돌려보면서 PPE 미착용 판정이 눈에 띄게 부정확한 걸 발견해 여러 라운드에 걸쳐 원인을 좁혀나갔다. 전부 실제 프레임을 다시 뽑아 눈으로 확인하고, ZERO를 직접 다른 프롬프트로 재호출해가며 원인을 검증한 뒤 고쳤다.

**1) head+helmet IoU 판정 폐기 → "안 잡히면 미착용" 단순화 → 오탐 발생 → head 판정 재도입**: 원래 head+helmet IoU 기반 판정(논문 방식)을 썼는데, ZERO가 "head" 단독 프롬프트를 거의 인식 못해(실측 0건) 한 번 폐기하고 "helmet/vest가 안 잡히면 바로 미착용"으로 단순화했다. 그런데 실제 영상에서 오탐이 발생 — 사람이 멀거나(작게 보임) 숙인 자세라 각도가 안 좋으면 실제로 착용했어도 안 잡히는데 그걸 곧장 미착용으로 확정해버렸다. 재실측해보니 "head"가 아니라 **"person head"/"upper body"**로 프롬프트를 바꾸면 인식이 잘 됐다(6명 중 5~6명, confidence 0.4~0.6대) — "helmet"→"safety helmet"과 같은 순수 어휘 문제였다. 다만 "safety helmet"과 같은 호출에 섞으면 서로 경쟁해 인식률이 크게 떨어져(실측), `app/inference/detector.py`에 `detect_head_upper_body()`를 별도 ZERO 호출로 분리했다. `app/rules/ppe_compliance.py`의 `evaluate_ppe_compliance()`를 "helmet 없으면 head가 보일 때만 미착용 확정, head도 안 보이면 UNKNOWN(판단 보류)"으로 재설계 — head/upper_body가 실제 시야를 확보했다는 증거일 때만 미착용을 확정하는 방식.

**2) 위치 매칭을 IoU → 중심점 거리로 교체**: 미착용 확정에 "연속 2회 관측" 히스테리시스(`app/rules/ppe_violation_log.py`)를 넣었는데도, 확정된 위반이 같은 사람인데 30초 쿨다운 안에 또 새로 찍히는 문제가 있었다. 원인은 "같은 사람"을 잇는 기준이 직전 위치와의 **IoU(박스 겹침)** 0.5 이상이었는데, 걷는 사람은 ~1초 샘플 사이에 박스가 거의 안 겹칠 만큼 이동해버려 매번 "새 사람"으로 오인된 것. `app.inference.situation_probe`가 이미 쓰던 **중심점 거리** 매칭으로 `app/rules/ppe_compliance.py`(`stabilize_display`)·`app/rules/ppe_violation_log.py`(`record_if_new_violation`) 둘 다 교체 — 걸음 정도의 이동엔 훨씬 완만하게 반응한다.

**3) 사람이 다닥다닥 붙어 있을 때 스트림이 옆 사람에게 넘어가는 버그**: 고정 거리 기준(150px, situation_probe에서 그대로 가져온 값)이 실제 사람 간 간격(화면상 12px까지도 붙어 있음)보다 훨씬 넓어서, 진짜 미착용인 사람 옆의 착용한 사람까지 같이 미착용으로 뜨거나(같은 스트림을 "훔쳐감"), 반대로 확정된 위반이 갑자기 풀렸다 다시 뜨는 라벨 스왑이 발생했다. `_adaptive_match_distance()`(사람 박스 너비의 75%, 최소 30px~상한 150px)로 매칭 거리를 사람 크기에 비례하게 좁히고, **한 프레임(같은 `now` 시각) 안에서는 스트림 하나당 한 명만 매칭**되도록(`s.last_seen == now`인 스트림 제외) 막았다 — 인접한 두 사람이 같은 순간에 같은 스트림을 동시에 가져가는 걸 방지.

**4) UNKNOWN이 "정상"처럼 보이는 버그**: `stabilize_display`가 `raw_state == UNKNOWN`이면 스트림을 안 건드리고 곧장 UNKNOWN을 반환했는데, UNKNOWN은 위반 목록에 안 들어가 화면상 "정상"과 구분이 안 됐다. ZERO가 머리/헬멧을 둘 다 놓치는 순간(흔함)마다 확정된 미착용 표시가 잠깐씩 흰색으로 깜빡이는 원인이었다. 근처에 이미 확정된 스트림이 있으면 **그 표시 상태를 그대로 유지**하도록 수정 — "이번엔 정보가 없다"를 "방금 확인됐다"로 덮어쓰지 않는다. pending_count는 건드리지 않아 노이즈 한 번으로 진행 중인 스트릭을 깨지 않는다.

**검증**: 매 단계 15~57초 구간 클립(`backend/scripts/annotate_pipeline_video.py --start-sec 15 --end-sec 57`)을 실제로 재생성해 확인 — 최종적으로 사용자가 지적한 오탐 사례(원거리 오탐, 숙인 자세 오탐, 12초 인접 두 명 오탐, 39초 라벨 스왑, 41→42초 조기 해제, 22/28/31/35초 반복 깜빡임)가 전부 해결됨을 프레임 단위로 확인했다. 다만 ZERO 자체가 우연히 2연속 오탐(예: 근처 물체를 헬멧으로 오인)을 내는 경우까지는 알고리즘으로 완전히 막을 수 없다는 한계는 남는다 — v6 커스텀 모델이 더 안정적일 걸로 기대했으나 49번에서 확인하듯 실제로는 아니었다.

**부가 개선**: `backend/scripts/annotate_pipeline_video.py`에 `--start-sec`/`--end-sec` 옵션 추가(특정 구간만 빠르게 재검증), 샘플 주기를 24프레임(~1초)→16프레임(~0.67초)으로 단축.

## 49. ZERO vs 커스텀 모델(v6-29k-capped) 실측 비교 — ZERO 유지 결정

48번 작업 중 v6-29k-capped 학습(`rf-detr-large`, 100 epoch 설정에 55 epoch에서 조기 종료, `succeeded`)이 끝나고 이미 배포까지 완료돼 있었다(`RF-DETR Large · v6-29k-capped`, deployment_id `9960de0a-cf20-44dc-9af7-19bb232499bf`). 사용자 요청으로 `LastSight_Demo.mp4` 전체(87.3초)를 ZERO 버전과 커스텀 모델 버전 각각으로 처리해 직접 비교했다.

**검증 지표(BDAI 학습 결과, 55 epoch 시점)**: mAP@50 0.84, precision 0.89, recall 0.83 — 수치만 보면 양호.

**버그 발견 및 수정 (비교 전에 먼저 잡음)**: `app/inference/detector.py`의 `_CLASS_NAME_TO_OBJECT_CLASS` 매핑에 ZERO용 별칭 `"safety helmet"`만 있고 커스텀 배포 모델이 실제로 반환하는 클래스명 `"helmet"`이 빠져 있어서, **커스텀 모델의 헬멧 탐지 결과가 전부 무시되고 있었다.** `"helmet"` 키를 추가하고, ZERO에 보낼 프롬프트 목록은 `_ZERO_TEXT_PROMPTS`로 별도 분리해 이 수정이 ZERO 프롬프트 구성에 영향 없게 했다.

**실측 결과(전체 영상 비교)**:
- PPE 미착용 확정 건수: ZERO 9건 vs 커스텀 모델 **0건**
- 화재경보 발생 시각: 둘 다 t=60초, 신뢰도 0.37로 동일(fire/smoke 탐지는 두 버전 모두 ZERO를 그대로 씀 — `FIRE_SMOKE_DEPLOYMENT_ID` 비활성 상태 유지 중이라 이 비교와 무관)
- 붐비는 장면(5~6명)에서 person 박스: ZERO는 대부분 잡히는데, 커스텀 모델은 **아예 하나도 안 잡히는 프레임**이 여럿 있었다(t=35초, 50초 직접 확인)

**원인 분석**:
1. **person 클래스가 붐비는 장면에서 유독 약함**: confidence를 0.01(사실상 무필터)까지 낮춰도 사람이 여럿 겹친 장면에서는 person 신뢰도가 0.02~0.07대로 주저앉았다(사람이 1~2명뿐인 장면에선 0.5~0.9대로 정상). helmet/vest는 붐비는 장면에서도 비교적 잘 잡히는 걸 보면 person 클래스만 특히 학습이 덜 된 것으로 보인다 — person 라벨(37,736개)이 COCO의 "잘린 사람" 위주 샘플링(41번 참고)이라 우리 CCTV의 "여러 명이 겹쳐 서 있는" 분포와 안 맞았을 가능성.
2. **head/no_vest가 사실상 예측에 안 나옴**: 학습 스냅샷엔 head 2,325개·no_vest 2,155개 인스턴스가 있었는데(`client.training.stats()`로 확인), confidence=0.01로 낮춰도 예측 결과에 단 한 건도 안 나왔다. `app/rules/ppe_compliance.py`의 head/upper_body 폴백은 커스텀 모델 배포 시엔 아예 호출을 건너뛰도록 짜여 있어서(다른 클래스보다 훨씬 적은 데이터로 이 모델에서는 실질적으로 못 쓴다는 뜻), 미착용을 확정할 신호 자체가 없어 0건으로 나온 것 — 48번에서 고친 로직의 버그가 아니라 이 모델의 클래스 불균형 문제.

**결정**: 사용자가 두 영상을 비교해보고 **ZERO를 그대로 쓰기로 결정**. `.env`의 `PPE_DEPLOYMENT_ID`는 값(deployment_id)만 주석으로 남겨두고 비활성 상태 유지 — person 데이터를 보강(특히 여러 명이 겹친 장면 위주로)하고 head/no_vest 데이터도 더 확보해 재학습하면 다시 켤 수 있게 해뒀다. helmet/vest 자체의 탐지 정확도는 커스텀 모델이 나쁘지 않았다는 점은 재학습 시 참고할 것.

## 50. 프론트엔드 통합 검증 중 발견한 백엔드 버그 3건 — 2차 검증이 실은 한 번도 로그에 안 남고 있었음

사용자 요청으로 프론트엔드(`npm run dev`)와 백엔드를 함께 띄우고 `LastSight_Demo.mp4` 전체로 사전계산한 시나리오를 실제로 재생하며 브라우저(Chrome 자동화 도구)로 화면을 직접 확인했다. 평상시 대시보드·화재경보 전환·작업자 카드는 눈으로 보기엔 정상이었지만, 개별 작업자 브리핑 카드가 계속 비어있는 걸 발견해 파고들다가 서로 다른 3개의 버그를 찾았다.

**1) 2차 검증 결과가 실제로는 한 번도 기록된 적이 없었다 (경로 중복 버그)**: `GET /zone-situation/demo-camera`가 항상 빈 배열을 반환했다. `_probe_zone_situation_and_log()`가 프레임 이미지를 열 때 `FRAMES_DIR / frame_path_rel`로 경로를 합쳤는데, `frame_path_rel` 자체가 이미 `"frames/0069.jpg"` 형태(precompute_demo.py가 이 형태로 저장)라 `FRAMES_DIR`(이미 `.../data/demo/frames`)과 합치면 `.../frames/frames/0069.jpg`로 겹쳐 파일을 못 찾고 조용히 리턴하고 있었다. `cv2.imread` 실패 시 그냥 `return`이라 예외도 안 남아 겉으로는 티가 안 났다 — **48·49번에서 검증한 개선 사항들과 무관하게, 46번에서 이 기능이 처음 만들어진 이래로 계속 작동 안 하고 있었던 것**으로 보인다. `FRAMES_DIR.parent / frame_path_rel`로 수정.

**2) asyncio 태스크가 완료 전에 가비지 컬렉션될 수 있었다**: `asyncio.create_task(_probe_zone_situation_and_log(...))`의 반환값을 어디에도 저장하지 않고 있었다. 파이썬 공식 문서 경고대로, 이벤트 루프는 태스크를 약한 참조로만 들고 있어서 다른 참조가 없으면 실행 도중에도 가비지 컬렉션될 수 있다. 모듈 전역 `set()`에 태스크를 담아뒀다가 완료되면 스스로 빠지는 `_spawn_background()` 헬퍼를 추가해 참조를 유지하도록 고쳤다. (1번을 고치기 전까지는 이 버그가 실제로 문제를 일으켰는지 확인이 안 됐지만, 최소 잠재적 위험이라 같이 고쳤다.)

**3) `STATE` 전역 재할당 때문에 `app/api/workers.py`가 항상 옛 빈 상태만 보고 있었다**: `scenario_runner.reset()`이 `global STATE; STATE = DemoState()`로 모듈 전역 이름 자체를 새 객체로 재할당하는데, `app/api/workers.py`는 `from app.pipeline.scenario_runner import STATE`로 **이름을 값으로 import**하고 있었다. 파이썬에서 `from module import name`은 import 시점의 객체 참조를 복사해오는 것이라, 이후 원본 모듈에서 그 이름이 재할당되면 이미 import해간 쪽은 서버 시작 시점의 옛(빈) 객체를 영원히 참조하게 된다 — `GET /scenario/state`(항상 `scenario_runner.py` 내부에서 모듈 전역을 직접 참조)는 정상인데, `GET /workers`·`GET /briefing/{track_id}`(workers.py 경유)만 계속 빈 리스트/더미 데이터나 404를 반환한 이유였다. `app/api/workers.py`가 `scenario_runner.STATE`처럼 모듈을 통해 접근하도록 고치고, 근본 원인 자체를 막기 위해 `reset()`도 `STATE = DemoState()` 대신 `STATE.__dict__.update(DemoState().__dict__)`로 **기존 객체를 제자리에서 초기화**하도록 바꿨다 — 앞으로 누가 또 이름으로 import해도 이 버그가 재발하지 않는다.

**디버깅 과정 메모**: 이 세 버그를 찾는 데 예상보다 오래 걸린 이유 중 하나는, 백그라운드로 띄운 uvicorn 프로세스의 stdout/stderr가 프로세스가 살아있는 동안은 전혀 캡처되지 않는 환경이라(`conda run`의 버퍼링 + 장시간 실행 프로세스라 파이프가 안 flush됨) `logger.warning(...)`으로 남긴 예외 로그를 전혀 볼 수 없었던 것이었다. `PYTHONUNBUFFERED=1`과 `conda run --no-capture-output`을 붙여서 로그를 파일로 직접 리다이렉트하고 나서야 실시간으로 확인할 수 있었다. 이후 임시 `print(..., flush=True)`로 함수 진입·조기 리턴·예외 지점을 하나씩 찍어보고 정확한 원인을 특정한 뒤 제거했다.

**검증**: 세 버그를 모두 고친 뒤 프론트엔드에서 시나리오를 다시 재생해 (1) `GET /zone-situation/demo-camera`에 "체류중/쓰러진 사람/연기에 둘러싸인 사람" 카테고리가 실제로 기록되는 것, (2) `GET /briefing/{track_id}`가 정상적으로 요약 카드를 반환하는 것을 확인했다.

## 51. 비상시 개인별 추적 상태 전면 폐기 → 화재 후 매초 "2차 확인" 카드 방식으로 재설계

46번에서 이미 "화재경보가 뜬 순간부터만 추적을 시작"하는 것으로 한 차례 단순화했었는데, 실제로 데모 영상을 반복 재생하며 확인해보니 그 추적 자체가 또 문제를 일으켰다: 화면을 벗어났다 들어온 사람에게 예전 트랙 ID가 잘못 재부착되는 현상(T0010이 나간 사람 자리에 새로 들어온 다른 사람에게 그대로 이어짐)이 실측으로 확인됐다. 45번에서 고친 "오래 놓친 트랙의 재부착 억제"로도 완전히는 못 막는 사례라, 사용자와 논의 끝에 **비상시에도 개인별 추적 상태 자체를 걷어내기로** 결정했다.

**새 설계**:
- 화재 모드에서는 감지된 사람 전원을 개인별 상태 구분 없이 **초록 박스 하나로만** 표시한다(`DetectionOverlay.tsx`, `emergencyMode` 분기).
- 대신 화재경보가 뜬 순간부터 **매초(`SITUATION_PROBE_INTERVAL_SECONDS`) 그 프레임을 ZERO로 2차 확인**해 카드를 하나씩 쌓는다 — "누적 추정"이 아니라 "그 순간의 사실 기록"이라는 관점. 기존 `probe_zone_situation()`(46번에서 만든 위치-매칭 방식)을 그대로 재사용하되, 이번엔 프레임마다 새로 부여하는 합성 ID(`f"P{i}"`)를 쓴다 — 프레임 간 지속성이 아예 없으므로 ID 재부착 문제 자체가 발생할 수 없는 구조.
- 카테고리는 `STAY_CATEGORY`("체류중")·`PROLONGED_PRESENCE_PROMPTS`(["쓰러진 사람", "연기에 둘러싸인 사람"]) 그대로 유지.
- 카드 색상: 우려 카테고리 없으면 초록(`#4ade80`), 쓰러진 사람은 빨강(`#ff2d2d`), 연기에 둘러싸인 사람은 파랑(`#3b82f6`).
- 타임라인 이정표는 매초 쌓이는 카드를 다 보여주지 않고, **카테고리별로 "지금까지의 최고 인원 기록"을 새로 경신할 때만** 이정표로 뽑는다(`runningMax` 방식) — 화면이 초 단위 카드로 도배되지 않으면서도 "상황이 실제로 악화된 순간"만 짚어준다.

이 재설계로 `WorkerStatus`/`resolve_status()`(장기체류·관측중 등 개인별 상태 규칙, `app/rules/state_engine.py`)와 ByteTracker(`app/tracking/byte_track.py`)는 화재 모드 파이프라인에서 더는 쓰이지 않게 됐다 — 파일 자체는 단위 테스트가 딸린 독립 모듈이라 지우지 않고 남겨뒀다(과도한 삭제보다는 vestigial 상태로 보존하는 쪽을 선택).

## 52. PPE 위반 카드에 관리자 검토·정정 기능 추가 + 실시간 배경 태스크 예외 소실 버그

**요청 배경**: PPE 미착용 이벤트가 로그에만 남고 관리자가 "이건 오탐이었다"고 정정할 방법이 없었다. "영상 시작하자마자 노드 생기고, 미착용 감지될 때마다 노드·카드가 생기고, 카드를 눌러서 안전모/안전조끼 각각 착용·미착용으로 수정할 수 있게" 해달라는 요청에 맞춰 감사 추적(audit trail) 기능을 추가했다.

**구현**:
- `PpeViolationLogEntry`에 `id`(uuid), `helmet_state`/`vest_state`(AI 원판정), `reviewed_at`/`reviewed_helmet`/`reviewed_vest`(관리자 정정, 원판정과 별도 필드 — 절대 덮어쓰지 않음) 추가. 화면 어디서든 "유효 상태"는 `reviewed_* ?? *_state`로 계산한다.
- `PATCH /ppe-violations/{camera_id}/{entry_id}`(신규) — 관리자가 최종 판정을 제출.
- 프론트엔드 `PpeViolationCard`/`PpeViolationEditModal` 신설 — 카드 클릭 시 그 순간 bbox·프레임을 보여주고, 안전모/안전조끼 각각 착용·미착용 버튼으로 정정.

**버그 발견**: `id` 필드를 `str`(기본값 없음)로 추가하자마자 첫 PPE 위반이 감지되는 순간부터 프론트엔드 화면이 완전히 멈췄다(영상은 계속 재생되는데 박스·카드는 그대로). 원인 추적 결과: `data/ppe_violation_logs/demo-camera.json`에 이미 `id` 필드 없이 쌓여있던 기존 항목 190여 개를 `PpeViolationLogEntry.model_validate()`로 다시 읽어들이는 순간 Pydantic `ValidationError`가 발생했는데, 이 예외가 FastAPI의 백그라운드 `asyncio.Task`(`app/api/scenario.py`, 반환값을 어디에도 저장하지 않고 모듈 전역 변수 하나에만 잡아둠) 안에서 조용히 죽어버려 **로그에 아무 에러도 안 남았다** — 50번에서 겪었던 "참조 안 된 asyncio 태스크" 문제군의 또 다른 사례. `/scenario/state`의 `frame_idx`가 정확히 그 위반이 감지된 시점에 멈춰있는 걸 발견하고, `load_ppe_violation_log()`를 파이썬 셸에서 직접 호출해 같은 에러를 재현한 뒤에야 원인을 특정했다. `id: str = Field(default_factory=lambda: uuid.uuid4().hex)`로 기본값을 주는 것으로 해결 — 옛 항목은 불러올 때마다 새 id를 받게 되지만, 개별적으로 다시 검토할 일은 없으므로 문제 없음.

## 53. 타임라인 통합·재디자인 — 평상시/비상시 분리 화면 하나로, 라벨 배치 알고리즘 교체, 드래그 병합

- **타임라인 통합**: 화재가 나면 그 전까지의 평상시 PPE 위반 이력이 화면에서 통째로 사라지는 문제(51번 재설계 직후 실측)를 사용자가 지적 — 시나리오 시작(t=0)을 공통 기준점으로 삼아 "평상시 위반 이력 → 화재 발생 → 2차 확인 이정표"를 한 타임라인(`DashboardTimeline.tsx`)에 이어서 그리도록 기존 `SituationTimeline.tsx`/`PpeTimeline.tsx` 두 컴포넌트를 하나로 합쳤다.
- **라벨 겹침**: 처음엔 홀짝 교대로 라벨을 위/아래에 배치했는데, 시간이 가까운 이정표 여러 개가 우연히 같은 쪽에 몰려 겹치는 문제가 실측으로 확인됐다. `assignTimelineSides()`(각 항목을 놓을 때 "그 쪽 마지막 항목과의 간격"이 더 넓은 쪽을 그리디하게 고름)로 먼저 완화했으나, 이 방식도 위/아래 딱 2단뿐이라 한 지점에 3개 이상 몰리면 여전히 겹쳤다 — 이번 세션에서 `assignTimelineLayout()`으로 교체, 위/아래 각각 **여러 단(tier)**을 두고 라벨 폭(글자 수 추정)만큼 간격이 나는 가장 가까운 단에 채워 넣는 방식으로 다시 고쳤다. 트랙 높이도 실제 쓰인 최대 단수에 맞춰 동적으로 계산.
- **CSS overflow-x/overflow-y 트랩**: `overflow-x: auto`만 줘도 CSS 스펙상 `overflow-y`가 강제로 `auto`가 돼, 라벨이 위/아래로 튀어나가는 부분이 그대로 잘리는 문제가 있었다 — 가로 스크롤 전용 자식(`.situation-timeline__scroll`)을 분리하고 트랙 자체 높이를 라벨이 들어갈 공간까지 포함해 동적으로 계산하는 방식으로 해결.
- **노드-라벨 연결선**: 사용자가 "노드랑 설명이 선으로 이어진 디자인"을 요청 — 웹의 마일스톤 타임라인 레퍼런스(로그팝 스타일)를 참고해, 각 dot에서 라벨까지 실제 거리만큼 얇은 선(`.situation-timeline__stem`, 노드 색과 동일)을 그어주는 방식을 추가.
- **드래그로 PPE 노드 병합**: 위치 매칭 실패로 같은 사람의 같은 위반이 노드 두 개로 쪼개지는 경우, 관리자가 직접 두 노드를 끌어다 놓으면 하나로 합쳐지는 기능(`POST /ppe-violations/{camera_id}/merge`, 이른 시점 데이터를 남기고 늦은 쪽 삭제)을 추가 — 이번 세션에서 실제로 헬멧 미착용 노드와 조끼 미착용 노드를 드래그해 병합되는 것, 병합 후 더 이른 프레임 이미지가 남는 것을 API 직접 호출로 end-to-end 검증했다.
- 그 외 UI 정리: 최근 이벤트(`EventFeed`) 사이드바 제거하고 타임라인을 화면 오른쪽 끝까지 확장, 안전장비/구조 카드 그리드를 기본 접힘 토글로 변경, `SituationCard` 디자인을 `PpeViolationCard`와 통일, "이상상황 감지" 통계 카드 제거(매초 확인 스냅샷 개수일 뿐 실제 위험도가 아니라 오해 소지가 있었고 구조 카드로 이미 확인 가능해 중복 판단), 화재 발생 노드를 원형 dot 대신 발광 효과가 있는 불꽃 아이콘으로 표시.

## 54. 구역(zone) 관리 기능 확장 — 고정 통계 카드, 그리기/편집 UI, 버그 2건

- **구역 통계 고정 표시**: 기존엔 `zone_person_counts`에 값이 있는 구역만 카드가 떴다가 사람이 없으면 카드 자체가 사라졌다 — `zone-maps` API로 카메라에 등록된 전체 구역 목록을 미리 받아, 값이 없는 구역도 `?? 0`으로 항상 표시하도록 변경.
- **"구역 보기" 모달**: 처음 보는 사람이 "A구역"이라는 이름만으로 실제 화면 어디인지 알기 어렵다는 점을 고려해, 첫 프레임(`0000.jpg`) 위에 구역 폴리곤을 색으로 칠해 보여주는 모달 추가.
- **"구역 편집"**: 관리자가 직접 카메라 화면에 클릭으로 폴리곤을 그리고 이름을 지어 구역을 새로 정의할 수 있는 에디터(`ZoneMapModal.tsx`) 추가. 백엔드(`app/rules/zone.py`)는 이미 임의 개수·모양의 폴리곤을 그대로 처리하도록 만들어져 있어서(좌/우 절반 분할은 데모용 초기값일 뿐), 프론트엔드 에디터만 있으면 됐다.
- **버그 1 (구역 편집이 실제 인원수·카드에 반영 안 됨)**: `run_scenario()`가 "시나리오 시작"을 누를 때마다 `_register_demo_zone_map()`을 무조건 호출해 구역 설정 파일을 A/B 절반 분할로 매번 덮어쓰고 있었다 — 관리자가 새 구역을 그려 저장해도 시나리오를 다시 시작하는 순간 원래대로 리셋됐던 것. 구역 설정 파일이 이미 있으면 절대 건드리지 않고, 파일 자체가 없는 최초 부팅 시에만 기본값을 만들도록 수정.
- **버그 2 (편집 진입 시 데이터 유실 위험)**: 구역 목록을 아직 다 불러오기 전에 "편집"을 누르면 `draftZones`가 빈 배열로 초기화돼, 그대로 저장하면 기존 구역이 전부 삭제될 수 있는 경쟁 상태(race condition)를 테스트 중 직접 재현했다 — `zoneMap`이 로딩되기 전에는 편집 버튼 자체를 비활성화하는 것으로 해결.
- **CSS 캐스케이드 버그**: 편집 모드에서 이미지 위 SVG에 `pointer-events: auto`를 줘도 클릭이 씹히는 문제 — 같은 명시도(0,1,0)를 가진 `.briefing-card__image-overlay { pointer-events: none }` 규칙이 소스상 더 뒤에 있어 이겨버린 것이 원인. 두 클래스를 겹친 선택자(`.briefing-card__image-overlay.zone-map-modal__svg--drafting`)로 명시도를 올려 해결.

## 55. 화재 직후 구조 카드 사진이 실제 화면과 다른 시점을 보여주던 버그 — 프레임 파일명 충돌

사용자가 "구조카드 프레임이 매치가 안 되는데?"라고 지적 — 특히 "초반이 안 맞아"(화재 발생 직후 카드들)라는 단서로 원인을 좁혀갔다.

**증상**: "화재 발생 후 0초" 카드를 열어보면 불꽃·연기가 전혀 없는, 화재 훨씬 이전의 깨끗한 장면이 나왔다.

**원인**: `scenario.json`을 촘촘하게 다시 만드는 두 스크립트(`precompute_demo_dense_head.py`: 화재 전 0~58초 구간용, `precompute_demo_dense_tail.py`: 화재 후 58초~끝 구간용)가 각각 **로컬 반복 변수(0부터 다시 시작하는 idx)로 이미지 파일명**을 지었다. `dense_tail`이 먼저 실행돼 화재 이후 프레임을 `0058.jpg`~`0174.jpg`쯤에 저장해뒀는데, 나중에 실행된 `dense_head`가 자기 프레임(화재 전 29.0~57.5초, idx 0~115)을 저장하면서 **똑같은 파일명(`0058.jpg`~`0115.jpg`, 58개)에 자기 이미지를 덮어써버렸다**. `scenario.json`의 JSON 메타데이터(감지 박스 등)는 두 시점 모두 그대로 남아있었지만, 그 58개 파일명이 가리키는 실제 그림 파일은 이제 하나(화재 전 것)뿐이었던 것 — 화재 직후(대략 t=58~72초, "화재 발생 후 0~11초"에 해당) 구간의 사진이 전부 화재 전 사진으로 뒤바뀐 상태였다. `python`으로 `scenario.json`의 `frame_path` 중복을 전수조사해 정확히 58개 충돌 그룹, 정확히 그 시간대라는 걸 확인해 가설을 검증했다.

**복구**: 감지 데이터(사람/헬멧/조끼/화재 박스)는 JSON에 멀쩡하게 남아있었으므로 ZERO를 다시 호출할 필요 없이, 원본 영상(`LastSight_Demo.mp4`)에서 충돌난 58개 시점의 프레임 픽셀만 다시 뽑아 새 파일명(`fix_XXXX.jpg`)으로 저장하고 `scenario.json`의 해당 항목만 그 경로로 갱신하는 일회성 스크립트(`scripts/fix_frame_collisions.py`)를 작성해 실행 — 순수 OpenCV 프레임 추출이라 비용 없이 몇 초 만에 끝났다. 복구 전후 `scenario.json.bak3` 백업, 복구 후 충돌 0건 확인.

**재발 방지**: 두 스크립트 모두 파일명을 로컬 idx 기반에서 **`t`(초, 밀리초 단위로 반올림)** 기반으로 바꿨다 — `dense_head`는 항상 t<58초, `dense_tail`은 항상 t≥58초를 다루므로 시간 범위 자체가 절대 안 겹치고, 그러면 t로 지은 파일명도 어느 스크립트를 어느 순서로 몇 번을 다시 돌리든 원천적으로 충돌할 수 없다 — "실행 순서에 의존하지 않는" 방식으로 근본적인 재발을 막았다.

**부가 개선**: 이 버그를 확인하는 과정에서 화재 발생 타임라인 노드가 상대 시간("+61초")만 보여줘 실제 몇 시 몇 분인지 바로 알기 어렵다는 것도 같이 발견돼, 노드 아래에 절대 시각(예: "오후 11:13:03")도 함께 표시하도록 추가했다. 화재 노드를 클릭하면 발생 일시·트리거 방식(자동탐지/수동)·신뢰도·구역을 보여주는 상세 카드(`FireAlertModal.tsx`)도 함께 추가했다(기존엔 클릭이 안 먹는 노드였음).

## 56. Gemini 기반 "요약 브리핑" 기능 신설 — 타임라인 데이터를 근거로 한 자연어 상황 요약

**배경**: 구조 카드 타임라인을 처음부터 다 훑지 않고도 지금까지 상황을 빠르게 파악할 수 있게, 버튼을 누른 시점까지의 데이터를 요약해주는 기능을 요청받았다. ZERO는 "있다/없다"만 답하는 개방형 어휘 탐지 모델이라 자유 문장 요약에는 애초에 쓸 수 없다는 걸 이전 세션에서 이미 확인해뒀던 터라(`app/inference/situation_probe.py` 상단 docstring 참고), 별도 LLM이 필요하다는 걸 먼저 사용자에게 설명했다.

**발견**: 사용자가 BDAI 플랫폼의 "모델 → gemini" 화면을 보여줬는데, 확인해보니 **테넌트에 Google Gemini가 이미 OpenAI SDK 호환 게이트웨이로 연결돼 있었다**(`https://llm.bdai.superb-ai.com/tenants/{tenant}/llm`, 모델 `gemini-3.5-flash` 등) — 기존에 ZERO 호출용으로 쓰던 `SUPERB_AI_API_KEY`/`SUPERB_AI_TENANT`(`.env`)가 접두사(`sbd_pk_...`)와 테넌트명이 정확히 일치해, **새 키 발급 없이 그대로 재사용**할 수 있다는 걸 확인했다.

**구현**:
- `app/inference/briefing.py`(신규): 화재경보·구역별 인원·2차 확인 이력(카테고리별 누적 최고치 + 가장 최근 확인)·PPE 위반 건수를 텍스트로 정리하고, 대표 프레임 이미지(현재 프레임 + 화재 발생 직후 첫 확인 프레임) 최대 2장을 함께 Gemini에 보낸다.
- 시스템 프롬프트에 CLAUDE.md 2번(절대 원칙)을 명시적으로 박아뒀다 — "전원 안전"·"대피 완료" 확정 금지, 잔류인원 확정 금지, 관측 끊긴 사람 안전/위험 단정 금지, 신원·인상착의 기반 동일인 단정 금지.
- `POST /situation-summary`(신규, `app/api/situation_summary.py`) — 호출 실패 시 예외를 던지지 않고 502로 명확히 알림(다른 추론 모듈과 같은 "있으면 좋은 보조 기능" 원칙).
- 프론트엔드: 타임라인 오른쪽 하단에 버튼 추가, 클릭 시 로딩 상태 표시 후 결과를 모달로 표시.

**버그**: 처음 `max_tokens=400`으로 테스트했더니 응답이 "3일 13시 52분 기준 화재 경보는"처럼 문장 중간에서 뚝 끊겼다. 원시 응답을 직접 뜯어보니 `finish_reason: "length"`, `completion_tokens: 15`인데 `total_tokens: 411`으로 격차가 컸다 — Gemini 3.x 계열이 답변 전에 내부적으로 쓰는 "사고(thinking)" 토큰이 `extra_content.google.thought_signature`라는 긴 필드로 같이 잡히는데, 이 토큰도 `max_tokens` 한도 안에서 같이 소진된다는 걸 확인했다. `max_tokens=2048`로 올려 해결(게이트웨이 한도 8,192 이내).

**디자인 개선**: 처음엔 2~4문장짜리 줄글 문단을 그대로 보여줬는데, "가독성이 없고 줄글이다, 디자인이 별로다"라는 피드백을 받아 응답 형식을 통째로 바꿨다 — 시스템 프롬프트에서 Gemini가 순수 JSON(`{"headline": "...", "points": ["...", ...]}`)으로만 답하도록 강제하고, 응답에 마크다운 코드블록이나 군더더기가 섞여도 가장 바깥 `{...}` 블록만 잘라 파싱하는 방어 로직(`_parse_summary`)을 추가했다(파싱 실패 시에도 원문 전체를 point 하나로 넣어 최소한 뭐라도 보여줌). 프론트엔드는 headline을 굵은 제목으로, points를 카드형 불릿 리스트로 렌더링 — 한눈에 스캔하기 쉬운 형태로 바뀌었다.

**버튼 이름**: "브리핑 요약" → "구조 브리핑" → 최종 "요약 브리핑"으로, 사용자 피드백에 따라 두 차례 수정했다.

**검증**: 매 단계 백엔드 테스트 스위트(92 passed, 사전에 있던 무관한 14개 실패 외 회귀 없음)와 프론트엔드 타입체크를 반복 확인했고, 실제 시나리오 재생 중 평상시·화재 발생 후 양쪽 모드에서 브라우저로 직접 버튼을 눌러 응답 내용·디자인을 확인했다.

## 58. Render 배포 — 단일 서비스 Docker 구성, 무료 티어 리소스 한계로 영상 스트리밍 503 발생·해결

해커톤 제출에 필요한 "서비스 구현(데모 링크)"를 위해 Render로 외부 접속 가능한 배포를 진행했다.

**구성 결정**: 백엔드(FastAPI)가 프론트엔드 빌드 결과물까지 같이 서빙하는 **단일 Docker 서비스**로 만들기로 했다 — CORS·두 서비스 관리를 피하고 URL 하나로 끝내기 위함. 데모 원본 영상(`LastSight_Demo.mp4`, 201MB)은 git에 없어서(57번 참고) 별도 처리가 필요했는데, `gh` CLI로 GitHub Release(`demo-assets-v1`)를 만들어 영상을 에셋으로 첨부하고 안정적인 다운로드 URL을 확보했다.

**구현**:
- `Dockerfile`(멀티스테이지): Node 스테이지에서 프론트엔드 빌드 → Python 런타임 스테이지에 `backend/`와 빌드된 `frontend/dist`를 복사
- `backend/requirements.txt`(신규): conda 없는 환경(Render)에서 pip만으로 설치하도록 `environment.yml`을 미러링(numpy→그대로, opencv→`opencv-python-headless`)
- `backend/app/main.py`: 모든 API 라우터/마운트를 등록한 "뒤"에 `frontend/dist`를 `"/"`로 마운트(`html=True`) — 순서를 지켜야 API 경로를 안 가림
- `frontend/src/api.ts`: 배포 환경(같은 오리진)에서는 `API_BASE`를 상대 경로("")로 써서 CORS 자체가 필요 없게 하고, 로컬 개발(`import.meta.env.DEV`)에서만 `localhost:8000`을 기본값으로 쓰도록 분기. 웹소켓 연결도 `API_BASE`가 빈 문자열일 때 `window.location`에서 직접 ws(s) URL을 구성하도록 수정
- `render.yaml`(Blueprint) — Render 대시보드에서 저장소만 연결하면 그대로 서비스가 만들어지게. 시크릿(`SUPERB_AI_API_KEY` 등)은 `sync: false`로 대시보드에서 직접 입력하게 함
- `.dockerignore` — 학습용 대용량 자산(`data/public_datasets` 17GB 등)이 빌드 컨텍스트에 안 들어가게

**로컬 검증**: 이 환경에 Docker가 없어서 Homebrew로 `colima`(경량 Docker 런타임)와 `docker` CLI를 설치해 컨테이너를 실제로 빌드·실행했다 — `/health`·정적 프레임·영상(Range 요청 포함)·전체 시나리오 재생까지 브라우저로 직접 확인한 뒤에야 Render에 올렸다. Render 대시보드 연결·환경변수 입력은 사용자가 직접 진행.

**배포 후 발견한 버그**: 실제 배포 사이트에서 사용자가 "영상이 안 보인다"고 제보 — 확인해보니 영상 요청이 200과 503(서버 과부하)을 오갔다. `x-render-origin-server: uvicorn` 헤더로 Render 플랫폼이 아니라 내 앱까지 요청이 도달했다가 실패하는 것까지 확인했고, 반복 요청해보니 몇 초 뒤엔 다시 성공하는 패턴이 나왔다 — **Render 무료 티어(CPU 0.1코어·RAM 512MB)가 211MB 영상 스트리밍과 웹소켓 실시간 갱신을 동시에 감당 못 해 간헐적으로 실패**하는 것으로 결론지었다(로컬 Docker 테스트는 리소스 제약이 없어 100% 안정적이었던 것과 대조됨).

**해결**: 세 가지 대안(유료 플랜 업그레이드/영상 압축/영상만 외부 직접 재생) 중 사용자가 무료 티어 유지 + 외부 직접 재생을 선택 — `DEMO_VIDEO_URL`이 Render 서버를 거치지 않고 **브라우저가 GitHub Release URL로 직접 요청**하도록 `frontend/src/api.ts`를 수정했다. 이제 로컬 개발도 똑같이 이 URL을 쓰므로 로컬에 영상 파일을 따로 둘 필요가 없어졌고(README 갱신에도 반영), `Dockerfile`의 영상 다운로드 단계와 `main.py`의 `/demo-video/source.mp4` 라우트는 더 이상 안 쓰여 제거했다 — Render 서버는 이제 영상 트래픽을 전혀 처리하지 않는다. 재배포 후 네트워크 요청 로그로 GitHub 쪽 CDN이 206(Range 응답)을 안정적으로 주는 것과 화면에 실제로 영상이 재생되는 것을 확인했다.

**부가 정리**: README.md·backend/README.md를 "클론 → conda 환경 → 백엔드 → 프론트엔드"만 따라 하면 영상까지 포함해 바로 뜨도록 갱신하고, 실제로는 Vite가 읽지도 않던 죽은 `VITE_API_BASE_URL` 문서 줄을 제거했다. `backend/README.md`의 "폴더 역할" 설명도 예전 개인별 추적 기반 구조를 기준으로 낡아 있던 것을 51번 재설계 이후 실제 구조(화재 후 매초 2차 확인)에 맞게 정정했다.

## 59. 프로젝트 문서 전체 최신화 — CLAUDE.md, screen_guide.md, 두 README, 최종기획서 HTML

51번(개인추적 폐기 재설계) 이후 코드는 계속 바뀌었는데 프로젝트 문서들이 그 변화를 따라가지 못하고 있다는 지적을 받아, 폴더 전체를 훑으며 낡은 문서를 실제 구현 기준으로 다시 맞췄다.

## 60. 관리구역(소화기/전기패널/비상구) 감시 기능 전면 제거

화면 연결만 남겨뒀던 관리구역 감시 기능(SSIM 기반 변화 감지, 16번·54번 참고)을 백엔드 코드까지 포함해 완전히 제거했다.

**제거 이유**: 단일 RGB 카메라는 깊이 정보가 없어 "실제로 접근이 막혔는지"와 "카메라 시야선상에 다른 물체가 겹쳐 보일 뿐인지"를 구분할 수 없다는 구조적 한계를 사용자가 지적했다 — 예를 들어 소화기에서 떨어진 곳에 물건을 놓아도 카메라 각도상 소화기 앞을 가로지르는 것처럼 찍히면 SSIM은 무조건 "변화"로 판단한다. 이런 오탐이 반복되면 관리자가 알림을 무시하게 되는 경보 피로(alert fatigue)로 이어지고, 이는 "신뢰할 수 있는 안전 신호"라는 이 프로젝트의 핵심 원칙과 정면으로 배치된다고 판단해, 화면만 안 만드는 게 아니라 기능 자체를 걷어내기로 결정했다.

**제거 범위**:
- 백엔드: `app/rules/clearance_zone.py`(SSIM 변화 감지 로직)·`app/rules/clearance_zone_log.py`(로그) 파일 삭제, `app/models/schemas.py`에서 `ClearanceZoneType`/`ClearanceZoneDef`/`ClearanceZoneState`/`ClearanceZoneStatus`/`ClearanceZoneLogEntry` 삭제 및 `ZoneMapConfig.clearance_zones` 필드 제거, `app/api/zone_maps.py`에서 `/clearance-zones/...` 엔드포인트 4종 삭제, `app/api/incidents.py`·`app/inference/situation_probe.py`에서 관리구역 참조 제거
- 테스트: `test_clearance_zone.py`·`test_clearance_zone_log.py`·`test_clearance_zone_api.py` 삭제, `test_incidents_api.py`·`test_zone_maps_api.py`에서 관련 케이스만 제거
- 프론트엔드: `types.ts`의 `clearance_zones` 패스스루 필드 제거
- 문서: `CLAUDE.md`·`README.md`·`backend/README.md`·`docs/screen_guide.md`·`docs/LastSight_AI_최종기획서.html` 전체에서 관련 서술 삭제(기획서는 25개 섹션 중 15곳 이상에서 언급되고 있어 전부 훑어야 했다). 남겨둔 예전 개인추적 폐기 사례(vestigial)와 달리, 이번엔 "제외 기능" 같은 별도 표시 없이 존재 자체를 지우는 방식으로 정리했다 — 사용자가 명시적으로 이 방식을 요청했다.
- 데이터: git에 커밋돼 있던 `data/clearance_zone_logs/`(테스트용 런타임 로그) 삭제

**검증**: 삭제 후 `pytest` 전체 스위트가 76 passed / 14 failed(변경 전과 동일한, 무관한 사전 실패)로 회귀 없음을 확인했고, 프론트엔드 `tsc --noEmit`도 에러 없이 통과했다. 백엔드를 재시작해 `/openapi.json`에서 `clearance-zones` 관련 엔드포인트가 전부 사라진 것과 `/zone-maps/{camera_id}` 응답에 더 이상 `clearance_zones` 필드가 없는 것을 직접 확인했다.

## 61. "요약 브리핑" 버튼을 대화형 브리핑 챗봇으로 전환

3순위 아이디어(대화형 브리핑)를 구현했다. 배경: 2번(2차 확인 카드 관리자 검토)을 만들었다가 "관리자가 그 많은 카드를 수작업으로 검토한다는 게 실제로 말이 되나"는 지적으로 되돌린 뒤(60번 이후 세션), 대신 이 프로젝트의 핵심 차별점("확정 안 하는 AI")을 심사위원이 직접 유도신문해서 테스트해볼 수 있게 만드는 방향으로 옮겨갔다.

**구현**: 한 번 누르면 headline+points를 한 번만 반환하던 단발성 `generate_situation_summary()`/`POST /situation-summary`/`SituationSummaryModal`을 전부 걷어내고, 멀티턴 대화형으로 교체했다.
- 백엔드: `app/inference/briefing.py`에 `answer_chat_message()`(대화 이력+매 턴 새로 grounding한 데이터를 Gemini에 전달), `parse_time_hint()`(질문에서 "74초쯤"/"화재 나고 12초 후"/"오후 9시 55분쯤" 같은 시간 표현을 정규식으로 인식), `find_frame_near()`(그 시점에 가장 가까운 프레임을 situation_checks → ppe_violation_events → `scenario.json`의 사전계산 프레임 순으로 탐색 — 화재 전후 상관없이 영상 전체에 걸쳐 항상 뭔가는 찾아준다는 게 핵심). `app/api/situation_chat.py`(`POST /situation-chat`)가 이를 감싼다.
- 시스템 프롬프트에 PPE는 "명"이 아니라 "건"으로 답하라는 규칙을 추가했다 — 이 시스템은 개인을 추적하지 않으므로 "몇 명"에 정확히 답할 수 없다는 원칙을 챗봇에도 그대로 반영.
- 프론트엔드: 정적 모달을 걷어내고 `SituationChatPanel.tsx`(메시지 목록+입력창, 답변에 참고 프레임이 있으면 썸네일+클릭 시 확대)를 신설, 영상 옆에 배치(`.camera-row`) — 예전에 사이드바가 타임라인 너비를 잡아먹어 없앤 적이 있어(21번), 이번엔 영상 높이만큼만 차지하고 타임라인은 그대로 전체 너비를 쓰게 분리했다.

**실측으로 드러나 고친 문제 세 가지** (전부 사용자가 직접 테스트하다 발견):
1. **영상 입력 시도**: BDAI Gemini 게이트웨이에 실제로 짧은 영상 클립을 `video_url` 타입으로 보내봤더니 `Invalid content part type: video_url`로 거부됨을 직접 확인 — 영상 입력은 지원 안 됨이 확인돼, 대신 이미 매초 저장해두던 프레임 사진들을 시간 힌트로 찾아 보여주는 방식으로 확정했다.
2. **시간대 불일치**: 챗봇에 넘기는 모든 시각(지금 시각·화재 발생 시각·로그 시각)이 UTC 그대로였는데, 화면 나머지는 전부 KST(`toLocaleTimeString("ko-KR")`)로 보여주고 있어 9시간이 어긋나는 게 실측됐다 — `_kst_str()` 헬퍼로 Gemini에게 보여주는 시각을 전부 KST로 통일했다.
3. **마크다운 미준수**: "마크다운 쓰지 마라"는 시스템 프롬프트 지시를 Gemini가 완벽히 지키지 않아 `**굵게**`/`### 제목`/`---`/번호 목록이 섞여 나와 좁은 채팅 말풍선에서 가독성이 크게 떨어짐이 실측됐다 — 프롬프트만 믿지 않고 응답을 받은 뒤 정규식으로 마크다운 기호를 걷어내는 `_strip_markdown()` 후처리 안전망을 추가했다(프롬프트 보완과 후처리 안전망을 같이 두는 방어적 설계 — 이 프로젝트의 다른 안전장치들과 같은 결).

한 가지는 버그가 아니라 세션 중 코드 수정 때문이었다 — 백엔드 파일을 고칠 때마다 uvicorn `--reload`가 프로세스를 재시작하면서 메모리에 있던 시나리오 상태(화재경보·PPE 로그 전부)가 초기화됐다. 그 순간 질문하면 "위반 없음"처럼 텅 빈 상태를 정직하게 답하는 것뿐이었는데 언뜻 버그처럼 보였다 — 시나리오를 다시 안정적으로 돌려서 재확인해 정상 동작임을 확인했다.

**검증**: 시간힌트 파서·프레임 조회·`_kst_str`·`_strip_markdown` 단위테스트 다수 추가, `pytest` 전체 스위트 97 passed / 14 failed(기존과 동일한 무관 사전 실패)로 회귀 없음 확인. `tsc --noEmit` 통과. 데모 시나리오를 실제로 돌리며 3턴짜리 대화(요약 → "그래서 다 안전한 거 맞지?" → "오늘 안전장비 위반 몇 건이야?")를 연속 테스트해 각 5~10초 안에 정상 응답하고, 유도신문은 정확히 거부하며("아닙니다, 절대 안전하지 않은..."), 시간 힌트도 실제로 정확한 프레임(예: 화재+12초 → t=73.25초 프레임)을 찾아 답하는 것까지 확인했다.

## 62. 챗봇 사용성 문제 3건 추가 수정 (사용자 실측)

61번 배포 직후 사용자가 직접 써보면서 세 가지 문제를 더 발견했다.

1. **응답 중간 끊김**: 인원이 여럿(6명)이고 구역이 여러 개(A/B)일 때 Gemini가 사람을 한 명씩 자세히 나열하려다 `max_tokens`(1536)에 걸려 "A구역 4명:" 다음에서 문장이 끊기고 B구역은 언급도 안 되는 게 실측됐다. `max_tokens`를 2560으로 올리고, "인원별로 나열하지 말고 구역 단위로 요약하라"는 규칙을 시스템 프롬프트에 추가해 애초에 짧게 답하도록 유도했다 — 둘 다 필요했다(한도만 올리면 여전히 장황해질 수 있고, 프롬프트만 고치면 Gemini가 안 지킬 수 있으므로).
2. **마크다운 안전망 구멍**: 61번에서 `**볼드**`/`#`/`---`/번호 목록은 걸러냈는데, 재테스트하다 홑따옴표 `*기울임*`과 이모지(🚨👥📦)는 그대로 새어나오는 게 발견됐다. `_strip_markdown`에 단일 `*...*` 제거, 이모지 유니코드 범위 제거를 추가했다.
3. **평상시 안전 문구**: 화재 없는 평상시 요약에서 "안전하게 관리되고 있습니다", "평온한 상태" 같은 총평성 문구가 나오는 걸 발견해, 시스템 프롬프트에 "평상시에도 전체를 안전하다고 총평하지 않고 개별 관측 사실만 나열하라"는 규칙을 추가했다. 다만 화재 중 유도신문 거부(가장 중요한 케이스)는 이미 확실히 동작하는 걸 확인했고, 평상시 문구는 프롬프트 수준에서만 완화했다 — 실제 위험 상황이 아니라 후처리 안전망까지는 아직 안 만듦.

추가로, 시나리오를 시작할 때마다 채팅 패널이 자동으로 "지금까지 상황을 요약해줘"를 스스로 보내던 것(예전 "요약 브리핑" 버튼 자리를 그대로 대체하려던 설계)을 사용자가 "왜 시작하자마자 멋대로 질문이 올라가냐"고 지적해 없앴다 — 이제 패널은 빈 채로 뜨고 관리자가 직접 물어봐야 답이 온다(`SituationChatPanel.tsx`의 자동 전송 `useEffect` 제거, 빈 상태 안내 문구 추가).

**검증**: 마크다운/이모지 제거 단위테스트 2건 추가, `pytest` 99 passed / 14 failed(기존과 동일한 무관 사전 실패)로 회귀 없음. `tsc --noEmit` 통과. 끊김 재현 조건(A구역 4명·B구역 2명)을 그대로 재구성해 재테스트하니 두 구역 다 언급하며 문장이 완결되는 것과, 이모지·홑따옴표 기울임이 안 섞여 나오는 것을 직접 확인했다.
