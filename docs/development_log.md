# 개발 과정 기록 (발표자료·질의응답 대비용) — 핵심 요약본

이 문서는 SAIV(SafeAIVision) 프로젝트의 개발 과정을 핵심 의사결정 위주로 압축 정리한 요약본이다. 프로젝트명이 "LastSight AI"에서 "SAIV(SafeAIVision)"로 최종 확정되면서, 전체 이력을 담고 있던 기존 상세 로그는 `docs/development_log_archive.md`로 백업하고 이 문서를 새로 작성했다. 내용이 서로 다를 경우 `docs/SAIV_최종기획서.html`(최종 기획서)을 기준으로 삼는다.

---

## 1. 프로젝트 방향 설정

Superb AI × BDAI 해커톤 산업안전·물류 트랙, 시나리오 B-2("작업 환경 및 안전 장비 감지")를 출발점으로 삼아 재정의했다. 초기에는 "화재를 발견하는 AI가 아니라, 화재 신호는 관리자가 입력하고 그 이후 대응을 돕는 AI"로 설계했으나, 논의 끝에 **화재/연기 자동 탐지도 시스템에 포함**시키는 것으로 방향을 확장했다. 차별점은 "화재 탐지에서 그치지 않고, 화재경보 이후 대피 이행까지 끝까지 확인하는 AI"로 재정의했다.

Superb AI 멘토링 피드백을 받아, "화재 이후 잔류인원 추적"에만 집중하면 데이터 부족·인식 오류로 구현 난도가 지나치게 높아진다는 지적에 따라 **평상시 예방(PPE 상시 점검) + 비상시 대응(화재 탐지·대응)** 두 축 구조로 확장했다.

## 2. 핵심 파이프라인 두 차례 전환

**1차 전환 — 출구 통과 판정 폐기 → 관측 지속시간 모델**: 최초 설계는 "출구 가상선을 통과했는지" 판정하는 방식이었으나, 카메라 시야가 출구 바깥까지 잡지 못하는 경우(현장에서 흔함) 통과 확인 자체가 구조적으로 성립할 수 없다는 한계가 드러났다. 이에 따라 "화재경보 이후 각 작업자가 지금도 관측되고 있는지"만 보는 방식으로 전환했다.

**2차 전환 — 개인별 추적·상태값 전면 폐기 → 화재 후 매초 2차 확인 카드**: 관측 지속시간 모델(개인별 추적 + 4단계 상태값)을 실제 데모 영상에 돌려보니, 화면을 벗어났다 들어온 사람에게 예전 추적 ID가 잘못 재부착되는 문제가 반복 발견됐다. 신원 특정을 하지 않는 시스템 설계상 완벽한 재식별은 원천적으로 불가능하다는 결론을 내리고, 화재 발생 이후 개인별 추적·상태 판정 자체를 걷어냈다. 대신:
- 화재 모드에서는 감지된 사람 전원을 상태 구분 없이 초록 박스로만 표시
- 화재경보 발생 시점부터 **매초** 그 프레임을 ZERO로 2차 확인해 "체류중/쓰러진 사람/연기에 둘러싸인 사람" 카드를 하나씩 축적(프레임마다 새 합성 ID를 쓰므로 재부착 문제 자체가 발생할 수 없는 구조)

기존 ByteTrack 추적·상태 규칙 엔진·확인 우선순위 트리아지 코드는 vestigial로 남아있으나(단위 테스트만 유지) 실시간 파이프라인에서는 더 이상 쓰지 않는다. "관측이 끊겼다고 대피 완료로, 계속 관측된다고 위험 확정으로 간주하지 않는다"는 절대 원칙은 그대로 유지되며, 이제 "2차 확인 카드가 확정 선언이 아니라는 것"으로 구현된다.

## 3. 데이터 파이프라인 (BDAI 프로젝트 2개)

목적이 다른 두 BDAI 프로젝트로 분리 운영했다 — **SAIV PPE**(person/helmet/vest/no_vest/head)와 **SAIV Fire/Smoke**(fire/smoke).

**PPE**: Construction Site Safety(Roboflow, CC BY 4.0), SFCHD(화학공장 실사 CCTV, 12,373장, 공식 라이선스 표기 없음 — 학술 발표 데이터셋), SHWD(Safety Helmet Wearing Dataset, 저장소 MIT·이미지 출처 불명확), COCO 2017 person(경계-잘림 위주 샘플링, 다양성 보강), Kaggle Safety Vests Detection Dataset(CC BY 4.0), Roboflow runningperson(CC BY 4.0, "뛰는 사람" 인식 공백 보강)을 반입했다. 최종 라벨링 풀은 96,888장까지 확장됐다.

**Fire/Smoke**: Fire and Smoke Segmentation(Roboflow, CC BY 4.0)과 AI Hub 176 "화재 발생 예측 데이터"(공공데이터, 제3자 재배포 금지 조건)를 반입해 13,354장까지 확장했다.

라이선스가 불명확한 SFCHD·SHWD는 해커톤 운영진에게 별도 문의했으며, 두 데이터셋 모두 **실제 서비스에 배포된 모델의 학습에는 쓰이지 않았다**(서비스 기본값은 ZERO — 아래 5번 참고).

## 4. 모델 실험 — PPE(6차) / Fire·Smoke(4차)

**PPE**: 1차 베이스라인(mAP 0.493) → 2차 연기 증강(mAP 0.759) → 3차 "뛰는 사람" 보강 시도(모션 블러 코드 결함 발견, 학습 취소) → 4차 색상편향 대응(SFCHD vest 66.8% 파란색 편향 실측 확인, 데이터 다양성 부족 원인 규명 후 취소) → 5차 데이터 전면 재구성(SHWD·COCO 반입, RF-DETR Nano, mAP 0.4199) → 6차 데이터 대량 확장(RF-DETR Large, 29,005장 캡 샘플링, mAP 0.579·mAP@50 0.837·precision 0.886·recall 0.838).

**Fire/Smoke**: 1차 베이스라인(195장, mAP 0.01) → 2차 AI Hub 176 반입 후 재학습 3회 시도 전부 인프라 장애로 실패/취소 → 3차 클립 단위 stride 서브샘플링(1,844장) 학습은 완료됐으나 epoch 4 정점 후 0으로 붕괴(BDAI가 정점이 아닌 마지막 epoch를 최종 모델로 저장하는 것도 이때 확인) → 4차 segmentation→detection 태스크 전환(라벨의 37%가 실제로는 bbox였음을 발견), rf-detr-nano, mAP 0.587·mAP@50 0.891·precision 0.907·recall 0.887로 성공.

## 5. ZERO vs 커스텀 모델 — 최종적으로 ZERO 채택

두 모델 모두 검증 지표만 보면 커스텀 학습 모델이 양호했으나, 데모 영상으로 ZERO(제로샷 파운데이션 모델)와 직접 비교 실측한 결과:

- **PPE**: 붐비는 장면(5~6명)에서 커스텀 모델은 person을 한 명도 못 잡았으나(0/6), 같은 프레임의 helmet/vest는 정상 탐지 — person 클래스만 학습이 덜 됐다는 뜻. COCO의 "경계-잘림" 위주 샘플링이 실제 CCTV의 "여러 명이 겹쳐 선" 분포와 맞지 않았던 것으로 진단.
- **Fire/Smoke**: 화재가 없는 장면(t=30초)에서 커스텀 모델이 화재경보 임계값을 넘는 신뢰도(0.945)로 **오탐**했다(ZERO는 0건, 정확). 화면 속 빨간 소화기를 "불"로 오인했을 가능성. 반대로 실제 화재 진행 중(t=60~85초)에는 커스텀 모델의 fire 신뢰도가 ZERO보다 대체로 높아, 민감도 자체는 낮지 않았다.

**결론**: 검증 지표가 좋아도 학습 데이터의 장면 다양성이 부족하면(SFCHD가 실제로는 215개 세션 반복촬영에 불과했던 것처럼) 실사용에서 파운데이션 모델보다 못할 수 있다는 것, 특히 Fire/Smoke는 오탐이 잦으면 경보 피로(alert fatigue)로 이어질 수 있다는 것을 직접 검증했다. 서비스 기본값은 PPE·Fire/Smoke 모두 **ZERO**로 확정했고, 커스텀 모델은 배포 상태로 남겨 데이터 보강 시 즉시 재전환 가능하게 했다.

## 6. 서비스 구현

- **평상시/비상시 자동 전환 대시보드**: 평상시는 PPE 준수율·구역별 인원, 비상시는 현재 관측 인원·화재경보 배너로 자동 전환
- **PPE 미착용 로그**: 추적을 쓰지 않고 위치+시간 기반으로 중복 없이 증거 사진과 함께 기록, 관리자가 카드를 열어 직접 정정 가능(원판정은 감사 기록 유지)
- **구역(zone) 편집 UI**: 관리자가 카메라 화면에 폴리곤을 직접 그리고 이름 붙임
- **통합 타임라인**: 평상시 PPE 이력 + 화재 발생 + 2차 확인을 하나의 시간축에 표시, 드래그로 중복 노드 병합
- **구조 브리핑 챗봇**: 지금까지 기록된 데이터(+시간 힌트가 있으면 그 시점 프레임)를 근거로 Gemini(BDAI 테넌트 게이트웨이 재사용)가 자유 질문에 답함. 마크다운 후처리 안전망, 유도신문 거부 등 안전 원칙을 시스템 프롬프트에 강제
- **배포**: Render에 단일 Docker 서비스로 배포(백엔드가 프론트엔드 빌드까지 서빙), 외부 접속 가능

## 7. 이후 수정 사항

**2026-08-16 — PPE 판정 검토 카드 bbox 정렬 오류 수정**: Figma 기반 UI 동기화 커밋(`8e24ca3`)에서 상세 모달(`PpeViolationEditModal`/`SituationDetailModal`)의 증거 이미지에 `object-fit: cover`(비율 유지하며 잘라서 채움)를 적용했는데, bbox를 그리는 SVG 오버레이는 `preserveAspectRatio="none"`(비율 무시하고 늘려서 채움)을 그대로 쓰고 있어 서로 다른 스케일링 방식이 충돌 — 이미지 속 사람과 판정 박스가 어긋나 보이는 문제가 있었다. 이미지는 `object-fit: contain`, SVG는 `preserveAspectRatio="xMidYMid meet"`으로 통일해(둘 다 잘리지 않고 letterbox로 중앙 정렬) 좌표계를 일치시켰다.

이어서 PPE 검토 목록 카드(`PpeViolationCard.tsx`) 썸네일에서도 같은 증상이 보고됐는데, 원인은 달랐다 — 이 카드는 실제 `bbox_xyxy`를 전혀 안 쓰고 있었다. 카드 썸네일 위에 그려지던 빨간 박스는 `top:40px; left:calc(50% - 27px); width:54px; height:112px` 같은 **고정 좌표의 장식용 사각형**(Figma 디자인에서 그대로 가져온 값)이었을 뿐, 실제 감지 위치와는 애초에 무관했다. 실제 `entry.bbox_xyxy`를 받아 그리는 SVG 오버레이로 교체하고(모달과 동일하게 `frameWidth`/`frameHeight`를 `App.tsx`에서 전달), 이미지도 `object-fit: contain`으로 맞춰 정합성을 갖췄다.

## 8. 남은 것 / 알려진 한계

- 사고 리플레이(화재경보·PPE 로그 병합 타임라인): 백엔드 API·로직은 완성됐으나 프론트엔드 화면 연결은 아직 안 함
- 커스텀 fire/smoke·PPE 모델은 학습 데이터가 소수 영상 클립뿐이라 낯선 장면 일반화가 부족(그래서 서비스는 ZERO 사용)
- ZERO는 플랫폼이 스케줄에 따라 켜고 끄는 공유 엔드포인트라 워밍업 중 호출 실패 가능
- 라이선스가 불명확한 SFCHD·SHWD는 해커톤 운영진 확인 요청 중 — 실제 서비스에는 영향 없음(ZERO 사용)
