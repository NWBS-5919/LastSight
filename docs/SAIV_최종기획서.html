1. 한 문장 문제 정의

공장 CCTV는 평상시 PPE 미착용을 사람이 계속 지켜보기 어렵고, 화재 발생 시에도 경보가 늦거나 경보 이후 각 작업자가 위험구역에 얼마나 오래 머무는지를 관리자가 즉시 파악하기 어렵다.

2. 제안 배경

2-1. 기존 화재 대응의 구조

(평상시) 사람이 직접 순찰하며 PPE 착용 상태 확인 — 인력·시간 한계로 상시성 부족 → 화재감지기 작동 또는 육안 발견 → 경종·시각경보·비상방송 → 작업자 대피 → 집결지에서 수동 인원 확인 → 미확인자가 있으면 관리자·동료에게 질문 → CCTV를 되돌려 마지막 위치 확인

공백은 두 군데에 있다. 첫째, "평상시 위험 요소가 방치되는 것"과 "누군가 발견하는 것" 사이. 둘째, "화재가 발생했다는 사실을 알리는 것"과 "경보 이후 각 작업자 상태를 파악하는 것" 사이다.

2-2. 기존 방식의 한계

현재 방식현장 한계
순찰로 PPE 착용 상태 확인순찰 간격 사이의 공백은 방치될 수 있음
화재감지기(열/연기 센서) 의존초기 미세 연기·화염을 놓치거나 오탐이 잦을 수 있음
출근명부·출입기록으로 재실자 확인이미 퇴근하거나 일시 외출한 사람이 포함될 수 있음
집결지에서 이름을 부르며 확인소음, 혼란, 부상, 언어 차이로 확인이 지연될 수 있음
관리자가 CCTV를 직접 재생여러 카메라의 과거 영상을 짧은 시간 안에 검토하기 어려움
카메라에서 사람이 사라지면 판단 불가대피, 가림, 사각지대 이동을 구분하기 어려움

3. 서비스 정의

3-1. 정식 주제명

RGB CCTV 기반 평상시 안전 예방 및 화재경보 이후 매초 상황 재확인 시스템

3-2. 서비스 소개

SAIV는 기존 CCTV 영상을 활용해 평상시에는 PPE 미착용을 상시 감시하고, 비상시에는 화재/연기를 자동 탐지해 경보를 트리거한 뒤 화재경보 이후의 매 순간을 다시 확인해 "지금 이 순간 무엇이 보이는지"를 카드로 남기는 통합 산업안전 서비스이다. 카메라 시야가 출구 바깥까지 잡지 못하는 현실적 제약 때문에 "출구를 통과했는지"나 개인별 체류시간 자체는 판정하지 않는다 — 대신 화재경보 이후 매초 그 프레임을 다시 확인해 카테고리별 인원(체류중/쓰러진 사람/연기에 둘러싸인 사람)만 사실로 남긴다.

2차 확인 카테고리정의
체류중우려 신호 없이 그 순간 관측만 됨
쓰러진 사람ZERO 2차 확인에서 우려 신호가 잡힘 — 확인 필요
연기에 둘러싸인 사람ZERO 2차 확인에서 우려 신호가 잡힘 — 확인 필요

개인별 추적·체류시간 판정(inside_observed/prolonged_presence/tracking_lost/camera_failure)은 초기 설계였으나, 화면을 들락날락하는 사람마다 추적 ID가 계속 새로 매겨져 "얼마나 오래 관측됐는지"가 사실상 의미 없는 값이 되는 문제를 실측으로 확인하고 폐기했다(2026-08-04 재설계 — 25번 최종요약의 설계 변경 이력 참고). 비상시 화면에는 그래서 사람마다 다른 상태를 표시하지 않고, 탐지된 모든 사람을 동일한 초록 박스로만 보여준다.

3-3. 핵심 가치

화재 발생 사실을 알리는 데서 그치지 않고, 평상시에는 위험 요소를 상시 감시하고 화재 이후에는 매초 다시 확인한 사실만 쌓아 관리자가 여러 CCTV를 직접 되돌려보는 시간을 줄인다. 지금까지 쌓인 기록은 버튼 하나로 Gemini 기반 요약 브리핑으로도 확인할 수 있다.

5. 주제의 경쟁력

5-1. 문제 재정의의 차별성

SAIV는 화재·연기 탐지, PPE 감지 같은 단일 기능에 머무르지 않고, 평상시와 비상시 두 축의 사건 흐름을 연결한다.

[평상시] 사람·PPE 탐지 → 착용 판정 → 위반 로그 기록 [비상시] 화재/연기 탐지 → 경보 자동 트리거 → 매초 ZERO 2차 확인(우려 상황 문구 대조 + 그 순간 사람 박스와 위치 매칭) → 카테고리별 인원 집계(체류중/쓰러진 사람/연기에 둘러싸인 사람) → 통합 타임라인에 이정표로 기록 → (필요 시) Gemini 요약 브리핑

6. 서비스 범위와 안전한 표현

6-1. 시스템이 판단하는 것

  • CCTV 화면에 보이는 사람(개인별 추적 ID는 화재경보 이후엔 사용하지 않음)
  • 작업자가 위치한 카메라·구역
  • PPE(안전모·안전조끼) 착용 여부
  • 화재/연기 여부와 경보 트리거
  • 화재경보 후 매초 재확인한 그 순간의 인원과 카테고리(체류중/쓰러진 사람/연기에 둘러싸인 사람)
  • 지금까지 쌓인 기록을 근거로 한 요약 브리핑
  • 제한된 보호구·복장 정보

6-2. 시스템이 판단하지 않는 것

  • 공장 전체의 정확한 총인원
  • CCTV가 없는 공간의 재실 여부
  • 작업자가 출구를 통과했는지 여부(카메라가 문 바깥을 못 보는 경우가 현실적으로 흔해 판정 대상에서 제외)
  • 특정 작업자가 화재경보 후 얼마나 오래 머물렀는지(개인별 체류시간 — 화면을 들락날락할 때마다 추적 ID가 계속 바뀌어 의미 있는 값을 만들 수 없어 판정 대상에서 제외)
  • 지금 화면에 없는 작업자가 실제로 안전한지 위험한지
  • 얼굴 기반 신원·국적·인종·성별·나이·체형
  • AI 단독 전원 안전·전원 대피 완료 선언
핵심 표현 원칙: "잔류자를 확정한다"가 아니라 "CCTV 관측 범위 내에서 관측/미관측 상태를 분류하는 보조 시스템"이라고 설명한다.

7. 전체 서비스 작동 흐름

1단계. 평상시 모니터링

  • CCTV 영상에서 사람·PPE(안전모·조끼)를 상시 탐지한다.
  • head+helmet IoU 기반으로 안전모 착용 여부를 기하학적으로 판정한다(색상 편향에 덜 취약).
  • 이름·사번·얼굴 정보와 연결하지 않는다.

2단계. 화재/연기 자동 탐지 및 경보 트리거

  • fire/smoke 탐지 결과가 최근 프레임의 일정 비율 이상 임계값을 넘으면 자동으로 화재경보를 발생시킨다(단발성 오탐 방지).
  • 관리자 수동 입력은 자동 탐지를 놓치는 경우를 위한 보조 오버라이드로 유지한다.
  • 화재경보 발생 시각·구역을 append-only 로그로 기록한다.

3단계. 다국어·시각 대피 안내

사업장에서 사전에 등록한 주요 언어를 동시에 출력하고, 얼굴을 보고 국적이나 사용할 언어를 추정하지 않는다.

4단계. 화재경보 이후 매초 2차 확인

  • 화재경보가 뜨는 순간부터 개인별 추적은 쓰지 않고, 초당 한 번씩 그 프레임을 ZERO에 다시 확인시킨다.
  • "쓰러진 사람", "연기에 둘러싸인 사람" 등 우려 상황 문구 여러 개를 동시에 개방형 어휘 탐지로 던져, 걸린 박스를 그 순간 감지된 사람 박스와 위치(중심점 거리)로 매칭한다.
  • 매칭 결과로 그 순간의 카테고리별 인원(체류중/쓰러진 사람/연기에 둘러싸인 사람)을 집계한다 — 카테고리 합계는 항상 그 순간 감지된 인원수와 같다.
  • 화면에는 사람마다 다른 상태를 표시하지 않는다 — 개인별 체류시간 판정은 화면 이탈·재진입마다 추적 ID가 계속 바뀌어 의미를 가질 수 없다는 걸 실측으로 확인하고 폐기했기 때문이다(3-2번 참고). 탐지된 모든 사람은 동일한 초록 박스로 표시한다.

5단계. 통합 타임라인 이정표 생성

매초 쌓이는 확인 기록을 전부 화면에 표시하면 타임라인이 도배되므로, 카테고리별로 "지금까지의 최고 인원 기록"을 새로 경신할 때만 이정표로 뽑아 타임라인에 추가한다. 평상시 PPE 위반 이력, 화재 발생 시점과 한 줄로 이어서 표시해 화재가 나도 이전 기록이 화면에서 사라지지 않는다.

6단계. 구역별 상황 카드 저장

  • 그 순간의 캡처 프레임(전체 화면)과, 그 위에 그릴 사람별 박스+카테고리를 함께 저장한다.
  • 나중에 카드를 다시 열어도 "어느 사람이 쓰러진 사람으로 잡혔는지" 사진 위에 표시할 수 있다.
  • 우려 신호(쓰러진 사람/연기에 둘러싸인 사람)가 하나라도 있으면 카드에 "확인 필요" 배지를 붙인다 — 확정이 아니라 신호일 뿐이다.

7단계. 요약 브리핑

관리자가 타임라인의 "요약 브리핑" 버튼을 누르면, 지금까지 기록된 화재경보·구역별 인원·2차 확인·PPE 위반 데이터를 근거로 Gemini가 headline과 불릿 포인트로 상황을 요약한다. 화면에는 항상 "AI가 자동 생성한 추정 정보 — 확정 아님" disclaimer가 함께 표시된다.

8단계. 관리자 검토

  • AI가 만든 2차 확인 카드·요약 브리핑은 관리자가 최종 확인한다.
  • 공모전 MVP에서는 소방기관 시스템으로 자동 전송하지 않는다.
  • 화재경보/PPE 로그를 병합해 특정 시각 상태를 재구성하는 사고 리플레이 API는 백엔드에 구현돼 있으나, 시간 관계상 프론트엔드 화면은 아직 없다(docs/screen_guide.md "백엔드는 준비됐지만 화면이 아직 없는 것" 참고).

9. Superb AI 플랫폼 활용 계획

Step 1. 데이터 선별

  • 자체 촬영 영상 검토(person/helmet/vest + 추적·관측지속시간 판정 테스트용)
  • 공개 데이터셋 라이선스·클래스 정의 확인 후 채택(CC BY 4.0 등)
  • fire/smoke는 자체 촬영 대신 공개 데이터셋 활용(실제 발화 불가)

Step 2. 데이터 구축 및 라벨링

  • PPE 프로젝트와 Fire/Smoke 프로젝트를 목적이 달라 별도로 분리 생성
  • 클래스 정의(4-1) 및 속성 등록
  • SDK로 라벨 반입 후 스냅샷 생성 — 학습은 항상 스냅샷 기준

Step 3. 모델 학습 및 실험

  • PPE: rf-detr-nano로 베이스라인 → 연기 증강 → 뛰는 자세 보강 → 색상 편향 대응 → no_vest/head 보조 클래스 순으로 반복 개선
  • Fire/Smoke: segmentation 시도 → 데이터 다양성·라벨 불일치로 실패 진단 → detection(rf-detr-nano)으로 전환해 해결
  • ZERO 파운데이션 모델과 커스텀 모델의 실사용 성능을 비교해 최종 배포 판단

Step 4. 서비스 구현 및 데모

  • 추론 결과를 화재경보 후 매초 ZERO 2차 확인과 위치 매칭 집계로 연결
  • 평상시 PPE 이력+화재 발생+2차 확인을 잇는 통합 타임라인, 구역별 상황 카드, Gemini 요약 브리핑 구현
  • 구역 편집 UI, 대시보드(평상시/비상시 자동 전환) 제작
  • 실제 영상 기반 시연, Render로 외부 접속 가능하게 배포

가장 큰 교훈: 검증 지표가 좋아도 학습 데이터의 장면 다양성이 부족하면 실사용에서 파운데이션 모델(ZERO)보다 못할 수 있다. 이걸 직접 검증하고 데이터 기반으로 최종 배포를 결정하는 과정 자체가 이번 프로젝트의 실험적 성과다.

14. MVP 구현 범위

14-1. 필수 구현 — 비상시 대응

  • 고정 카메라 영상 입력
  • 화재/연기 자동 탐지 + 경보 자동 트리거(5초 주기 샘플링, 2회 연속 감지 시 확정)
  • 화재경보 발생 시점부터 매초 그 프레임을 2차 확인해 카테고리별 인원(체류중/쓰러진 사람/연기에 둘러싸인 사람) 집계
  • 감지된 사람 전원을 실시간 박스로 표시(개인별 상태 구분 없음)
  • 구역 매핑(관리자가 폴리곤을 직접 그리고 이름 붙이는 편집 UI)
  • 평상시 PPE 이력 + 화재 발생 + 2차 확인을 잇는 통합 타임라인
  • 지금까지 기록을 근거로 한 Gemini 요약 브리핑
  • 화재경보·PPE 상태 변화 타임스탬프 로그, 외부 접속 가능한 배포(Render)

14-2. 필수 구현 — 평상시 안전관리

  • PPE(안전모·조끼, 각각 on/off 토글 가능) 상시 미착용 감지 — 추적 없이 person 박스마다 그때그때 판정
  • 위반은 위치+시간 기반으로 중복 없이 증거 사진과 함께 기록, 관리자가 카드를 열어 직접 정정 가능(원판정은 감사 기록으로 유지)
  • 위치 매칭 실패로 쪼개진 중복 노드는 타임라인에서 드래그로 병합
  • 평상시/비상시 모드 전환(화재경보 발생 시 자동)

14-3. 구현했지만 화면 연결은 아직 안 한 것

백엔드 API·규칙·테스트는 완료됐으나 시간 관계상 프론트엔드 화면을 아직 붙이지 못했다 — 로직은 그대로 있으므로 화면만 붙이면 동작한다.

  • 사고 리플레이 — 화재경보/PPE 로그를 병합해 특정 시각 상태 재구성

14-4. 차별화 기능(구현·화면 연결까지 완료)

  • 매초 2차 확인 + 위치 매칭 집계 — 화재경보 이후 초당 한 번씩 ZERO로 그 순간을 재확인해 "지금 이 순간의 사실"만 카드로 쌓음(개인별 체류시간 추적 없음)
  • 평상시 PPE 이력·화재 발생·2차 확인을 잇는 통합 타임라인 — 화재가 나도 이전 기록이 화면에서 사라지지 않음
  • 요약 브리핑 — 지금까지 기록을 근거로 Gemini가 headline+불릿 포인트를 자동 생성(항상 "추정 정보" disclaimer 동반)

14-5. 제외 기능

  • 실제 119 시스템 자동 연동
  • 얼굴인식과 사번 매칭
  • 공장 전체 다중 카메라 Re-ID
  • 체형·성별·나이·국적 추정

  • 소화기 사용 또는 가연성 물질 제거 행동 명령

15. 데모 시나리오

  1. 작업자 여러 명이 공장 내부에서 평상시처럼 작업한다 — 대시보드는 평상시 모드(오늘 PPE 미착용 적발 건수, 현재 관측 인원, 구역별 인원)를 표시한다.
  2. 한 명이 안전모를 벗는다 — PPE 미착용이 즉시 감지되어 타임라인에 노드로 기록된다. 관리자는 카드를 열어 증거 사진을 보고 필요하면 판정을 직접 정정할 수 있다.
  3. 연기가 감지되어 화재경보가 자동으로 트리거된다 — 대시보드가 비상시 모드로 자동 전환되고, 타임라인에 발광 효과가 있는 화재 노드가 추가된다.
  4. 전광판과 음성으로 사용 가능한 출구를 다국어 안내한다.
  5. 화재경보가 뜬 순간부터 개인별 상태 구분 없이, 화면에 감지된 모든 사람이 동일한 초록 박스로 표시된다.
  6. 화재경보 이후 매초 그 프레임을 ZERO로 다시 확인해 "체류중/쓰러진 사람/연기에 둘러싸인 사람" 카테고리별 인원을 집계한다. 카테고리별 "지금까지의 최고 기록"을 새로 경신할 때만 타임라인에 이정표로 표시된다.
  7. 우려 신호(쓰러진 사람 등)가 잡히면 해당 이정표와 카드에 "확인 필요" 배지가 붙는다 — 구조 필요 확정이 아니라 신호일 뿐임을 카드에 항상 명시한다.
  8. 관리자가 타임라인 오른쪽 하단 "요약 브리핑" 버튼을 누르면, 지금까지 기록된 화재경보·구역인원·2차 확인·PPE 위반 데이터를 근거로 Gemini가 headline과 불릿 포인트로 상황을 요약한다.

화면은 하나다 — App.tsx 페이지 한 장이 화재경보 유무로 테마·통계 카드 구성만 자동 전환하고(파랑/평상시 ↔ 빨강/비상시), 세부 정보는 모달로 여닫는다. 별도 라우팅은 없다.

19. 서비스 한계

  • CCTV가 설치되지 않은 구역은 분석할 수 없다.
  • 화장실·탈의실처럼 촬영이 제한된 공간의 재실자는 확인할 수 없다.
  • 심한 연기·정전·카메라 파손 이후에는 마지막으로 확보된 프레임 이후 상황을 알 수 없다.
  • 화재경보 이후 개인이 얼마나 오래 한 자리에 머물렀는지는 판정하지 않는다 — 추적 ID 재부착 문제를 실측으로 확인하고 폐기했기 때문이다(17번 참고). "그 순간 무엇이 보였는지"만 매초 기록으로 남는다.
  • 커스텀 fire/smoke 모델은 학습 데이터가 8개 영상 클립뿐이라 낯선 장면에서는 검증 지표만큼의 성능을 보장하지 않는다(그래서 서비스 기본값은 ZERO를 사용).
  • ZERO는 플랫폼이 스케줄에 따라 켜고 끄는 공유 엔드포인트라 워밍업 중 호출이 실패할 수 있다.
  • 요약 브리핑은 지금까지 기록된 데이터를 근거로 AI가 자동 생성한 추정 문장이며, 관리자 판단을 대체하지 않는다.
  • 사고 리플레이는 백엔드 로직·API까지는 완성됐으나 프론트엔드 화면이 아직 없어 이번 데모에서는 직접 확인할 수 없다.
  • AI 결과만으로 소방대원의 진입 여부나 수색 경로를 결정해서는 안 된다.
  • 실제 화재영상이 아닌 연출·합성 데이터를 사용하므로 현장 성능은 별도 검증이 필요하다.

20. 기대 효과

대상기대 효과
안전관리자평상시 PPE 준수 상태를 상시 확인하고, 여러 CCTV를 직접 되돌려보는 시간을 줄여 확인이 필요한 대상을 빠르게 파악
방재실화재경보 이후 매초 쌓이는 확인 카드와 요약 브리핑으로 상황을 구조화하여 파악
자위소방대우려 신호(쓰러진 사람 등)가 잡힌 구역을 빠르게 식별

23. 최종 발표 구성

문제

평상시 위험 요소는 상시 감시가 어렵고, 화재경보가 울려도 이후 각 작업자의 상태를 자동으로 확인하기 어렵습니다.

해결책

SAIV는 CCTV로 PPE를 상시 감시하고, 화재/연기를 자동 탐지해 경보를 트리거한 뒤 매초 그 순간을 다시 확인해 확인이 필요한 대상을 알려줍니다.

안전 원칙

화면 밖으로 나간 작업자를 대피 완료로, 계속 보인다고 위험 확정으로 간주하지 않습니다. AI는 전원 안전을 단독 선언하지 않습니다.

차별점

화재 탐지에서 그치지 않고, 화재경보 이후 대피 이행까지 끝까지 확인하는 AI입니다.

24. 심사위원 예상 질문과 답변

Q1. 카메라에서 사람이 사라지면 대피한 것으로 잘못 판단하지 않나요?

아니다. 이 시스템은 출구 통과 여부 자체를 판정하지 않는다 — 카메라가 문 바깥까지 못 보는 경우가 현실적으로 흔해, "통과 확인"이 구조적으로 성립하기 어렵다는 걸 검증하고 폐기했다. 화면 밖으로 나간 사람은 그 순간 이후 2차 확인 카드에 그냥 안 잡힐 뿐이며, 별도의 "관측 끊김" 상태를 표시하거나 안전/위험을 확정하지 않는다.

Q2. 잔류 인원 수를 정확하게 알 수 있나요?

공장 전체 잔류 인원을 확정하는 시스템은 아니다. CCTV 관측 범위 내에서 그 순간 감지된 인원과 카테고리만 매초 기록하는 보조 시스템이다.

Q3. 왜 자체 학습한 fire/smoke 모델 대신 ZERO를 쓰나요?

커스텀 모델은 검증 지표(F1 0.897)는 좋았지만, 학습 데이터가 영상 8개 클립뿐이라 실사용에서는 훨씬 넓은 범위로 학습된 ZERO보다 일반화가 떨어지는 것을 직접 확인했다. 검증 지표만 믿지 않고 데이터 기반으로 서비스 배포를 판단한 사례다. 배포는 그대로 남겨 언제든 전환 가능하다.

Q4. 작업자가 화재경보 후 얼마나 오래 그 자리에 있었는지는 왜 안 보여주나요?

처음엔 ByteTrack 계열 추적으로 개인별 체류시간을 판정하는 걸 목표로 했다. 하지만 실제 데모 영상에 돌려보니, 화면을 벗어났다 다시 들어온 사람에게 예전 추적 ID가 잘못 재부착되는 문제가 반복적으로 나타났다. 얼굴인식 등 신원 특정 기법을 쓰지 않는 이 시스템 설계상 완벽한 재식별은 원천적으로 불가능하다는 결론을 내리고, 화재 이후 개인별 추적·체류시간 판정 자체를 걷어냈다(2026-08-04 재설계). 대신 화재경보 후 매초 그 프레임을 다시 확인해 "그 순간 몇 명이 보였고, 그중 우려 신호가 있었는지"만 사실로 남긴다 — 부정확한 체류시간보다 정확한 순간 기록이 안전상 더 신뢰할 수 있다고 판단했다.

Q5. 왜 얼굴인식을 사용하지 않나요?

신원 자동식별이 반드시 필요하지 않고 개인정보 부담이 크기 때문이다. 2차 확인 카드에는 그 순간의 캡처 사진과 제한된 보호구·복장 정보만 제공한다.

Q6. Superb AI 플랫폼은 어디에 사용하나요?

데이터셋·프로젝트 생성, 클래스 스키마 설계, 라벨 반입, 스냅샷 관리, 모델 학습, ZERO 파운데이션 모델 호출, 모델 배포까지 SDK로 전 과정을 코드화해 재현 가능한 파이프라인으로 구축했다.

최종 기획 문장
SAIV는 평상시에는 PPE를 상시 감시하고, 화재 발생 시 다국어와 시각정보로 대피를 안내하며 화재/연기를 자동 탐지해 경보를 트리거한다. 경보 이후에는 개인별 체류시간을 추정하는 대신 매초 그 프레임을 다시 확인해 "지금 이 순간의 사실"만 카드로 쌓고, 필요한 순간엔 우려 신호를 강조 표시하며, 지금까지의 기록을 근거로 한 요약 브리핑을 제공함으로써 현장 관리자의 대응을 지원한다.
